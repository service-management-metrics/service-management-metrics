# リスクと統制のメトリクス

**リスクの仕事は、何がうまくいかない可能性があり、それに対して何をしているかについての継続する対話である。したがって、台帳を短く生きたものに保ち、重要な統制をテストし、不確実性を整って見せるあらゆる数字を疑う。**

## 概要と動機

サービスへのあらゆる変更はリスクを伴い、放置することもまた同様です。[リスク管理（risk management）](https://en.wikipedia.org/wiki/Risk_management)は、リスクの特定、評価、優先順位付けと、それに続く、それらを減らす、受容する、移転する、回避するための協調した行動です。ITILは、リスクをすべてのプラクティスを貫く糸として扱います。変更実現は変更がどれだけの精査を要するかを決め、サービス継続は中断に備え、情報セキュリティは脅威から守ります。アジャイルとDevOpsの働き方は、異なる方法でリスクを減らします。速いフィードバックと元に戻す能力を伴い、継続的に届けられる小さな変更は、各変更をより危険でなくし、問題をより早く見えるようにします。

二つの見方は、測定値で出会います。継続的に提供するチームも、自分たちの主なリスク、誰がそれを所有するか、頼っている統制が機能するかを知る必要があります。重い承認を主張するリスク機能も、その統制が害を減らし、単に人々を遅くしているだけではない証拠を必要とします。このトピックは両方のための測定値を与え、セキュリティと監査についての隣のトピックに述べられたプラクティスの上に築かれています（トピック 8.1「セキュリティインシデントと脆弱性のメトリクス」とトピック 8.3「コンプライアンスと監査のメトリクス」を参照）。

四つの用語が繰り返されます。

- **リスク：** 起きたときに目的に影響する、不確実なイベントまたは状態。原因、イベント、結果を持ち、可能性と影響は通常、知られているのではなく、見積もられる。
- **リスク台帳：** オーナー、評価、対応を伴う、特定されたリスクの一覧。[リスク台帳（risk register）](https://en.wikipedia.org/wiki/Risk_register)は、最新で読まれていれば作業の道具であり、そうでなければコンプライアンスの成果物である。
- **統制：** レビュー、自動テスト、承認、職務分掌、監視のアラートなど、リスクを減らす行動または仕組み。組織が頼る統制の集合は、その[内部統制（internal control）](https://en.wikipedia.org/wiki/Internal_control)システムである。
- **主要リスク指標（KRI）：** 損失が起きる前に、リスクの水準の変化を知らせる測定値。[主要リスク指標（key risk indicator）](https://en.wikipedia.org/wiki/Key_risk_indicator)は、イベントに先行し、誰かがそれに基づいて行動するときに有用である。

リスクの定量化には、よく知られた弱点があります。可能性を影響に対して色付きのセルの格子にプロットする[リスクマトリクス（risk matrix）](https://en.wikipedia.org/wiki/Risk_matrix)は、広く使われ、広く批判されています。評価は主観的で、異なるリスクが異なる理由で同じセルに入りえ、順序尺度のスコアを掛け合わせる算術には確かな根拠がありません。[ブラックスワン理論（black swan theory）](https://en.wikipedia.org/wiki/Black_swan_theory)を通じて記述されることがある、まれで深刻なイベントは、特に評価が難しいものです。誠実な対応は、マトリクスを対話の補助として使い、範囲を示し、統制とインシデントについての証拠でそれを支えることです。リスクを所有するチーム、それを監督するチーム、独立した保証を分ける、三つの防衛線の枠組みは、役割の構造を提供し、第一線、つまりデリバリーと運用のチームが本当に自分たちのリスクを所有するときに最もうまく機能します。

[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、リスクの報告に特有の形で当てはまります。赤い評価が精査を招くと、人々はリスクを黄色と評価します。クローズされたリスクが成功だと、人々は対処せずにリスクをクローズします（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

## 主要な原則

- **台帳を短く最新に保つ。** レビューされる、よくオーナーのいる少数のリスクは、そうでない何百ものリスクに勝る。
- **第一線に自分たちのリスクを所有させる。** 仕事に最も近い人々が、それを最もよく知っている。
- **頼る統制をテストする。** 一度もテストされていない統制は、願いである。
- **誰かが行動する先行指標を優先する。** 対応計画のない指標は飾りである。
- **偽の精度ではなく、範囲と証拠を示す。** 評価は見積もりである。
- **変更を小さく元に戻せるものにしてリスクを減らす。** 速いロールバックを伴う継続的デリバリーは統制である。
- **非難なくリスクについて話す。** 誠実な報告は、実践全体の原料である。

## 推奨事項

### リスクの対話を生かし続ける

**1. 台帳を短く保ち、各リスクを標準の形で書く。** 「[原因]のために、[イベント]が起き、[結果]につながる可能性がある」という形の一文を使います。台帳を、判断や計画を変えるリスクに限定します。重複を統合し、曖昧なものを分割し、過ぎ去ったリスクを廃止します。人々が議論する数十のリスクの一覧は、誰も読まない千のものより価値があります。

**2. すべてのリスクを、行動できるオーナーに割り当てる。** オーナーは、対応に権限を持つ人で、通常、リスク機能ではなく、デリバリーまたは運用のチームにいます。オーナーシップをその人と確認し、人々の役割が変わるときにレビューします。オーナーの網羅率がこれを測り、オーナーのいないリスクは所見です。

**3. すでに行われている対話の中でリスクをレビューする。** 別の会議を作る代わりに、計画、レビュー、インシデントのレビューで上位のリスクを挙げます。より効果的になる方法についての定期的な振り返りというアジャイルの習慣は、「次に何が私たちを傷つけうるか？」という問いの自然な居場所です。結果を台帳に記録します。

**4. 評価を証拠と範囲と組にする。** 各重要なリスクについて、それが起こりそう、あるいは深刻だと考える根拠を記録します。インシデント、ニアミス、テスト結果、供給者の履歴。可能なところでは可能性と影響の範囲を示し、どれだけ不確かかを述べます。順序尺度のスコアを単一の数字に組み合わせて、測定値として扱ってはいけません。マトリクスを使うなら、議論を始めるために使います（トピック 1.6「サービスメトリクスのための統計リテラシー」を参照）。

### 統制をテストする

**5. 主要な統制と、それぞれが何のためかを名指す。** 各主要なリスクについて、頼る少数の統制と、それぞれの失敗がどう見えるかを列挙します。何百もの小さな活動を列挙する統制台帳は、重要なものを隠します。テスト、ポリシーの確認、承認のゲートなど、パイプライン内の自動化された統制を含めます。

**6. 設計だけでなく、運用をテストする。** 設計のレビューは、統制が運用されたら機能するかを問います。運用のテストは、証拠の抽出を調べることで、期間中にそれが運用され、機能したかを問います。リスクに合う周期でテストを計画し、結果を記録し、失敗をフォローアップします。可能なところでは証拠を自動化し、テストが継続的に行われるようにします。

**7. 統制の失敗を情報として扱う。** 失敗したテストは、統制システムが機能していることです。失敗を記録し、理由を問い、原因を直します。統制の有効性の率は、フォローアップとともに読まれるべきです。素早く見つかって直される失敗は、弱いテストから来る完璧な率より健全です。

**8. 価値を加えるところでは、独立した保証を使う。** 内部監査または独立したレビュー担当者は、第一線が所有し、第二線が監督する統制をテストできます。独立性は、自分の仕事に自分で採点することを防ぎます。チームが同じことで三つのグループにテストされないよう調整します。

### 指標と判断をうまく使う

**9. 主要なリスクごとに少数の先行指標を選ぶ。** 主要リスク指標は、測るのが安く、原因に結び付き、閾値と対応と組になっているべきです。たとえば、最も古い重要な脆弱性の年齢はセキュリティリスクを、緊急の扱いを要する変更の割合は変更リスクを示します。誰が指標を見て、閾値で何をするかを定義します（トピック 8.1「セキュリティインシデントと脆弱性のメトリクス」を参照）。

**10. 各違反で判断を記録する。** 指標が閾値を越えたとき、誰かが決めます。行動する、受容する、閾値を調整する。判断と理由を書き下します。これは、閾値が適切に設定されているか、対応が適時かを示す履歴を築きます。

**11. リスクベースの承認を変更の既定にする。** 継続的デリバリーの環境では、一律の承認委員会を、リスクベースの経路に置き換えます。低リスクの標準変更には自動確認とピアレビュー、少数の高リスクの変更にはより完全なレビュー（トピック 4.3「変更実現のメトリクス」を参照）。統制が動いた証拠を添えます。自動化された証拠を伴う小さな変更は、署名を伴う大きなものより安全なので、これはリスクと遅れを同時に減らします。

**12. 損失とニアミスから学ぶ。** インシデントとあと一歩だった事例の後、台帳を更新します。リスクはあったか、うまく評価されていたか、統制は機能したか。答えを使って両方を改善します。イベントと台帳の間のループが、台帳を誠実に保ちます（トピック 4.2「ポストモーテムと学習のメトリクス」を参照）。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| リスクレビューの最新性 | 議論なしにリスクをレビュー済みと印を付ける、間隔を変える | 実質についてレビューを抽出する。台帳にある固定の間隔 |
| オーナーの網羅率 | 本人の知らないうちにオーナーを割り当てる、権限のない上級者の名前を挙げる | オーナーの確認。オーナーが対応に行動できることを確認する |
| 統制のテストの網羅率 | 簡単な統制をテストする、設計のレビューを運用のテストとして数える | 第二者が固定する主要な統制の一覧。記録されるテストの種類 |
| 統制の有効性の率 | 小さな標本をテストする、通る標本を選ぶ | オーナーから独立した標本の方法。記録される標本サイズ |
| KRI違反への対応時間 | 違反の後に閾値を変える、中身のない判断を記録する | 閾値の変更ログ。判断の内容の抽出 |
| 対処計画の適時性 | 簡単な日付を設定する、完了を再定義する | 承認時にオーナーと合意した日付。リスクの評価が動いたかを確認する |
| リスクベースの変更の割合 | レビューを避けるために変更を低リスクと分類する、統制によって生み出されていない証拠を添える | 規則に照らして分類を抽出する。パイプラインからの自動化された証拠 |

健全な読みは、人々が議論する短い台帳、自分のリスクを知っているオーナー、一部の失敗が見つかって直されている、テストされた統制、本当の判断を導く指標、そして小さな変更への重い承認の減少です。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| リスクマトリクス | 素早く、視覚的で、対話のきっかけ | 主観的。偽の精度。順序尺度の算術 |
| 定量化された範囲 | 不確実性についてより誠実 | データと技能が要る。労力 |
| 重い承認委員会 | 見える統制 | 遅い。変更のまとめを促す |
| リスクベースの自動確認 | 速く一貫している | エンジニアリングが要る。自動確認は間違いうる |
| 中央のリスク機能がリスクを所有する | 一貫性 | 仕事から遠い。オーナーが関与しない |
| 第一線のオーナーシップ | 知識と説明責任 | 質にばらつき。監督が要る |
| 定期的な統制のテスト | 安定した統制には効率的 | テストの間の漂流を見逃す |
| 継続的な統制の監視 | 適時の証拠 | ツールの労力。ノイズ |

散文での答えは、オーナーシップをチームに置き、軽い中央の監督と独立したテストを適用し、可能なところでは証拠を自動化し、評価を対話への促しとして使うことです。

## チームで話し合う問い

**1. 来年このサービスを傷つける可能性が最も高い三つのリスクは何で、それぞれ誰が所有するか？**
各メンバーに、三つのリスクを個別に書いてもらい、それから比較します。重なりと違いの両方が示唆に富みます。ファシリテーターは、各リスクに誰が行動するかを記録してください。上位三つに合意し、オーナーを確認します。

**2. 最も頼っている統制は何で、それが機能することを最後に確認したのはいつか？**
コードレビューの規則、バックアップ、承認のステップなどの統制を一つ選びます。その運用の証拠が最後に調べられたのはいつかをたどります。誰も知らなければ、テストを計画します。対話は、設計と運用の違いを示します。

**3. 評価を黄色から赤に変えさせるものは何で、誰が気づくか？**
指標と閾値を話し合います。チームが注意を避けるために評価を下げたことがあるか、どんな圧力がそうさせたかを尋ねます。変更を正当化する証拠と、赤と言うことを安全にする方法に合意します。

**4. リスクを減らさずに変更を遅くする承認はどれか？**
典型的な変更が必要とする承認を列挙し、それぞれについて、どのリスクに対処し、変更を止めたことがあるかを尋ねます。一つを自動確認に置き換えることを提案します。変更が安全であることを示す証拠に合意します。

**5. 統制が失敗したとき、どうやって分かり、何をしたか？**
最近の失敗を思い出します。テスト、インシデント、監査人のどれで見つかったか。より強いループがどんなものかを話し合います。見つけた人がどう扱われたかを含めます。

**6. 私たちが受容したリスクは何で、その判断をいつ見直すか？**
受容されたリスクとレビュー日を列挙します。それぞれにオーナーと理由があることを確認します。レビュー日のない受容されたリスクは、誰も見ていないリスクです。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、運用リスクの大半を所有します。自分たち自身のリスクの短い一覧を維持し、計画とレビューで議論し、証拠が自動になるよう統制をパイプラインに組み込むべきです。低リスクの変更が流れるようにするリスクベースの変更経路から恩恵を受け、何がうまくいかない可能性があるかについて誠実であるべきです。

### サービスと運用のチーム

運用チームは、バックアップ、監視、アクセスのレビュー、復旧のテストなどの統制を運営します。運用の証拠を保ち、統制を定期的な周期でテストし、指標の違反を早く挙げるべきです。重い統制のコストを負い、どれがほとんど何も加えないかを述べるべきです。

### リーダーシップとガバナンス

リーダーは、リスク許容度を設定し、どれだけの摩擦が許容できるかを決めます。オーナーと証拠を伴う、上位のリスクの短い一覧を求め、赤い評価を歓迎し、統制のテストに資金を付け、独立した保証を支えるべきです。ガバナンスは、台帳がインシデントとニアミスを反映していることを確認し、整って見えるレポートを報いるべきではありません。

### 顧客とユーザー

ユーザーは、顕在化したリスクの結果を負い、台帳より前にそれを知っていることがよくあります。懸念にフラグを付ける方法を持ち、機密性の範囲内で、自分たちに影響するリスクについて伝えられるべきです。インシデントと変更についての彼らの体験は、リスクのレビューの証拠です。

## 実践：サービスマネジメントの例

国のエネルギー事業者のデジタルグループが、顧客の請求、モバイルアプリ、送配電の運用との連携を運営しています。以下の数字は例示です。

グループのリスク台帳には340件の項目があり、最後に整理されたのは3年前です。リスクレビューの最新性は22パーセントで、61件のリスクは去ったオーナーを抱えています。マトリクスは85件のリスクを赤で示し、誰もレポートを読んでいません。新しいサービス保証の責任者は、リセットを提案します。デリバリーのチームとともに、台帳を判断を変えるリスクに削減し、38件にします。それぞれを、行動できるチームの名前付きのオーナーに割り当て、彼らが確認します。12の主要な統制を選び、設計のレビューの代わりに、それぞれの運用をテストします。5件が失敗します。二つのバックアップの復旧は一度もテストされておらず、一つのアクセスのレビューは飛ばされ、二つの変更の承認はテストの証拠なしに署名されていました。

チームは失敗を直し、標準変更の変更承認委員会を、リスクベースの経路に置き換えます。自動テストとピアレビューが統制で、パイプラインが変更レコードに証拠を添えます。各主要なリスクには、閾値と対応を伴う一つか二つの先行指標が付きます。請求の長期の停止のリスクでは、指標は最も古い重要な脆弱性の年齢と、四半期の失敗したバックアップの復旧の数です。最初の四半期は、38件すべてのリスクをオーナーが確認し、レビューの最新性91パーセント、最初のテストでの統制の有効性の率12件中7件と、修正後の12件中12件、KRI違反への対応時間の中央値2日を示します。リスクベースの経路を通る変更の割合は64パーセントです。

最高リスク責任者は、1年以内に赤いリスクの数を半分にすることを求めます。サービス保証の責任者は、対処計画の適時性と統制の有効性を追跡することを提案し、赤いリスクの件数は再評価で下がりうること、誠実な赤い評価を見たいことを説明します。判断は記録され、次の四半期のレポートには、各引き下げの背後にある抽出された判断が含まれます。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

年次のレビューではなく、ステークホルダーとの定期的な対話を通じて、リスク台帳を生かし続けます。注意点は、スコアの数字は不確実性を整って見せうることです。

### AI

AIシステムには、オーナー、人によるレビューの時点、レビュー日を伴う、リスク台帳の項目が要ります。AIの監督の統制の有効性を、テストすることで測ります。注意点は、人が出力をレビューすると述べるポリシーは、誰かがテストするまで統制ではないことです。

### 自動化

テストできるところでは統制の確認を自動化し、自動化を失敗したものと飛ばされた確認で測ります。注意点は、通る自動化された統制が、間違ったものをテストしているかもしれないことです。

### アナリティクス

統制のテストの網羅率と有効性を、標本サイズとともに報告します。これが情報を与える判断は、どの統制を強化するかです。注意点は、小さな標本と主観的なスコア付けが精度を制限するので、そう述べることです。

## 業種別の視点

**スタートアップ。** リスクは主に、資金が尽きること、主要な人を失うこと、大きな停止についてです。上位五つの1ページの一覧を保ち、毎月レビューし、バックアップと復旧をテストします。後から改修するより安いので、最初から統制をパイプラインに組み込みます。

**中小企業。** 少数のリスクが支配的です。特定の人への依存、単一の供給者、ランサムウェア、データの喪失。オーナーを伴う短い一覧を保ち、復旧をテストし、保険と連絡先を最新に保ちます。重い枠組みには抵抗し、そこから合うものを借ります。

**大企業。** 規模は、共通の分類、軽量な台帳のツール、実践における三つの防衛線を要します。第一線に自分たちのリスクを所有させ、第二線を小さく助言的に保ち、独立したテストを効率的にします。監査、リスク、コンプライアンスにまたがる重複したテストを避けます。

**政府・公共部門。** リスク管理は、標準の枠組み、監査委員会、公的な報告を伴う正式な義務であることがよくあります。必要な枠組みと整合させ、リスク許容度の声明を文書化し、証拠を保ちます。公的な説明責任は、誠実な赤い評価をより価値あるものにし、同時により難しくします（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは、リスクをレビューするオーナーの時間、主要な統制を定義してテストする労力、まだなければ台帳と指標の監視のツール、独立した保証のコストです。証拠の収集の自動化にはエンジニアリングの労力がかかり、その後は繰り返しのコストを減らします。

見返りは、驚きの減少、より速く軽い変更の承認、より信頼できる保証です。刈り込まれた台帳とリスクベースの変更経路は、大きな承認機関が消費していた時間を節約します。インシデントの前に見つかる失敗した統制のテストは、値付けしにくい損失を防ぎます。自分たち自身のデータからケースを築きます。変更の承認あたりにかかる時間の前後、テストで見つかった統制の失敗と、インシデントや監査人によって見つかったものの数、統制が防げたはずの過去のインシデントのコスト。たどれる出典と方法なしに、業界の損失の統計を引用するのは避けます。

## アンチパターンと落とし穴

- **永遠に増え続ける台帳。** 誰も読まない。重要なリスクに刈り込む。
- **証拠のない評価。** 色のついた意見である。証拠と範囲を添える。
- **名前だけのオーナー。** リスクが行動できない人にある。適切な人とオーナーシップを確認する。
- **設計をテストして保証と呼ぶ。** 機能しうる統制は、機能していないかもしれない。運用をテストする。
- **赤いリスクの件数だけを報告する。** 件数は再評価で下がる。対処と統制の結果を見る。
- **すべての変更への承認委員会。** 小さな変更を遅くし、まとめることを教える。リスクベースの経路を使う。
- **赤い評価を罰する。** そうするとリスクが隠される。早期の警告を報いる。
- **リスクとデリバリーの文化の分離。** チームとともにではなく、チームに対して行われるリスクの仕事は、コンプライアンスの芝居を生む。

## チェックリスト

- [ ] 台帳が短く、リスクが原因、イベント、結果の形で書かれている。
- [ ] すべてのリスクに、行動できる、確認された第一線のオーナーがいる。
- [ ] リスクがチームの定期的な対話の中でレビューされている。
- [ ] 主要な統制が名指しされ、述べた周期で運用がテストされている。
- [ ] 統制の失敗が記録され、説明され、直されている。
- [ ] 各主要なリスクに、閾値と対応を伴う一つか二つの先行指標がある。
- [ ] 指標の違反での判断が記録されている。
- [ ] リスクベースの変更経路があり、可能なところでは自動で証拠が添えられる。
- [ ] 受容されたリスクにオーナー、理由、レビュー日がある。
- [ ] インシデントとニアミスが台帳を更新する。

## AIプロンプト

**リスクを標準の形で書き直す。**

```text
以下は私たちのリスク台帳の [数] 件の項目です：[機微な詳細を除いて貼り付け]。それぞれを「[原因]のために、[イベント]が起き、[結果]につながる可能性がある」という形で書き直してください。曖昧な項目、重複、すでに起きた問題である項目に印を付けてください。どれを統合または廃止できるかを提案してください。評価しないでください。前提と、オーナーと確認すべきことを列挙してください。
```

**統制のテストを設計する。**

```text
統制 [説明。例：請求システムの四半期ごとのアクセスのレビュー] について、運用のテストを設計してください。調べる証拠、偏りなく標本を選ぶ方法、何が合格と不合格か、結果をどう記録するか、時間とともに証拠の収集をどう自動化するかを含めてください。特定のツールを仮定しないでください。前提とテスト設計のリスクを列挙してください。
```

**リスクの先行指標を提案する。**

```text
リスク：[原因、イベント、結果の形で説明]。測るのが安く、原因に結び付いた、最大三つの先行指標を、閾値違反への提案される対応と、それぞれの指標が誤解を招きうる方法とともに提案してください。閾値の値を捏造せず、自分たちのデータからどう較正すべきかを記述してください。前提を列挙してください。
```

**変更承認のプロセスをレビューする。**

```text
[変更の種類] の変更承認のプロセスは次のとおりです：[ステップ、承認者、典型的な遅れを説明]。リスクを減らさずに遅れを加えるステップを特定し、自動確認と証拠を伴うリスクベースの代替を提案し、リスクが上がったか下がったかを知るために何を測るべきかを述べてください。研究結果を主張しないでください。前提と、リーダーシップの入力が要る判断を列挙してください。
```

## 要点

- リスク台帳を短く、行動できるチームが所有し、すでに存在する対話でレビューされるものに保つ。
- 主要な統制が運用されていることをテストし、失敗を有用な情報として扱い、証拠を自動化する。
- 閾値、対応、記録された判断を伴う少数の先行指標を使う。
- 一律の承認を、自動化された証拠に裏付けられたリスクベースの変更経路に置き換える。
- 偽の精度の代わりに範囲と証拠を示し、マトリクスを対話を始めるために使う。
- 赤い評価を出すことを安全にし、損失とニアミスから学ぶ。
