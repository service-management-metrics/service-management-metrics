# セキュリティインシデントと脆弱性のメトリクス

**セキュリティはサービスを継続的に提供し運営することの一部である。したがって、人々がどれだけ長く露出したままか、うまくいかなかったことをどれだけ速く封じ込めるか、同僚が進んで手を挙げるかを測り、間違いを決して非難の理由にしない。**

## 概要と動機

すべてのサービスは弱点を抱えており、そのうちのいくつかはサービスに対して使われます。[脆弱性（vulnerability）](https://en.wikipedia.org/wiki/Vulnerability_(computing))は、ソフトウェア、ハードウェア、構成、プロセスにある、システムの機密性、完全性、可用性を損なうために悪用されうる弱点です。セキュリティインシデントは、その被害が生じる、あるいは確からしく脅かされるイベントです。この領域のメトリクスは、二つの問いに答えようとします。私たちはどれだけ露出しているか、そして問題をどれだけ速く見つけ、直し、回復するか。

アジャイルとDevOpsの伝統は、セキュリティを、継続的デリバリーの終わりにある関門ではなく、その性質として扱います。[DevSecOps](https://en.wikipedia.org/wiki/DevSecOps)は、パイプラインにセキュリティの確認を組み込み、開発、セキュリティ、運用の間で責任を共有することで、DevOpsの考え方を拡張します。ITILは、情報セキュリティ管理のプラクティスを通じて、ポリシー、リスクに基づく考え方、インシデント、変更、資産管理との結び付きをもたらします。二つは日々の仕事で出会います。依存関係の更新は通常の変更として到来し、脆弱性の所見はオーナー付きのバックログアイテムになり、インシデントは他のものと同じ非難なきレビューで扱われます（トピック 4.2「ポストモーテムと学習のメトリクス」を参照）。

セキュリティのメトリクスは、特有の歪みにさらされています。

- **所見を数えることは、見ないことを報いる。** スキャンの少ないチームは、見つけるものも少ない。脆弱性の生の件数は、何かが改善したからではなく、スキャナーがアクセスを失ったから下がりうる。
- **深刻度スコアは入力であり、真実ではない。** [共通脆弱性評価システム（CVSS：Common Vulnerability Scoring System）](https://en.wikipedia.org/wiki/Common_Vulnerability_Scoring_System)は、抽象的な脆弱性の深刻度スコアを与え、[共通脆弱性識別子（CVE：Common Vulnerabilities and Exposures）](https://en.wikipedia.org/wiki/Common_Vulnerabilities_and_Exposures)のような登録簿が識別子を与える。脆弱性が自分にとって重要かは、自分の環境で到達可能か、エクスプロイトが使われているか、影響を受ける資産がどれだけ価値あるかに依存する。単独で使われる生の深刻度スコアは、労力を間違った場所に送る。
- **非難は報告を抑える。** リンクをクリックしたことや、自分が引き起こしたインシデントを報告したことで罰されると、報告が止まり、露出は見えないところで増える。心理的安全性はセキュリティの統制である。
- **時間の測定値は裾を隠す。** パッチ適用までの時間の中央値は健全に見えながら、少数の重要なシステムが何か月も露出したままかもしれない。

このトピックは、定義、悪用の手口、防護柵を伴う主な測定値を与えます。前の部の資産と構成の記録の上に築かれています。見つけられないものにパッチを当てたりスキャンしたりすることはできないからです（トピック 7.1「IT資産管理のメトリクス」とトピック 7.4「構成とCMDB品質のメトリクス」を参照）。注意点です。これは測定のガイドであり、セキュリティのマニュアルではありません。資格のあるセキュリティの専門家とともに統制を選び、ISO/IEC 27001や国の機関のガイダンスなど、自分に適用される規格と法的義務に従ってください。

[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、セキュリティには鋭く当てはまります。測定値が目標になると、人々は所見を再分類し、資産をスキャンから除外し、原因を直さずにチケットをクローズします（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

## 主要な原則

- **件数に加えて、露出の時間を測る。** 弱点がどれだけ長く開いたままかは、いくつ見つかるかより重要である。
- **文脈で優先順位を付ける。** 深刻度、悪用可能性、到達可能性、資産の価値を組み合わせる。
- **最初に網羅率を確認する。** 環境の半分を見逃したスキャンからのきれいなレポートは、偽の安心である。
- **セキュリティをパイプラインに組み込む。** 安全な選択を簡単な既定にし、速いフィードバックを与える。
- **分野を越えて協働する。** セキュリティ、開発、運用が一緒に成果を所有する。
- **報告を安全にする。** 間違いの非難なき扱いが、シグナルを流れ続けさせる。
- **人間の行動のデータを集約する。** グループのパターンを報告し、個人の名前を挙げたり順位を付けたりしない。

優先度の帯とポリシーの窓を台帳に述べます。露出の窓は、脆弱性がその資産に適用されると分かったとき、つまり公開と、その資産が影響を受けるコンポーネントを動かしていると分かった時刻のうち遅いほうで始まり、検証された修復、または文書化された期限付きの緩和で止まります。封じ込めまでの時間は、誰も読まなかった最初のアラートではなく、検出で始まります。テストの所見と誤検知は、レビューの後にのみ除外します。セキュリティ報告率はグループと傾向を記述し、個人は決して記述しません。

## 推奨事項

### 環境と露出を知る

**1. 資産と依存関係の記録から始める。** スキャン、パッチ適用、オーナーシップのすべては、何が存在するかを知ることに依存します。すべての所見を資産、オーナー、サービスに結び付け、スキャンの網羅率を台帳に対して測ります。網羅率が低いところでは、所見を読む前にそれを直します。スキャンされていない資産は未知で、既知の弱点より悪い。

**2. 最初に[攻撃対象領域（attack surface）](https://en.wikipedia.org/wiki/Attack_surface)を減らす。** 必要ないものを取り除きます。使われていないサービス、開いたポート、古いアカウント、忘れられた環境。廃止するものはすべて、パッチを当てる必要のないものです。インターネットに面したサービスと休眠アカウントの数を単純な指標として追跡し、オーナーとレビューします。

**3. ソフトウェアのサプライチェーンを含める。** 現代のサービスは多くのコンポーネントに依存します。[ソフトウェアサプライチェーン（software supply chain）](https://en.wikipedia.org/wiki/Software_supply_chain)には、ライブラリ、ビルドツール、コンテナイメージ、その背後の供給者が含まれます。前に述べたソフトウェア部品表を使って、脆弱なコンポーネントがどこで使われているかを見つけ（トピック 7.2「ソフトウェア資産とライセンスのメトリクス」を参照）、依存関係の所見をインフラの所見と同じ測定値に含めます。

### 優先順位を付けて直す

**4. 深刻度スコアだけでなく、文脈で順位付ける。** CVSSの深刻度を、エクスプロイトが使われていると知られているか、脆弱なコンポーネントが到達可能か、資産の重要度と組み合わせます。悪用が知られている脆弱性の公開リストは、最初の要因に役立ちます。順位付けの規則を書き、レビューし、深刻度の高いアイテムの優先度を下げたときは理由を記録します。

**5. 帯ごとにポリシーの窓を設定し、それに照らして報告する。** 各優先度の帯について、修復または緩和の目標時間に合意します。窓内の割合、露出の中央値と85パーセンタイル、最も古い未解決のアイテムを報告します。窓は対話のための目標であり、最も古いアイテムは、プロセスがどこで失敗するかを示すので注意に値します（トピック 1.6「サービスメトリクスのための統計リテラシー」を参照）。

**6. パッチ適用を、通常の頻繁な変更として扱う。** 最も安全なパッチのプロセスは、頻繁に動き、退屈なものです。小さく頻繁な更新は、大きくまれなものより、テストと元に戻すのが容易で、自動化されたパイプラインはそれらを継続的に適用できます。リスクに基づく承認には変更実現のアプローチを使い、緊急の修正のための緊急経路を保ちます（トピック 4.3「変更実現のメトリクス」を参照）。

**7. 例外を見えるものにし、短命にする。** 時に修正は不可能です。理由、補完統制、オーナー、レビュー日とともに例外を記録し、例外の年齢を報告します。レビュー日のない例外は恒久的になり、恒久的な例外が本当のリスク台帳になります。

### 対応して学ぶ

**8. インシデント対応を訓練する。** [コンピュータセキュリティのインシデント管理（computer security incident management）](https://en.wikipedia.org/wiki/Computer_security_incident_management)は、準備、検出、封じ込め、根絶、復旧、教訓をカバーします。演習でリハーサルし、検出からの封じ込めまでの時間を記録し、重要なインシデントを非難なくレビューします。セキュリティインシデントの扱いの構造は、重大インシデントの扱いに似ています（トピック 3.4「重大インシデントのメトリクス」を参照）。

**9. 検出だけでなく、封じ込めを測る。** 検出ツールはアラートを生み、価値はその次に起きることにあります。確認されたインシデントの封じ込めと復旧にかかる時間と、自分たちの監視で見つかった割合と外部から報告された割合を追跡します。社内で検出されたインシデントの割合の上昇は、可視性が改善しているしるしです。

**10. ニアミスから学ぶ。** 報告されてブロックされたフィッシングのメールや、攻撃者より前に同僚が見つけた脆弱性は、無料の教訓です。インシデントと同じようにこれらを記録してレビューし、報告した人に感謝します。セキュリティ報告率はその文化の健全さの指標で、信頼とともに上がるはずです。

### 文化とパイプラインを築く

**11. 確認を開発者が働く場所に置く。** ビルドで依存関係と静的解析を実行し、プルリクエストでフィードバックを与え、チームが阻害要因と合意した問題でのみビルドを失敗させます。速く関連するフィードバックは直されます。価値の低い所見の洪水は無視されます。パイプラインの所見の修正時間を追跡し、チームとともに規則を調整します（トピック 2.7「プルリクエストとコードレビューのメトリクス」を参照）。

**12. 恥をかかせずに、訓練しテストする。** 模擬フィッシングのような意識向上の演習は技能を築けますが、結果が個人の名前を挙げたり懲戒したりするために使われると、信頼を損ないもします。集約された結果のみを報告し、不審なメッセージを報告する人の数に焦点を当て、目的を説明します。演習がスタッフに騙されたと感じさせるなら、変更します。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 露出の窓 | 検証なしに所見をクローズする、開始日を変える、深刻度を再分類する | 修正するチームの外の誰かによる検証のステップ。台帳にある開始日の規則。深刻度の変更ログ |
| パッチの順守 | パッチを当てにくい資産を範囲から除外する、システムが再起動されていないのにパッチが適用されたと数える | 記録される範囲の変更。チケットではなく、資産からインストールされたバージョンを検証する |
| 期限超過の重要な所見 | 所見を分割または統合する、深刻度を下げる | 一意の脆弱性と資産ごとに数える。すべての深刻度の変更をレビューする |
| スキャンの網羅率 | より狭い集合をスキャンする、認証に失敗したスキャンを数える | 資産台帳に照らした網羅率。スキャンの質（認証済み、完全） |
| 封じ込めまでの時間 | 時計を遅く始める、早期に封じ込めを宣言する | 時計は最初の検出のシグナルで始まる。証拠をもって封じ込めを検証する |
| リスク例外の年齢 | 例外を自動で更新する、年齢を減らすために例外を分割する | 理由を伴う例外の更新をレビューする。新しい証拠なしの更新に上限を設ける |
| セキュリティ報告率 | 価値の低い報告を促す、他の数字を改善するために報告を妨げる | 報告の質。コメントを読む。報告に安全を感じるかのアンケート |

健全な読みは、高いスキャンの網羅率、短く縮む露出の裾、レビュー日を伴う誠実な例外、素早く封じ込められ社内でより多く見つかるインシデント、そして恐れなく不審なイベントを伝えてくれるスタッフです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| 深刻度スコアのみによる優先順位付け | 単純で一貫している | 文脈を無視する。労力を間違った場所に送る |
| 文脈に基づく優先順位付け | 本当のリスクに焦点を当てる | データと判断が要る |
| 固定のパッチの窓 | 明確な期待 | 危険な慌てた変更を強いうる |
| リスクに基づく窓 | 状況に合う | 監査しにくい |
| 頻繁な自動パッチ適用 | 小さな変更、より少ない露出 | 良いテストとロールバックが要る |
| まれな大きなパッチ周期 | なじみがある | より長い露出、変更あたりのより大きなリスク |
| フィッシングの模擬 | 意識を築く | 誤用すると信頼を損ないうる |
| 報告文化への焦点 | 問題を早く浮かび上がらせる | 直接測りにくい |

散文での答えは、文脈で順位付け、良いロールバックを伴う小さなステップで頻繁にパッチを当て、期限付きで例外を記録し、報告文化を統制として投資することです。

## チームで話し合う問い

**1. 私たちのスキャンは、環境のどれだけを実際に見ているか？**
スキャンされた資産を資産台帳と比較します。何が欠けていて、なぜかを尋ねます。ファシリテーターは、コンテナ、リモートデバイス、サードパーティのシステムなど、体系的にスキャンされていないカテゴリを探してください。今四半期に埋めるギャップを一つ合意します。

**2. 最も古い未解決の重要な所見は何で、なぜまだ開いているか？**
平均ではなく、裾を見ます。最も古い数件をたどります。誰が所有し、何がブロックし、補完統制は何か。ファシリテーターは、例外が記録されているかを尋ねてください。最も古いものを誰がブロック解除するかを合意します。

**3. セキュリティの修正が最後に障害を引き起こしたのはいつで、その後何が変わったか？**
例を思い出します。原因は慌てた修正か、欠けたテストか。パッチ適用を日常的で安全にする方法を話し合います。答えを変更とリリースの実践に結び付けます。

**4. 同僚が今日不審なメールを報告したら、その人はどうなるか？**
報告から対応までの実際の経路を、報告者がどう感謝されるかを含めて記述します。報告したこと、またはクリックしたことで恥をかかされた人がいるかを尋ねます。対話は信頼についてです。報告をより簡単で安全にする小さな変更を合意します。

**5. 私たちのセキュリティの数字のうち、より安全でなくなりながら上がりうるものはどれか？**
測定値を列挙し、それぞれが範囲を狭めたり再ラベルしたりすることで改善されうる方法を考えます。それぞれに防護柵を割り当てます。この演習は、次のレビューのための台帳の項目を築きます。

**6. 確認されたインシデントをどれだけ速く封じ込められ、どうやってそれを知るか？**
直近二件のインシデントをレビューし、検出から封じ込めまでをたどります。遅れに注意します。どんな演習を実行したかを尋ねます。次のレビューの前に一つ実行することに合意します。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、修正の大半を行い、弱点の多くを持ち込みます。通常の流れの一部として依存関係を最新に保ち、セキュリティの所見をオーナーと日付を持つバックログアイテムとして扱い、速く関連するフィードバックを与えるパイプラインの確認を使うべきです。明確な優先順位と行動する時間が必要で、懸念を自由に挙げられるべきです。

### サービスと運用のチーム

運用チームは、スキャナーを運営し、パッチを適用し、インシデントに対応します。資産のリンクを最新に保ち、網羅率を誠実に報告し、期限付きで例外を扱うべきです。また、インシデント対応のリハーサルのための守られた時間と、間違いが起きたときの非難なき文化が必要です。

### リーダーシップとガバナンス

リーダーは、リスク許容度を設定し、セキュリティを継続的な活動として資金付けするか、プロジェクトとして資金付けするかを決めます。合計ではなく、露出の窓と最も古い未解決のアイテムを求め、報告文化を守り、可視性が改善すると数字が上がることを受け入れるべきです。ガバナンスは、例外とインシデントの学びの証拠を要求するべきです。

### 顧客とユーザー

ユーザーは受益者であり、防御の一線でもあります。自分たちのデータを守るサービスと、明確で公正なガイダンスを望みます。インシデントが彼らに影響するときは速やかに伝えられ、問題を報告したときは敬意を持って扱われ、仕事を必要以上に難しくしないセキュリティ対策を与えられるべきです（トピック 6.4「ユーザー体験と従業員体験」を参照）。

## 実践：サービスマネジメントの例

地域の信用組合が、小さなエンジニアリングチームと外部委託のセキュリティ運用サービスで、オンラインバンキング、モバイルアプリ、支店システムを運営しています。以下の数字は例示です。

取締役会が、セキュリティのダッシュボードを求めます。セキュリティアナリストの最初の草稿は、4,200件の未解決の脆弱性が減少していること、パッチの順守が96パーセントであることを示します。エンジニアリングの責任者は、スキャンの網羅率について尋ねます。スキャナーの出力を資産台帳に結合すると、アナリストは、移行の後にスキャナーが認証情報を失ったため、サーバーの31パーセントとほぼすべてのコンテナが直近30日にスキャンされていないことを見つけます。スキャンされた資産のうち、重要な脆弱性の露出の窓の中央値は9日で、85パーセンタイルは41日です。最も古い重要な所見は212日前のもので、4か月前に期限切れになった例外を伴うレガシーなシステムにあります。96パーセントのパッチの順守は、パッチツールが報告した資産のみについて計算されていました。

チームは、エンジニアリングと運用とともに四つの変更を行います。スキャンの網羅率がダッシュボードの最初の行になり、台帳の完全な網羅率に達する目標が設定され、スキャンの認証が修復され、監視されます。優先順位付けは、深刻度スコアに悪用の状況と資産の重要度を加え、4,200件の所見は、今重要な約60件の短い一覧に減ります。依存関係の更新は、自動テストを伴う頻繁な小さな変更として、パイプラインに移ります。例外にはオーナー、補完統制、レビュー日が付き、期限切れのものはリスク委員会がレビューします。セキュリティアナリストはまた、模擬フィッシングの結果の報告の仕方を変えます。グループレベルの報告率のみが示され、アナリストは報告してくれた同僚に個人的に感謝します。

二か月後、スキャンの網羅率は97パーセント、重要なアイテムの露出の窓の85パーセンタイルは14日で、最も古い重要な所見は、レビューまで60日の緩和された例外です。不審な支払い依頼のメールを支店の従業員が数分以内に報告し、インシデントは2時間未満で封じ込められます。取締役会は、年末までに未解決の脆弱性の件数を半分にすることを求めます。エンジニアリングの責任者は、件数はスキャンを減らすことで下がりうると説明して、代わりに露出の窓と期限超過の重要な所見を報告することを提案します。判断は記録され、取締役会は次の会議で新しい測定値をレビューすることに合意します。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

セキュリティを継続的デリバリーの一部として扱い、修正を他の変更と同じパイプラインとレビューを通じて流します。注意点は、脆弱性の件数の目標が、再分類を促すことです。

### AI

AIはプロンプトインジェクションやデータ漏えいなどの新しいリスクを加え、AIツールは所見のトリアージを助けられます。AIシステムが関わるインシデントと、AIがトリアージした所見のうち人が確認した割合を追跡します。注意点は、本当の所見を却下するAIは、偽の保証を与えることです。

### 自動化

安全なところではスキャンとパッチ適用を自動化し、スキャンの網羅率と失敗したパッチを測ります。注意点は、自動のパッチ適用はサービスを壊しうるため、段階的なロールアウトとロールバックを使うことです。

### アナリティクス

露出の窓を、深刻度別の分布として件数とともに報告します。これが情報を与える判断は、どこで最初に露出を削るかです。注意点は、脆弱性のスコアは成果ではなく入力なので、悪用可能性と資産の重要度と組み合わせることです。

## 業種別の視点

**スタートアップ。** 通常、専任のセキュリティチームはないので、基本をパイプラインに組み込みます。依存関係の更新、シークレットのスキャン、多要素認証、最小権限。短い重要なシステムの一覧の露出の窓を追跡し、単純なインシデント計画を持ちます。環境を知る前に大きなツールセットを購入するのは避けます。

**中小企業。** 外部委託のサービスとクラウドのツールがリスクの大半を担います。棚卸しを保ち、あらゆる場所で多要素認証を有効にし、システムを自動で最新に保ち、インシデントで誰に連絡するかを知っておきます。パッチの順守とバックアップの復旧時間を測ります。間違いを報告するスタッフに恥をかかせるのは避けます。

**大企業。** 規模は、多くのチームとツールにわたる一貫したデータを要します。優先度の帯と窓を中央で定義し、チームに自分たちの所見を所有させ、ビジネスサービス別に露出を報告し、定期的な演習を実行します。供給者のセキュリティチームと調整し、引き継ぎをテストします。

**政府・公共部門。** 分野によっては、特定の脆弱性について期限付きの義務的な指令、正式なインシデント報告の義務、監査の要件に直面します。それらを設計への入力として扱います。指令の期限の遵守を追跡し、証拠を保ち、個人のプライバシーを守りながら、求められるインシデントを報告します（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは、すでに所有しているかもしれないスキャンと監視のツール、資産のリンクを維持する時間、所見を直し依存関係を更新するエンジニアリングの時間、インシデント対応の準備と演習、そして研修です。パイプラインの確認には、セットアップの時間と一定のビルド時間がかかります。外部委託の監視にはサービス料があります。

見返りは、インシデントの可能性と影響の低下、より短い露出、慌てた緊急変更の減少です。これらの便益は現実のもので、起きなかったインシデントは記録を残さないので、定量化が困難です。出典とその関連性をたどれない限り、業界の平均的な侵害のコストやインシデントの頻度の引用は避けます。自分たち自身のデータからケースを築きます。露出の窓の傾向、遅いパッチ適用が原因の緊急変更の数、自動化が取り除いた手作業のパッチ作業に費やした時間、スタッフの時間と顧客への影響を含む過去のインシデントのコスト。ビジネスケースの前のトピックが示すように、リスクの低減を特定のシナリオの観点で記述します（トピック 7.7「投資対効果とビジネスケース」を参照）。

## アンチパターンと落とし穴

- **脆弱性の件数を報告する。** スキャンが見逃すと件数は下がる。露出の窓、期限超過のアイテム、網羅率を報告する。
- **深刻度スコアだけで優先順位を付ける。** 到達可能性と悪用を無視する。文脈を加える。
- **スキャンを真実として扱う。** 網羅率とスキャンの質を資産台帳に照らして確認する。
- **恒久的な例外。** 隠れたリスクになる。すべての例外にオーナーとレビュー日を与える。
- **間違いで人に恥をかかせる。** 報告が止まる。非難なきレビューと集約された結果を使う。
- **終わりの関門としてのセキュリティ。** デリバリーを遅くし、回避策を招く。パイプラインに確認を組み込む。
- **ビッグバンのパッチ周期。** 危険で遅い。小さな変更で頻繁にパッチを当てる。
- **供給者を無視する。** 彼らの弱点は自分たちのものである。供給者のセキュリティ義務とインシデントを追跡する。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| 可視性 | 一部のシステムの時折のスキャン | 主なシステムの定期的なスキャン | スキャンの網羅率が資産台帳に照らして追跡される。所見がオーナーに結び付く | 網羅率、露出の窓、例外が管理され、傾向として追われる | 依存関係を含む、チームと供給者にまたがる共有の見方 |
| 優先順位付けと修正 | 最も声の大きい依頼で直す | 深刻度ベースの一覧 | 文脈ベースの順位付け。帯別のポリシーの窓。頻繁な小さなパッチ | 窓と裾がレビューされる。パイプラインの確認がチームとともに調整される | 人による監督を伴う、自動化されたリスクベースの修復 |
| 対応と文化 | アドホックな対応。非難 | 基本的な計画。まれにしかテストされない | リハーサルされた計画。非難なきレビュー。報告が評価される | 封じ込めの時間と社内検出の率が管理される。報告文化が測定される | 供給者や顧客との共同の演習。学びが広く共有される |

## チェックリスト

- [ ] スキャンの網羅率が資産台帳に対して測定されている。
- [ ] 所見が資産、オーナー、サービスに結び付いている。
- [ ] 優先度の帯が、深刻度、悪用、到達可能性、資産の重要度を組み合わせている。
- [ ] 帯別のポリシーの窓が合意され、露出の窓と最も古い未解決のアイテムが報告されている。
- [ ] 依存関係とパイプラインの確認が、合意した阻害要因とともに、ビルドごとに実行される。
- [ ] パッチ適用が、緊急経路を伴う、頻繁で小さくテストされた変更として行われる。
- [ ] 例外にオーナー、補完統制、レビュー日がある。
- [ ] インシデント対応がリハーサルされ、封じ込めまでの時間が検出から測定されている。
- [ ] 人間の行動のデータが集約してのみ報告され、報告が感謝されている。
- [ ] 供給者のセキュリティ義務とインシデントが追跡されている。

## AIプロンプト

**脆弱性の優先順位付けの規則をレビューする。**

```text
脆弱性の優先順位付けの現在の規則は次のとおりです：[説明]。データの項目には次があります：[一覧。例：深刻度スコア、エクスプロイトの状況、資産の重要度、インターネットへの露出]。規則を盲点と悪用されうる方法についてレビューし、明確な帯とポリシーの窓を持つ文脈ベースの順位付けを提案してください。特定の数字を業界標準として述べないでください。前提と、セキュリティの専門家が確認すべきことを列挙してください。
```

**スキャンの網羅率を確認する。**

```text
以下は、クラス別の資産台帳と、直近の [間隔] にスキャナーが見た資産の要約です：[件数または無害化した一覧を貼り付け]。網羅率の低いクラス、ギャップのありそうな理由、それぞれの理由を確認する最も素早い確認を特定してください。失敗した、あるいは部分的なスキャンが成功に見えないよう、網羅率をどう報告するかを提案してください。前提を列挙してください。
```

**机上演習を計画する。**

```text
[組織の種類] のための、このシナリオについての90分の机上演習を設計してください：[説明。例：侵害された供給者の認証情報]。役割、インジェクトのタイムライン、促す判断、記録するもの（検出と封じ込めまでの時間を含む）、非難なきふりかえりの問いを含めてください。実際の名前やシステムを含めないでください。前提と、私たちの文脈に合わせて調整すべきことを列挙してください。
```

**報告された間違いへの非難のないメッセージを書く。**

```text
同僚が [説明。例：フィッシングメールのリンクをクリックした] と報告しました。同僚に感謝し、私たちが何をするかを説明し、必要な詳細を尋ねる、セキュリティチームからの短く親切な返信を起案してください。それから、誰の名前も挙げずに教訓を共有する、週次の更新のための集約したメモを起案してください。前提と、私がレビューすべきトーンの選択を列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：セキュリティまたは脆弱性のメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：セキュリティのメトリクスの項目が、悪用の手口、防護柵、プライバシーの規則を備えているかを確認するときに使います。

## 要点

- 所見の生の件数ではなく、露出の時間、最も古い未解決のアイテム、スキャンの網羅率を測る。
- 文脈で優先順位を付ける。深刻度、悪用、到達可能性、資産の重要度。
- 小さくテストされた変更で頻繁にパッチを当て、すべての例外にオーナーとレビュー日を与える。
- インシデントを素早く封じ込め、非難なく学び、社内検出を追跡する。
- 報告文化を統制として扱う。報告した人に感謝し、個人に順位を付けない。
- セキュリティの確認をパイプラインに組み込み、安全な選択が簡単な選択になるようにする。
