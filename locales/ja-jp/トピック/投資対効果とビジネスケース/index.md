# 投資対効果とビジネスケース

**ビジネスケースは予測である。したがって、範囲と述べた前提で書き、証拠が届くにつれて段階的に仕事に資金を付け、予測を実際に起きたことと照らして確認して、次のケースが前のものより誠実になるようにする。**

## 概要と動機

ITサービスの提供と運営の方法を改善するには、お金と注意が要り、すべての提案が他の提案と競合します。新しい基盤、人員の変更、自動化のプログラム、品質の取り組みは、いずれもより良い将来を約束します。リーダーはそれらを比較する方法を必要とし、チームは重要な仕事のために主張する方法を必要とします。ビジネスケースは伝統的な道具で、投資対効果はその最もよく知られた数字です。

[ビジネスケース（business case）](https://en.wikipedia.org/wiki/Business_case)は、提案されたプロジェクトや事業の正当化で、通常、問題、選択肢、コスト、便益、リスクを述べます。[投資対効果（ROI：return on investment）](https://en.wikipedia.org/wiki/Return_on_investment)は、投資からの利得をそのコストと比較します。[総所有コスト（TCO：total cost of ownership）](https://en.wikipedia.org/wiki/Total_cost_of_ownership)は、購入、運用、サポート、処分を含め、資産やサービスが寿命にわたって要するすべてを数えます。この部の前のトピックが入力を供給します。資産、ソフトウェア、構成の記録、サービス、クラウド資源のコスト（トピック 7.5「サービスコストとユニットエコノミクス」とトピック 7.6「FinOpsとクラウドコストのメトリクス」を参照）で、便益のトピックが成果の証拠を与えます（トピック 6.5「価値の実現とビジネス成果」を参照）。

二つの緊張が、ビジネスケースをうまく行うのを難しくします。

- **ビジネスケースは、承認を望む人々が書く予測である。** 著者はしばしば提案が成功することを望み、便益を水増しし、コストを削るインセンティブは強い。[楽観バイアス（optimism bias）](https://en.wikipedia.org/wiki/Optimism_bias)は、起こりそうなものより良い結果を期待する傾向で、プロジェクトの計画でよく文書化されている。是正策は[参照クラス予測（reference class forecasting）](https://en.wikipedia.org/wiki/Reference_class_forecasting)で、積み上げの物語ではなく、類似した過去のプロジェクトの実際の成果に基づいて見積もる。自分たち自身の過去のケースの履歴が、持っている最良の参照クラスである。
- **継続的デリバリーは、ビジネスケースが約束できることを変える。** アジャイルのアプローチは、要件と価値が仕事が進むにつれて発見されると想定する。1年前に固定された範囲、価格、便益は、それと衝突する。アジャイルの対応は、段階的な資金付けである。学ぶための小さな最初のステップ、それから証拠が届くにつれてさらなる資金。これは継続的デリバリーとステークホルダーとの継続的な協働という狙いに合い、統制を望む財務機能にも合う。また、ビジネスケースが仮説がテストされるにつれて見直される生きた文書であることも意味する（トピック 6.5「価値の実現とビジネス成果」を参照）。

財務のいくつかの考え方が役立ちます。[貨幣の時間価値（time value of money）](https://en.wikipedia.org/wiki/Time_value_of_money)は、今日の通貨の1単位は後のものより価値があると述べ、したがって、より先の将来の便益はより少なく数えられます。[正味現在価値（NPV：net present value）](https://en.wikipedia.org/wiki/Net_present_value)は、割引率を使って、将来のコストと便益の流れを、今日の単一の値に換算します。[回収期間（payback period）](https://en.wikipedia.org/wiki/Payback_period)は、初期の支出を回収する時間です。それぞれが要約であり、それぞれが前提を隠すので、それらを述べます。[機会費用（opportunity cost）](https://en.wikipedia.org/wiki/Opportunity_cost)は、一つの選択肢を選ぶコストが、手放した最良の代替案の価値であることを思い出させます。[埋没費用（sunk cost）](https://en.wikipedia.org/wiki/Sunk_cost)は、すでに使われ回収できないお金で、続けるかの判断を駆動すべきではありません。

ビジネスケースのあらゆる数字は、寛大な期間、有利な割引率、確認しにくい便益を選ぶことで、悪用されうるものです。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、ケース自体に当てはまります。承認が見出しのROIに依存すると、著者はそれを作り出すことを学びます（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。したがって、以下の測定値には、過去の予測の質の確認が含まれています。

## 主要な原則

- **ケースを範囲を持つ予測として扱う。** 低、期待、高の結果を示し、それぞれの背後の前提を述べる。
- **完全なコストを数える。** 構築に加えて、運用、サポート、研修、変更の労力、処分を含める。
- **便益とその証拠を明示する。** コスト削減、コスト回避、収益、リスクの低減を分け、それぞれをどう測るかを述べる。
- **段階的に資金を付ける。** 仮説がテストされ、絵が改善するにつれてお金を解放する。
- **何もしないことを含め、代替案と比較する。** 現状維持のコストはケースの一部である。
- **自分自身の履歴から学ぶ。** 予測を成果と照らして確認し、調整する。
- **埋没費用を無視する。** 先にあるものに基づいて決める。

## 推奨事項

### ケースを誠実に書く

**1. 問題と選択肢から始める。** 問題、それを誰が体験するか、現在それにいくらかかるかを記述します。少なくとも三つの選択肢を列挙します。何もしない、最小限のステップ、提案された変更、そして深刻な代替案。「何もしない」にもコストがあり、たとえば継続するインシデントや増大するリスクで、それを含めることが比較を公正にします。

**2. 変更の寿命にわたる総所有コストを数える。** 構築、ライセンス、ホスティング、運用、サポート、研修、移行、それを使う人々の時間、処分を含めます。立ち上げの後に到来するコストが、最もよく省かれるものです。便益の寿命に合う期間を使い、それが何かを述べます。

**3. 各便益と、それをどう測るかを記述する。** 種類を分けます。コスト削減は実際の支出を減らします。コスト回避は、さもなければ生じていた支出を防ぎ、検証がより難しい。収益の便益は市場の行動に依存します。リスクの低減は損失の可能性または影響を下げ、特定のシナリオの観点で述べるのが最善です。それぞれについて、指標、ベースライン、オーナーを挙げます（トピック 6.5「価値の実現とビジネス成果」を参照）。

**4. 範囲を示し、何がそれを駆動するかを述べる。** コストと便益について、主な前提とともに、低、期待、高の見積もりを示します。[感度分析（sensitivity analysis）](https://en.wikipedia.org/wiki/Sensitivity_analysis)は、前提が変わったときに結果がどう変わるか、どの前提が最も重要かを示します。ケースがすべての前提が寛大な場合にのみ機能するなら、そう述べます。シミュレーションは範囲を組み合わせられますが、入力が推測なら、偽の安心を与えることもあります。

### 楽観を補正する

**5. 自分自身の履歴を参照クラスとして使う。** 過去の類似した取り組みの実際のコストと便益の成果を見て、予測されたものと比較します。過去の取り組みが平均して見積もりより30パーセント多くかかったなら、これを無視する新しい見積もりは、同じ誤りを繰り返しそうです。調整するか、少なくとも調整を示します。上のコストと便益の正確さの測定値が、この記録を築きます。

**6. チーム外の誰かにケースをレビューしてもらう。** 結果に利害のない、財務や別のチームの同僚が、欠けているコスト、寛大な便益、テストされていない前提がないかケースを読みます。レビューを日常的で建設的なものにします。それを生き延びたケースは、より強くなります。

**7. 可能なら、見積もる人と擁護する人を分ける。** デリバリーのチームは労力の見積もりが得意で、スポンサーは価値の判断が得意です。同じ人が承認を望むとき、見積もりは漂流します。誰がどの数字を作ったかを記録します。

### 段階的に資金を付ける

**8. 証拠に結び付いたステップで資金を解放する。** 最もリスクのある前提をテストする小さな最初のステージに資金を付けます。薄いスライスを作る、パイロットを実行する、ベースラインを測る。次のステージを正当化する証拠、仕事を再構成させる証拠、止めさせる証拠を事前に定義します。これはお金に適用されたリスクへのアジャイルのアプローチで、間違うことのコストに上限を設けます。

**9. 各ステージで、先にあるものに基づいて決める。** すでに使われたお金は埋没費用で、続けるかどうかに影響を与えるべきではありません。学んだことを踏まえて、残りのコストが残りの期待される便益で正当化されるかを問います。チームに止める許可を与え、証拠に基づく中止を良い成果として扱います。

**10. ステークホルダーを巻き込み続ける。** 各ステージで、スポンサーと便益のオーナーとケースをレビューします。全体を通じたステークホルダーとの協働はアジャイルの中核の狙いで、ケースが承認後に誰も読まない文書になるのを防ぎます。

### 確認して学ぶ

**11. 成果をケースに照らしてレビューする。** 合意したレビュー時点で、実際のコストと実現した便益を予測と比較します。比、違いの理由、次のケースで何を変えるかを記録します。誠実な報告がそれに依存するので、レビューを非難なく事実に基づいたものにします。

**12. 正確さの分布を意思決定者に報告する。** 過去の取り組みにわたって、予測が成果とどう比較されたかを示します。便益が同様の幅で定期的に不足するポートフォリオは、新しいケースをどれだけ信頼すべきかをリーダーに語り、著者に誠実である理由を与えます。ゲートが機能しているかを見るため、証拠に基づく中止の率と組にします。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 投資対効果 | 長い期間を選ぶ、あるいは柔らかい便益を数える。運営コストを省く | 期間とコストの範囲の固定の規則。便益の証拠の質。独立したレビュー |
| 総所有コスト | サポート、研修、変更の労力、処分を省く。楽観的な量を使う | コストの区分のチェックリスト。類似した過去の仕事の実際のTCOと比較する |
| 回収期間 | 開始を遅く定義する。実現しない便益を数える | 時計の定義を固定する。実現した便益の正確さと比較する |
| 正味現在価値 | 低い割引率を選ぶ。期間を延ばす | 財務ポリシーが設定する割引率。感度分析を示す |
| コスト見積もりの正確さ | 事後に基準の見積もりを修正する。超過を範囲の変更として除外する | 承認時に凍結された見積もり。承認とともに範囲の変更を記録する。完了までの総コストを示す |
| 便益見積もりの正確さ | 測定されなかった便益を数える。便益を再定義する | 便益の台帳の規則。デリバリーチームの外のオーナーが確認する |
| 証拠に基づく中止の率 | 率を水増しするために低価値の仕事を止める。何も止めない | 正確さの測定値とともに読む。中止と継続の理由をレビューする |

健全な読みは、実績のあるポートフォリオです。既知の形で多少楽観的な予測、範囲と感度を含むケース、時に証拠に基づいて仕事を止めるゲート。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| 大きな事前のビジネスケース | 明確なコミットメントと統制 | 前提を固定する。楽観を招く |
| 段階的な資金付け | 間違うコストを限定する。早期に学ぶ | ゲートでの規律が要る。計画の確実性が低い |
| 単一のROIの数字 | 比較が単純 | 前提を隠す。悪用しやすい |
| 感度を伴う範囲 | 不確実性について誠実 | 比較しにくい。曖昧に感じられるかもしれない |
| 定性的なケース | 戦略的な理由とリスクの理由をとらえる | 比較と検証が難しい |
| 定量的なケース | 比較でき、テスト可能 | 偽の精度。数えられないものを省く |
| 外部の参照クラス | 楽観を補正する | 自分の文脈に合わないかもしれない |
| 自分自身の履歴の参照クラス | 自分の文脈に合う | 記録が要る。小さな標本 |

散文での答えは、段階的な資金付け、範囲、自分自身の履歴を、数字が見逃すものの短い定性的な説明とともに使うことです。ROI、NPV、回収期間を、評決ではなく、要約として使います。

## チームで話し合う問い

**1. 直近五つのビジネスケースはどれだけ間違っていて、どちらの方向にか？**
最近の取り組みについて、予測と実際のコストと便益を集めます。比を計算します。ばらつきと、誤差が一方に偏っているかを見ます。ファシリテーターは、最初のパスでは説明に抵抗し、パターンを記録するだけにしてください。それから、次のケースに何を意味するかを話し合います。

**2. 現在の提案の最もリスクのある前提は何で、どれだけ安くテストできるか？**
前提を列挙し、ケースがそれぞれにどれだけ依存し、どれだけ不確かかで順位付けます。上位のものについて、小さなテストを設計します。答えが最初の資金付けのステージを形作ります。

**3. 何もしないことにはいくらかかり、それをケースに入れたか？**
提案が承認されない場合の、ありそうな道筋を記述します。継続するインシデントのコスト、増える保守、増大するリスク。範囲で見積もります。ケースがそれと公正に比較されていることを確認します。

**4. 私たちのプロジェクトで常に遅れて現れるコストは何か？**
運用、研修、移行、廃止を考えます。それぞれについてケースを確認します。テンプレートに、コストの区分の標準チェックリストを加えます。

**5. チームの外の誰が私たちの数字に異議を唱え、何と言ったか？**
直近の独立したレビューを見ます。なければ、次を誰が行うべきかを決めます。対話は、レビューがケースへのサービスであり、攻撃ではないことを明確にするべきです。

**6. 証拠が変わったために何かを最後に止めたのはいつで、どう感じられたか？**
中止または再構成された取り組みを思い出します。それがどう受け止められ、信頼に何をもたらしたかを話し合います。次の中止を学びとして感じさせる方法に合意します。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、コストの見積もりを供給し、資金付けのステージから学びます。範囲で見積もり、実際のコストを記録し、前提が崩れたときに声を上げるべきです。段階的な資金付けは、最も重要なことを学ぶことに集中できるようにし、証拠に基づく中止は成功として数えられるべきです。

### サービスと運用のチーム

運用チームは、立ち上げ後のコストの多くを所有し、ケースから外されることがよくあります。運営コスト、サポートの労力、リスクを尋ねられ、インシデントの減少のような、自分たちの仕事に依存する便益を確認するべきです。運用での節約の主張を、自分たちのデータで検証できます。

### リーダーシップとガバナンス

リーダーは何に資金が付けられるかを決め、誠実さの風土を設定します。範囲と前提を求め、予測の実績をレビューし、段階的に資金を付け、中止を通常の成果として受け入れるべきです。ガバナンスは、大きなケースの独立したレビューと実施後の確認を要求し、成果のポートフォリオを見るべきです。

### 顧客とユーザー

ユーザーと事業のオーナーは、便益と中断の両方を負います。彼らはケースの一部であり、問題と便益を定義する助けをし、何がなぜ決まったかを伝えられるべきです。提供後の彼らの体験は、ケースが正しかったかの最良のテストです。

## 実践：サービスマネジメントの例

州の保健機関のITグループが、定型的なアクセス依頼を自動化し、手作業の処理を減らすプログラムを提案します。以下の数字は例示です。

提案の最初の草稿は、年間18,000件のリクエスト、平均的な手作業の処理コスト、リクエストの80パーセントの完全な自動化に基づき、5年間でROI 240パーセントを主張しています。財務のパートナーは、グループ自身の履歴を適用することを提案します。彼女は過去の八つの取り組みを引き出します。実際のコストは見積もりの中央値1.35倍で、範囲は1.0から1.9、実現した便益は期待された便益の中央値0.6でした。グループはまた、リクエスト量の数字が単一の忙しい年から来たこと、そしてコストの見積もりが研修と例外をレビューするスタッフの時間を省いていたことを見つけます。

チームは範囲を使ってケースを書き直します。コストの履歴を使うと、期待されるコストは3分の1上がります。便益の履歴を使うと、期待される便益はおよそ半分に減ります。改訂されたケースは、わずかにマイナスから約70パーセントまでの範囲のROI、20から40か月の間の回収期間、財務ポリシーの割引率で、中間と期待のケースで正、低いケースで負となるNPVを示します。感度分析は、自動化できるリクエストの割合が最も重要であることを示します。提案は段階に再構成されます。最初のステージは、自動化の割合をテストし、ベースラインの処理時間を測るため、総額の約5分の1の予算で、最も一般的な三つのリクエストの種類を自動化します。第二ステージの基準が書き下されます。それらのリクエストの種類の少なくとも50パーセントが完全に自動化され、リクエストあたりの処理時間が述べた量だけ減り、便益のオーナーが確認する。

最初のステージの後、三つのリクエストの種類の58パーセントが自動化され、例外は予想より時間がかかります。チームは、より多くの種類に拡張する前に例外処理を改善するよう、第二ステージを再構成します。機関の取締役会は、なぜROIの数字が下がったのかを尋ねます。責任者は、以前の数字は完全な自動化と超過の履歴なしを仮定していたこと、新しい範囲のほうがより誠実であることを説明します。判断は記録されます。第二ステージの証拠に基づく再構成が記録され、ポートフォリオのコストと便益の正確さの表が更新されます。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

証拠が届くにつれて段階的に仕事に資金を付け、リリース後にステークホルダーと予測を確認します。注意点は、単一の大きなビジネスケースは、楽観的な前提を招くことです。

### AI

AIのビジネスケースはしばしば生産性の主張に頼るので、ベースライン、測定された変化、品質への影響を記録し、予測と結果を比較します。注意点は、AIベンダーの主張は自分たちの文脈に移らないかもしれないため、拡大する前にパイロットでテストすることです。

### 自動化

存在するコストと便益のデータの収集を自動化し、ビジネスケースのプロセスを見積もりの正確さで測ります。注意点は、自動化の便益はしばしば節約された時間として主張されるが、その時間が使われない限りお金にはならないことです。

### アナリティクス

範囲と前提を示し、時間にわたる見積もりの正確さを追跡します。これが情報を与える判断は、続けるか、変えるか、止めるかです。注意点は、投資対効果が前提に依存するため、数字の隣に前提を示すことです。

## 業種別の視点

**スタートアップ。** 資源は乏しく、学びの速さが重要です。最もリスクのある前提と安いテストを伴う1ページのケースを使い、小さなステップで資金を付け、凝った財務モデルを避けます。NPVではなく、滑走路の長さがしばしば拘束する制約です。

**中小企業。** オーナーがスポンサーであり、財務機能です。回収とキャッシュフローに焦点を当て、スタッフの時間を含め、何もしない、購入するという選択肢と比較します。ベンダーが提供するROI計算機は、寛大な傾向があるので注意します。

**大企業。** ポートフォリオのガバナンス、割引率についての財務ポリシー、多くの競合する提案が、一貫性を重要にします。必要なコストの区分を持つ標準テンプレート、大きなケースの独立したレビュー、実施後のレビューを使います。スポンサー別と取り組みの種類別の予測の正確さの記録を、人の順位付けではなく、ポートフォリオの道具として保ちます。

**政府・公共部門。** 公的機関はしばしば、選択肢をどう評価するか、楽観バイアスをどう扱うか、非財務的な便益を含む費用対効果をどう考えるかを定める、英国のグリーンブックなどの正式な評価のガイダンスに従います。便益は社会的で貨幣化しにくいことがあり、透明性と監査が重要です。自分に適用されるガイダンスを使い、前提を文書化し、便益の証拠を記録します（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

このトピック自体がビジネスケースについてなので、要点は、それをうまく行うコストです。注意深いケースを書くには、数時間ではなく数日かかり、独立したレビューにはさらにかかります。コストと便益の正確さの追跡には、各取り組みの予測と成果の単純な記録が必要で、多くの組織はそれを欠いています。段階的な資金付けは、ガバナンスの会議を加えます。

見返りは、乏しいお金のより良い配分と、大きな失敗の減少です。誠実なケースは、楽観的なものに続く驚きを減らします。実績は、リーダーが新しいケースを適切に割り引けるようにし、ポートフォリオ全体をより信頼できるものにします。自分たち自身の履歴から論拠を築きます。実際と見積もりのコストと便益の比、のちに放棄された取り組みに使われたお金、レビューのコストと、それが防いだ超過との比較。自分たちの種類の仕事への方法と関連性をたどれない限り、プロジェクトの失敗率の研究の引用は避けます。

## アンチパターンと落とし穴

- **事実として提示される単一のROIの数字。** 前提を隠す。範囲と感度を示す。
- **運営コストを省く。** 構築は生涯コストのごく一部である。全生涯を数える。
- **柔らかい便益を硬いものとして数える。** コスト回避と生産性の主張には証拠が要る。ラベルを付けてテストする。
- **積み上げだけで予測する。** 楽観を繰り返す。自分自身の履歴と比較する。
- **すべての資金を事前に。** 推測を固定する。証拠のゲートを伴う段階で資金を付ける。
- **すでに使ったお金のために続ける。** 先にあるものに基づいて決める。
- **自分の宿題に自分で採点する。** 独立した読み手にコストと便益をレビューさせる。
- **ケースを決して見直さない。** 成果のレビューがなければ、何も改善しない。予測を結果と照らして確認する。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| ケースを書く | 見出しの数字を伴う非公式な売り込み | コストと便益を伴うテンプレート | TCOのチェックリスト、範囲、感度を伴う標準テンプレート | 自分自身の履歴による調整が適用される。独立したレビュー | 事業のオーナーと財務とケースを共同で作成する。ポートフォリオ全体で共有された前提 |
| 資金付け | すべて事前 | マイルストーン | 証拠の基準を伴う段階的な資金付け | ゲートが日常的に証拠に基づいて仕事を再構成または中止する | ポートフォリオの資金が、証拠に基づいて取り組み間で柔軟に動く |
| 学び | フォローアップなし | 時折のレビュー | ケースに照らした実施後のレビュー | コストと便益の正確さが分布として追跡され、新しいケースで使われる | 学びが組織全体とパートナーに共有され、方法が改善される |

## チェックリスト

- [ ] ケースが、何もしないことを含む選択肢を列挙している。
- [ ] 総所有コストが、構築、運用、サポート、研修、変更、処分をカバーしている。
- [ ] 各便益に、種類、指標、ベースライン、オーナーがある。
- [ ] コストと便益が、ドライバーを述べた範囲として与えられている。
- [ ] 感度分析が、どの前提が最も重要かを示している。
- [ ] 見積もりが、類似した取り組みの自分自身の履歴と比較されている。
- [ ] 独立したレビュー担当者がケースを読んでいる。
- [ ] 資金付けが、続ける、再構成する、止めるための証拠の基準とともに段階的である。
- [ ] 成果が、合意した日付にケースに照らしてレビューされている。
- [ ] 過去の取り組みにわたるコストと便益の正確さが、意思決定者に報告されている。

## AIプロンプト

**ビジネスケースのストレステストを行う。**

```text
以下は [取り組み] のビジネスケースの要約です：コスト [範囲付きの一覧]、便益 [種類と範囲付きの一覧]、期間 [年]、割引率 [財務が設定した率]、前提 [一覧]。欠けているコストの区分、より強い証拠が要る便益、結果を支配する前提、楽観のリスクを特定してください。感度分析と段階的な資金付けの構造を提案してください。数字を捏造しないでください。前提と、私が答えるべき問いを列挙してください。
```

**自分たちの履歴から参照クラスを築く。**

```text
予測と実際のコストと便益を持つ、次の過去の取り組みがあります：[表を貼り付け]。実際と予測の比を計算し、中央値とばらつきを述べ、取り組みの種類別のパターンにコメントし、新しい取り組みを見積もるときにこれをどう使うかを提案してください。標本が頼るには小さすぎる箇所を警告してください。外部のベンチマークを使わないでください。前提を列挙してください。
```

**ステージゲートを設計する。**

```text
[取り組み] について、三つの資金付けのステージを提案してください。それぞれについて、テストする最もリスクのある前提、先に進むことを正当化する証拠、仕事を再構成させる証拠、止めさせる証拠を述べてください。各ステージを小さく安く保ってください。特定のデリバリーの方法を仮定しないでください。前提と、リーダーシップの入力が要る判断を列挙してください。
```

**実施後のレビューを書く。**

```text
[取り組み] の1ページの実施後のレビューを起案してください。入力：元のケース [要約]、実際のコスト [数字]、実現した便益と証拠 [要約]、途中で変わったこと [一覧]。コストと便益の比、違いの理由、次のケースで何を変えるか、便益のオーナーへの問いを含めてください。トーンは事実に基づき、非難なしにしてください。前提と、確認が必要な主張を列挙してください。
```

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：ビジネスケースまたはROIのメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：財務のメトリクスの項目が、期間、前提、悪用の手口、防護柵を述べているかを確認するときに使います。

## 要点

- ビジネスケースは予測である。範囲、前提、感度を示す。
- 変更の寿命にわたる総所有コストを数え、何もしないことと比較する。
- 予測と成果の自分自身の履歴を使って、楽観を補正する。
- 段階的に資金を付け、先にあるものに基づいて決め、証拠に基づく中止を成功として扱う。
- 成果をケースに照らしてレビューし、正確さを意思決定者に報告する。
- ROI、NPV、回収期間を、評決ではなく、述べた規則を伴う要約として使う。
