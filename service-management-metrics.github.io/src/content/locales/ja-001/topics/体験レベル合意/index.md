# 体験レベル合意

**体験レベル合意は、「サービスは目標を満たしたか」という問いに、「使ってみてどう感じたか」という問いを加える。それが機能するのは、体験の測定値がユーザーとともに選ばれ、運用の測定値の隣に保たれる場合だけである。**

## 概要と動機

[サービスレベル合意（service-level agreement）](https://en.wikipedia.org/wiki/Service-level_agreement)（SLA）は、プロバイダーが提供にコミットすることを、通常はプロバイダーが数えられる言葉で記録します。可用性、応答時間、解決時間。それらの測定値は有用であり、同時に不完全でもあります。チームはダッシュボード上のすべての目標を満たしながら、ユーザーが遅いログインを回避し、サービスデスクに繰り返し説明し、承認を待つことで一週間を費やしていることがありえます。緑のレポートと不満なユーザーの間のこのギャップは、ウォーターメロン効果と呼ばれることがあります。外側は緑で、内側は赤（トピック 5.1「SLA、OLA、XLAのメトリクス」を参照）。

**体験レベル合意（XLA：experience level agreement）**は、プロバイダーとサービスを使う人々の間の、サービスが与えるべき体験についての合意です。望ましい成果と感情を述べます。たとえば「到着して数分以内に仕事を始められる」「依頼が扱われると信頼できる」。そして、それらが満たされているかを示す測定値に名前を付けます。この用語はITサービスマネジメント（ITSM）のコミュニティ全体で使われ、その正確な定義は著者やベンダーによって異なります。XLAをITILの一部として記述する前に、フレームワークの所有者の現行の出版物を確認し、どの用法に従うかを述べてください。このトピックは、XLAを実際的な考え方として扱います。体験の測定値を運用の測定値の隣に置く合意です。

この考え方には、ITの外にルーツがあります。[ユーザーエクスペリエンス（user experience）](https://en.wikipedia.org/wiki/User_experience)は、人が製品、システム、サービスを使う全体的な体験であり、[カスタマーエクスペリエンス（customer experience）](https://en.wikipedia.org/wiki/Customer_experience)は、時間にわたる組織との顧客のやり取りの総和です。[ユーザビリティ（usability）](https://en.wikipedia.org/wiki/Usability)は、人々がどれだけ効果的に、効率的に、満足して目標に到達できるかに関わります。アジャイルのチームは、デザイン思考とユーザーリサーチ、そしてユーザーが動くソフトウェアに反応するステークホルダーレビューから、この領域を知っています。XLAは、同じ注意を稼働中のサービスにもたらします。

体験は測るのが難しく、歪めやすいものです。幸せなユーザーにしか届かないアンケート、上がるように調整されたセンチメントのスコア、誰も説明できない単一の「体験指数」は、操作されたチケット時間と同じくらい確実に誤解を招きます。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、そのまま当てはまります。体験の測定値は、ノルマではなく、対話のきっかけです（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

このトピックは、前のトピックのアンケートの測定値の上に築かれ（トピック 6.1「顧客満足度のメトリクス」を参照）、尋ねることに依存しない、行動と旅路ベースの測定値を加えます。

## 主要な原則

- **人々が気にする成果から始める。** ユーザーに良い一日がどんなものかを尋ね、合意を彼らの言葉で書く。
- **体験を運用と組にする。** XLAはSLAの隣に位置し、その代わりではない。
- **異なる角度からの少数の測定値を使う。** 人々が言うこと、することと、システムが記録することを組み合わせる。
- **接点だけでなく旅路を測る。** 体験は、必要から成果までの全経路である。
- **不確実性について誠実である。** 体験のデータはノイズが多く、小さなグループは保護が必要である。
- **目標をユーザーと合意し、見直す。** XLAは生きた合意であり、それが記述する人々とレビューされる。
- **体験のデータで個人に順位を付けることは決してしない。**

## 推奨事項

### ユーザーとともに合意を設計する

**1. 測る前にインタビューする。** 各重要なグループのユーザーの標本と時間を過ごし、尋ねます。このサービスでの良い一日はどんなものか。どこで時間を無駄にするか。それが機能していたら何をやめるか。[人間中心設計（human-centered design）](https://en.wikipedia.org/wiki/Human-centered_design)の習慣を使います。実際の仕事を観察し、聞いたことをユーザーの言葉で書く。結果として得られる記述が、合意の体験の目標になります。

**2. 体験の記述を成果として書く。** 「新入社員を初日の朝から生産的にできる」は、「新入社員のアクセス依頼が2日で解決」より多くを語ります。各記述を、一人称で短く、一つのサービスに結び付けて保ちます。人々が覚えていられるよう、サービスごとに三つから五つの記述を目指します。

**3. 三つの角度から測定値を選ぶ。** 各記述について、人々が言うこと（パルスの質問またはコメントのテーマ）から一つ、人々がすること（旅路の完了、繰り返しの問い合わせ、放棄されたリクエスト）から一つ、可能ならシステムが記録すること（旅路のステップのレイテンシ）から一つを選びます。三つが食い違うとき、調査すべきものを見つけたのです。

**4. 目標は軽く合意する。** 初期には、硬い数字ではなく、方向（「失われた時間を減らす」）とレビュー日を設定します。新しい体験の測定値に対する硬い目標は、測定値が理解される前に悪用を招きます。目標が現れるときは、範囲にして、誰が合意したかを述べます。

### データを集めて読む

**5. 短い定期的なパルスの質問を使う。** 一つの記述についての一つの質問を、定期的な間隔で尋ねるほうが、長い年次のアンケートより答えやすいものです。記述を入れ替え、文言を安定に保ち、定められた期間内に同じ人に一度より多く尋ねないようにします。パルスの設計を、前のトピックのアンケートの原則に結び付けます（トピック 6.1「顧客満足度のメトリクス」を参照）。

**6. コメントを方法を持って読む。** [センチメント分析（sentiment analysis）](https://en.wikipedia.org/wiki/Sentiment_analysis)のツールは大量のテキストを仕分けできますが、皮肉、専門用語、文脈を誤読します。ツールの出力を最初のパスとして扱い、毎月人に抽出を確認してもらい、手作業でコード化するテーマの短い一覧を保ちます。分析の狙いは、スコアを生むことではなく、ユーザーと話す話題を見つけることです。

**7. 旅路から行動のシグナルを加える。** ユーザーが気にする旅路を、彼らの了解を得て計装します。どこで始め、どこで離脱し、どこでヘルプを求めるか。ページの読み込み時間、エラー、ステップの[実ユーザー監視（real user monitoring）](https://en.wikipedia.org/wiki/Real_user_monitoring)は、アンケートが与えられない見方を与えます。何を集めるかをユーザーに伝え、必要なものに絞り、共有する前に集約します。

**8. 小さなグループと個人を守る。** 体験のデータは、誰が苦労しているかを明らかにしうるものです。結果を集約し、合意した規模未満のグループを抑制し、データを業績評価に決して使いません。誰が生のコメントを見られるかを決め、それに応じて保管します。規制された場面では、行動データを集める前にプライバシーの専門家に確認します。

### 合意を使う

**9. SLAとXLAを並べて示す。** 同じページに、各サービスの運用の達成率と体験の測定値を表示します。組み合わせが要点です。体験スコアが下がっているのにSLAが緑なら、対話への促しであり、体験スコアが緑でSLAが失敗しているなら、ユーザーに何が伝えられていないかを見る価値があります。

**10. ユーザーとの定期的な体験レビューを開く。** 四半期ごとにユーザーグループの代表と会い、データを示し、それが何を意味するかを尋ね、試す改善を一つか二つ合意します。サービスデスクとプロダクトチームを含めます。貧弱な体験の原因は、サポートではなくプロダクトにあることが多いからです。

**11. 修正に資金を付ける。** 摩擦を特定してそのままにしておく合意は、測定値が芝居であることをユーザーに教えます。上位二、三の体験の問題を、オーナーと日付とともにバックログに載せ、次のレビューで報告します。この本の後の継続的改善のメトリクスを参照してください（トピック 9.5「継続的改善のメトリクス」を参照）。

**12. サービスとユーザーが変わるにつれて合意を見直す。** もう重要でない記述を廃止し、新しいものを加えます。他のメトリクスの定義と同じように、変更を記録し、傾向のグラフに印を付けます。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 体験スコア | 満足しているユーザーにだけアンケートを送る、良い出来事の後にアンケートのタイミングを合わせる、より同意しやすいよう記述を言い換える | 回答率と回答者の構成。安定した文言の記録。コメントを読む |
| センチメントの傾向 | 傾向が上がるまでツールやテーマの一覧を調整する、否定的な経路を除外する | 毎月の抽出を人が確認する。固定のコード化の手引きを保ち、変更を記録する |
| ユーザーあたりの摩擦イベント | 数えられるものが減るようイベントを再定義する、サービスデスクを連絡しにくくして繰り返しの問い合わせを妨げる | 経路別の問い合わせ量。サービスデスクの放棄率（トピック 3.1「サービスデスクのメトリクス」を参照） |
| ITの問題で失われた時間 | 低い見積もりに誘導する聞き方をする、重大インシデントだけを数える | 自己申告の時間を、測定した劣化時間と比較する。アンケートの文言のレビュー |
| 旅路の完了率 | 失敗が対象外になるほど狭く旅路を定義する、難しい事例を別の経路に誘導する | 台帳にある旅路の定義。ヘルプの問い合わせ率とエスカレーション |
| XLA達成率 | すでに満たされている目標を設定する、非常に少数の目標を定義する | ユーザーとともにレビューする目標設定。傾向と目標の履歴とともに達成率を示す |
| 体験のギャップ | 最も良く見えるサービスや期間を選ぶ、比較するSLAを変える | 事前に合意した固定の比較の集合。すべてのサービスを示す |

健全な読みは、コメントとユーザーのレビューの対話に合う体験の様子、チームが説明できる理由でゆっくり変化する少数の測定値、そして短くなる体験の修正のバックログです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| SLAのみ | 明確で、数えられ、契約上のもの | ユーザーが感じることを見逃す。ユーザーが不満でも緑でありうる |
| XLAのみ | ユーザーが価値を置くものに近い | 測定と比較がより難しい。供給者との契約の基礎としては弱い |
| SLAとXLA | 両方の見方を与え、ギャップを明らかにする | より多くの仕事。食い違いを読むのに信頼と判断が要る |
| アンケートベースの体験の測定値 | ユーザーの直接の声 | 回答バイアス。回答者への負担 |
| 行動の測定値 | アンケートの負担なし。客観的 | 計装とプライバシーへの配慮が要る。何が起きたかを示すが、なぜかは示さない |
| 単一の体験指数 | 見出しが容易 | 詳細を隠す。操作しやすく、説明しにくい |

散文での答えは、XLAを追加として使い、運用と体験のギャップがすでに見えている少数のサービスに導入することです。供給者が制御できない体験の測定値で、契約上のSLAを置き換えてはいけません。法的、商業的なコミットメントはSLAに保ち、XLAは改善と対話を駆動するために使います。

## チームで話し合う問い

**1. 最も重要なサービスについて、ユーザーにとっての良い一日は、彼ら自身の言葉でどんなものか？**
二、三人のユーザーを集める、あるいは最近のインタビューを再利用し、彼らの記述を書き留めます。ファシリテーターは、それらを運用の言葉に言い換えるのに抵抗してください。記述を現在のSLAと比較し、どの記述がカバーされ、どれが無視されているかを尋ねます。ギャップが体験の測定値の候補です。

**2. 私たちの緑のダッシュボードとユーザーの物語が食い違うのはどこか？**
チームに、サービスが目標を満たしながらユーザーが不満を言った最近の事例を尋ねます。事例をデータを通じてたどります。何を測り、何を見逃したか。対話は、欠けているステップ、引き継ぎ、早く止まった時計を浮かび上がらせることがよくあります。事例を、ユーザーとの次のレビューのための例として記録します。

**3. この体験の記述が真かどうかを知るために、どの三つの測定値を使うか？**
記述を一つ選び、人々が言うことから一つ、することから一つ、システムが記録することから一つの測定値を選びます。それぞれが何を見逃しうるか、どう悪用されうるかを尋ねます。懐疑的なユーザーを納得させる最小の集合に合意します。

**4. ユーザーが予期しないかもしれない何を集めているか、彼らはそれに納得できるか？**
行動のデータソースと、それぞれの目的を列挙します。ユーザーの代表に反応してもらいます。ファシリテーターは、不快感を障害ではなく、設計についての情報として扱ってください。何を集めるのをやめるか、何を集約するか、誰が生のデータを見られるかを決めます。

**5. すべてのSLAが緑のまま、体験スコアが下がったら、何をするか？**
対応をリハーサルします。誰が最初に見て、何を確認し、誰に話すか。チームが体験スコアを信頼するか、それを退ける方法を探すかを決めます。答えは、チームが合意をどれだけ真剣に受け止めているかを示します。

**6. 私たちが約束した体験の修正は何で、それらはどうなったか？**
ユーザーとの直近二回のレビュー会議を見直します。各コミットメントについて、日付、オーナー、成果を示します。一覧が空か古いなら、その理由を話し合います。次のレビューまでに提供する修正を一つと、それが起きたことをユーザーに伝える方法に合意します。

## 四つの視点

### プロダクトとデリバリーのチーム

プロダクトチームは、貧弱な体験の原因の多くを握っています。混乱する画面、遅いステップ、不明確なエラー。体験の測定値は、実際の使用からの証拠を彼らに与え、リファインメントに直接供給されます。チームは、各計画の前にコメントのテーマを読み、旅路の測定値をバックログに結び付けるべきです。体験スコアをチームの目標として扱ってはいけません。それは、運用と共有するサービスについての情報です。

### サービスと運用のチーム

運用チームは、摩擦を最初に目にします。繰り返しの問い合わせ、回避策、怒った電話。体験の測定値は、SLAが隠すものを示す方法と、チケットをより速くクローズする代わりに原因を直す理由を与えます。定義とサンプリングを守り、良く見えるチャネルにユーザーを誘導するのを避け、不満のコメントを全文読むべきです（トピック 3.1「サービスデスクのメトリクス」を参照）。

### リーダーシップとガバナンス

リーダーは、XLAが対話かスコアボードかを選びます。体験のデータが投資する場所について何を言っているかを問い、給与を体験指数に結び付けるのを避け、スタッフのデータのプライバシーを守るべきです。ガバナンスは、定義、サンプリング、変更履歴を求め、体験の測定値の説明のつかない跳ね上がりを、方法を確認する理由として扱うべきです。

### 顧客とユーザー

ユーザーは合意の作者です。良い状態がどんなものかを述べるよう招かれ、結果を示され、何が変わったかを伝えられるべきです。自分たちについて何が集められ、なぜかを知り、ノーと言う方法を持つべきです。頻繁に尋ねられ、何も改善されないのを見るユーザーは答えるのをやめ、その沈黙は、データを現実より良く見せるでしょう。

## 実践：サービスマネジメントの例

中規模の専門サービス会社が、1,800人のスタッフのための社内ITサービスを運営しています。以下の数字は例示です。

月次のSLAレポートは、コラボレーション基盤の可用性99.8パーセント、インシデントの96パーセントが目標内に解決されたことを示します。IT責任者は満足していますが、顧客先のコンサルタントは遅いサインインについて不満を言い続けています。サービスマネージャーは、コラボレーション基盤のXLAのパイロットを提案します。

12人のコンサルタントへのインタビューから、三つの記述が現れます。「そうしようと決めてから2分以内に、顧客との通話に参加できる」「アカウントに戻るためにITに電話しなくてよい」「何かが壊れたとき、何が起きているか分かる」。チームはそれぞれについて測定値を選びます。最初のものについては、その記述のパルス評価と、顧客側の実ユーザー監視から、リージョン別に集約した、サインインの開始から通話への参加までの測定時間を取ります。二つ目については、アクティブユーザーあたり月ごとのパスワードリセットの問い合わせを数えます。三つ目については、ステータスのメッセージが30分以内に更新されたインシデントの割合を追跡し、それについてのパルスの質問をします。

最初の二か月のデータは、サインインから通話参加までの時間の中央値が本社のリージョンでは問題ないが、他の二つでは長いこと、そしてユーザーあたりのパスワードリセットの問い合わせが、管理対象のノートパソコンのスタッフで他より3倍高いことを示します。最初の記述の体験スコアは、オフィス勤務のスタッフの4.2に対して、5点満点で3.1です。SLAはどちらでも緑です。サービスマネージャーは所見をユーザーレビューに持ち込みます。チームは二つの改善に合意します。リモートのリージョン向けのシングルサインオンの設定の調整と、管理対象のノートパソコンのトークン更新の設定の変更。三か月後、時間の中央値は下がり、ユーザーあたりのリセットの問い合わせは減り、体験スコアは3.8に上がります。責任者は、このサービスでXLAを続け、もう一つ追加し、次のレビューまで数値目標を設定しないことに合意します。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

体験の測定値をユーザーと合意し、ステークホルダーの継続的な関与とともに、サービスが進化するにつれて見直します。注意点は、プロバイダーだけで設定された体験の目標は、ユーザーが感じることを記述しないことです。

### AI

AI機能は体験を直接変えるので、それを使う旅路を含め、モデルの確信度ではなくユーザーの成果を測ります。体験スコアを、タスクの完了と人へのエスカレーションと組にします。注意点は、タスクに失敗しながら心地よく感じられるチャットボットは、スコアを良く見せることです。

### 自動化

摩擦イベントと旅路の完了を、同意とプライバシーの規則のもとで自動で集め、収集を網羅率で測ります。注意点は、個人についての自動の体験データは監視になりうるため、集約して最小限にすることです。

### アナリティクス

体験スコアを運用の測定値と同じページに、そして両者の間のギャップとともに報告します。これが情報を与える判断は、SLAが緑であっても、どのサービスを改善するかです。注意点は、ギャップは測定上の人為的なものでありうるため、標本を確認することです。

## 業種別の視点

**スタートアップ。** ユーザーとの密な接触により、インタビューが容易です。フレームワークを築くのに抵抗します。中核サービスについて三つの体験の記述を書き、毎月ユーザーにそれらについて尋ね、行動の測定値を一つ加えます。正式な合意は後で来ます。

**中小企業。** スタッフは少なく、ITとマネージャーを共有することがよくあります。会話と非常に短い月次のパルスを使います。小さなグループは簡単に特定されるので、行動のデータには注意します。

**大企業。** 規模は多くのユーザーグループと供給者をもたらします。サービスとペルソナごとに体験の記述を定義し、ダッシュボードをサービスごとに保ち、会社全体の単一の体験指数は避けます。供給者が影響できない測定値に責任を負わされずにデータを寄与できるよう、XLAを供給者との契約と整合させます。

**政府・公共部門。** サービスは職員だけでなく一般市民にも向き、アクセシビリティ、平易な言葉、平等なアクセスについての義務がしばしばあります。体験の記述と測定値にアクセシビリティを含め、支援技術に頼るユーザーとテストし、法律に沿って個人データを保護します。公的な報告が求められるところでは、結果とともに方法を報告します（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは中程度です。ユーザーインタビューは、サービスごとに数日かかります。月次のパルスアンケートにはアンケートのツールが要り、多くの組織はすでに持っています。行動の測定値には一定の計装が要り、既存の監視とポータルのアナリティクスから来るかもしれません。ユーザーとのレビューは、四半期に数時間かかります。コメントのコード化は、毎月1、2時間かかります。

見返りは、特定のリージョンやデバイスでの遅い旅路のような、SLAが示さない問題を見つけること、そして改善のお金をユーザーが価値を置くものに向けることにあります。ITの問題で失われた時間は、慎重に測れば、自社のスタッフの単価でコストに変えられます。生産性向上についての一般的な主張は避けてください。自分たち自身のベースラインからケースを築きます。修正の前後での、ユーザーあたりの失われた時間、ユーザーあたりの摩擦イベント、繰り返しの問い合わせ。また、公式のサービスが使いにくいために採用されるシャドーツールのような、回避策の避けられたコストも数えます。

## アンチパターンと落とし穴

- **SLAをXLAで置き換える。** 契約には数えられるコミットメントが要る。両方を保ち、一緒に示す。
- **一つの合成された体験指数。** 原因を隠し、悪用を招く。少数の別々の測定値を示す。
- **ユーザーなしに体験を定義する。** 会議室で書かれた記述は、プロバイダーの見方を記述する。ユーザーとインタビューし、テストする。
- **人々が答えなくなるまでアンケートする。** パルスを短く保ち、話題を入れ替える。
- **誰にも伝えずに行動のデータを集める。** 信頼を壊し、法に反するかもしれない。何を集めるか、なぜかについて率直であること。
- **体験のデータを業績評価に使う。** 学びのツールを監視に変え、誠実な報告を壊す。
- **原因ではなく、測定値を直す。** 数字を改善するために、ユーザーをより友好的なチャネルへ誘導しない。旅路を直す。
- **所見をスライドの上に放置する。** 体験の修正に資金を付け、追跡する。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| 体験の目標 | 暗黙的か、存在しない | 一部のサービスについてプロバイダーが書く | 主要なサービスについてユーザーとともに書かれた記述 | ユーザーグループとともに、四半期ごとに記述をレビューして見直す | サービスと供給者にまたがって共有され、ユーザーと共同で所有される |
| 測定 | 時折のアンケート | 一つのサービスのパルスアンケート | 各記述について三つの角度（言う、する、システム）の測定値 | 測定値を傾向として追い、小さなグループを保護し、SLAと比較する | プロバイダーにまたがってデータが組み合わされ、ユーザーが制御するプライバシーの選択がある |
| 行動 | 苦情が一つずつ扱われる | 修正がアドホックに行われる | 上位の体験の問題が、オーナーとともにバックログにある | 修正に資金が付き、追跡され、ユーザーに報告される | 改善がチーム、供給者、ユーザーにまたがって調整され、学びが共有される |

## チェックリスト

- [ ] 各XLAのサービスに、ユーザーとともに書かれた三つから五つの体験の記述がある。
- [ ] 各記述に、少なくとも二つの角度（言う、する、システム）からの測定値がある。
- [ ] 各サービスについて、SLAと体験の測定値が同じページに現れている。
- [ ] パルスアンケートが、短く、定期的で、文言が安定している。
- [ ] コメントが安定した手引きでコード化され、毎月人が抽出を確認している。
- [ ] 合意した規模未満のグループが、レポートで抑制されている。
- [ ] 集めた行動のデータがユーザーに開示され、必要なものに限定されている。
- [ ] どの体験の測定値も、個人の業績評価に使われていない。
- [ ] ユーザーの代表との四半期ごとのレビューがカレンダーにある。
- [ ] 上位の体験の問題が、オーナーと日付とともにバックログにある。

## AIプロンプト

**インタビューのメモから体験の記述を起案する。**

```text
以下は、[組織の種類] の [サービス] のユーザー [数] 人へのインタビューの匿名化したメモです：[メモを貼り付け]。ユーザーが気にする一つの成果に結び付いた、一人称の三つから五つの体験の記述を、可能な限り彼らの言葉を使って提案してください。それぞれについて、人々が言うことから一つ、することから一つ、システムが記録することから一つの測定値を提案してください。数字を捏造しないでください。前提と、メモから分からなかったことを列挙してください。
```

**SLAと体験の間のギャップを見つける。**

```text
[期間] の [サービス] について、SLAの結果は次のとおりでした：[結果を貼り付け]。体験のデータ（パルスのスコア、コメントのテーマ、摩擦の件数）は次のとおりでした：[データを貼り付け]。二つが食い違う箇所を述べ、それぞれの食い違いにありうる三つの説明を挙げ、次に何を確認するかを提案してください。データが支えられない原因を仮定しないでください。前提と、助けになる追加のデータを列挙してください。
```

**行動の測定値のプライバシーの方法をレビューする。**

```text
体験の測定のために、次の行動のシグナルを集める予定です：[一覧]。ユーザーは [職員、一般市民、または両方] で、[法域または業種] です。プライバシー、信頼、公正さへのリスクについて計画をレビューし、最小限の集約、保持、開示の実践を提案してください。プライバシーの専門家に持ち込むべきことに印を付けてください。法的な結論を出さないでください。前提を列挙してください。
```

**ユーザーとの四半期ごとの体験レビューを準備する。**

```text
[ユーザーグループ] の代表との [サービス] の四半期ごとの体験レビューのための議題と1ページの要約を起案してください。SLAと体験の結果を並べて、上位のコメントのテーマ、先四半期のコミットメントとその状況、ユーザーへの二つの質問を含めてください。データ：[データを貼り付け]。トーンは平易にし、専門用語を避けてください。前提を列挙し、確認が必要な主張に印を付けてください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：体験の測定値をダッシュボードに加える前に、その防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：XLAのメトリクスの項目が、悪用の手口と防護柵を備えているかを確認するときに使います。

## 要点

- XLAは、運用の目標に体験の目標と測定値を加え、SLAを補完する。
- 体験の記述をユーザーとともに、彼らの言葉で書き、それぞれを、人々が言うこと、すること、システムが記録することの測定値に結び付ける。
- SLAと体験の結果を一緒に示し、食い違いを調査への促しとして扱う。
- ユーザーを守る：何を集めるかを開示し、集約し、小さなグループを抑制し、業績評価から外す。
- 単一の体験指数を避け、測定値が理解される前の硬い目標を避ける。
- データが明らかにする修正に資金を付け、何が変わったかをユーザーに伝える。
