# 第7部の導入：資産、構成、財務のメトリクス

**何を持ち、それがどう組み合わさり、いくらかかるかを知ることは、他のすべてのサービスの判断が立脚する土台である。それは、別個の雑用としてではなく、仕事の副産物として最新に保たれるのが最善である。**

サービスを提供し運営するチームは、モノについての事実に依存する判断を、週に何百も下します。この変更はどのサーバーに触れるか、来月どのライセンスが期限切れになるか、このクラウドアカウントは誰のものか、このサービスは顧客あたりいくらかかるか。それらの事実が間違っていたり欠けていたりすると、判断は推測です。資産、構成、財務の記録は、推測を情報に基づく選択に変えるために存在し、この部のメトリクスは、それらの記録がどれだけ良いか、どれだけうまく使われているかを問います。

アジャイルの実践とITILは、この領域に異なる方向から近づき、一緒のほうが強力です。ITILは、記録、オーナー、ライフサイクル、サービスの原価計算の規律をもたらします。アジャイルとDevOpsは、変更を継続的に届ける習慣と、コードとして記述されるインフラ、作ったものを登録できるパイプラインをもたらします。最良の結果は、デリバリーのパイプラインが記録を自動で供給し、調達、財務、セキュリティ、運用、エンジニアリングが、一つの共有された絵のまわりで継続的に協働するときに得られます。自分たちのサービスを所有し、信頼され、必要な情報を与えられたチームは、記録が間違っているときのコストを自分で感じるため、記録を真実に保ちます。

これらの記録はまた、水増ししやすいものです。棚卸しは、すでに知られているものしか列挙しないので、完璧に見えることがあります。コストの数字は、共有のコストが別の場所に配賦されたために低く見えることがあります。ビジネスケースは、便益が寛大に見積もられたために強く見えることがあります。したがって、この部の各メトリクスには、悪用される方法と、それ自体ではなく独立した証拠に照らして確認する防護柵が付いています（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。これらの測定値のいずれも、人やチームに順位を付けません。環境、サービス、判断を記述します。

四つのレンズは次のように当てはまります。継続的デリバリーとInfrastructure as Codeは、記録を仕事の副産物にします。AIサービス、モデル、利用量ベースのライセンスは、記録、オーナー、品質と組にしたユニットコストを必要とする資産とコストです。自動化は、ディスカバリーとコストの収集に供給し、自らもギャップについて測られなければなりません。アナリティクスは、抽出から正確さを、標本の日付と大きさとともに報告します。

## この部のトピック

- **7.1 IT資産管理のメトリクス**：棚卸しの正確さ、ディスカバリーの網羅率、突合、オーナーシップ、仕事が行われるときに取得される記録によるライフサイクルの完全性。
- **7.2 ソフトウェア資産とライセンスのメトリクス**：ライセンスの状況、利用率、シェルフウェア、乱立、更新の準備、ソフトウェア部品表。
- **7.3 ハードウェア資産ライフサイクルのメトリクス**：年齢構成、故障率、交換時間、利用率、安全な廃棄、再利用。
- **7.4 構成とCMDB品質のメトリクス**：完全性、正確さ、依存関係の網羅率、影響の予測、構成記録の利用。
- **7.5 サービスコストとユニットエコノミクス**：サービスあたりのコスト、ユニットコスト、配賦、ショーバック、継続するチームへの資金付け。
- **7.6 FinOpsとクラウドコストのメトリクス**：タグによる配賦、無駄、コミットメント、異常、予測の差異、排出量。
- **7.7 投資対効果とビジネスケース**：総所有コスト、見返り、回収期間、正味現在価値、過去の予測の正確さ。

## これらのトピックの相互関係

最初の四つのトピックは、モノそのものを記述します。資産の記録（トピック 7.1「IT資産管理のメトリクス」を参照）は、何が存在し、誰が所有するかを語ります。ソフトウェアとハードウェアのトピック（トピック 7.2「ソフトウェア資産とライセンスのメトリクス」とトピック 7.3「ハードウェア資産ライフサイクルのメトリクス」を参照）は、各クラスに固有のライフサイクルと義務を加えます。構成のトピック（トピック 7.4「構成とCMDB品質のメトリクス」を参照）は、何が何に依存するかを言えるよう、関係を加えます。それらは一つの方法を共有します。変更の瞬間に取得し、双方向に独立した証拠に照らして確認し、記録を真実に保てる小ささに保つ。

最後の三つのトピックは、モノがいくらかかり、そのコストに見合うかを記述します。サービスの原価計算（トピック 7.5「サービスコストとユニットエコノミクス」を参照）は、支出をサービスごと、単位ごとのコストに変え、コストを公正に帰属させるために資産と構成の記録に依存します。クラウドコストの実践（トピック 7.6「FinOpsとクラウドコストのメトリクス」を参照）は、支出が1時間ごとに変わり、タグが課金とオーナーを結ぶ場所に、同じ考え方を適用します。ビジネスケースのトピック（トピック 7.7「投資対効果とビジネスケース」を参照）は、これらすべてを使って投資の選択を行い、それらの選択を実際に起きたことと照らして確認するよう求めます。

いくつかの防護柵の組が導かれます。棚卸しの正確さの数字は、ギャップの一覧とオーナーのいない割合とともに読まれるべきです。ライセンスの利用率は、座席の回収が人々を苛立たせないよう、ユーザーのアクセス体験とともに読まれるべきです。コストの測定値は、節約がより悪いサービスで買われないよう、常に信頼性や満足度の測定値の隣に置くべきです（トピック 5.2「SLI、SLO、エラーバジェット」を参照）。ビジネスケースは、以前の予測の実績とともに読まれるべきです。

この部は、前後に結び付きます。第6部の便益の証拠（トピック 6.5「価値の実現とビジネス成果」を参照）が、ビジネスケースに供給されます。第8部のリスク、監査、供給者の測定値は、ここに記述された資産と契約の記録に依存します。第9部は、これらすべてを動かし続ける人々と、時間とともに記録をより良くする継続的改善の習慣に目を向けます。
