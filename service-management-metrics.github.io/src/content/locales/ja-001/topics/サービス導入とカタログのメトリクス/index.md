# サービス導入とカタログのメトリクス

**誰も選ばず、見つけず、リクエストを完了しないサービスは、価値を届けていない。したがって、人々が提供するものをどう見つけ、どう使うかを測り、カタログをバックログと同じくらい誠実に保つ。**

## 概要と動機

チームはサービスに投資し、それから人々が使っていないことを発見します。新しいセルフサービスポータルは電子メールで迂回されます。ソフトウェアアクセスのために丁寧に設計されたカタログアイテムは年に2件のリクエストしか得られず、月に100件がチャットで届きます。監視サービスが立ち上がり、対象とされたチームの半分が接続しません。導入は、デリバリーの欠けている半分です。サービスが価値を持つのは、意図したユーザーが使い始め、使い続け、使い終えるときだけです。

**サービスカタログ（service catalog）**（ITIL自身の綴りは"service catalogue"）は、組織が提供するサービスとリクエスト可能なアイテムの一覧で、ユーザーが理解できる言葉で記述されます。[サービスカタログ](https://en.wikipedia.org/wiki/Service_catalog)には通常、ユーザーが何をどのように依頼できるかを列挙する顧客向けのビューと、各サービスがどう構築、支援されているかを記録する技術的なビューがあります。アジャイルのチームには、その形がなじみ深いでしょう。カタログは一種の、逆向きの[プロダクトバックログ（product backlog）](https://en.wikipedia.org/wiki/Product_backlog)です。バックログは、作ろうとしているものを列挙します。カタログは、すでに提供しているものを列挙します。どちらも同じ注意を要します。順序付け、刈り込み、明確な言葉遣い、ユーザーからの絶え間ないフィードバックの流れ（トピック 2.6「バックログとリファインメントのメトリクス」を参照）。

**導入（adoption）**は、意図したユーザーがサービスを取り入れ、使い続ける程度です。新しい実践がどう広がるかの研究には長い歴史があります。[イノベーションの普及（diffusion of innovations）](https://en.wikipedia.org/wiki/Diffusion_of_innovations)の理論は、導入を、初期採用者、多数派、遅い採用者を伴う、時間にわたるプロセスとして記述します。社内サービスにとっての実際的な教訓は、導入が告知によって起きることはまれだということです。サービスが見つけやすく、使いやすく、回避策より明らかに優れているときに起きます。

導入の測定値は、目標に変えたくなるものです。チャネルを義務化すると、ユーザーが憤慨して回避策を築く間も、利用の数字は良く見えます。すべてのリクエストをカタログアイテムに押し込むと、カタログの網羅率は上がり、完了は下がります。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵が当てはまるので、ここの各測定値は、単なる利用ではなく、本当の価値が上がっていることの確認と組になっています（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

このトピックは四つのことを扱います。人々がサービスを使うか（導入）、来た目的を見つけて終えられるか（カタログとリクエストのフロー）、カタログが最新で誠実か（衛生）、利用が少数のアイテムに集中しているか（形）。リクエストが出された後に何が起きるかを扱う、リクエストの履行（トピック 3.5「サービスリクエスト履行のメトリクス」を参照）とセルフサービス（トピック 3.7「セルフサービスと自動化のメトリクス」を参照）に結び付きます。

## 主要な原則

- **導入は成果なので、ユーザーが何をしようとしていたかを尋ねる。** ページビューではなく、完了した目標を数える。
- **合計だけでなく、ファネルを測る。** 人々がどこで離脱するかが、何を直すかを教える。
- **代替手段と比較する。** サービスは、電子メール、チャット、電話、回避策と競合している。
- **カタログを可能な限り小さく、最新に保つ。** 古くなったアイテムは、ユーザーに探すのをやめさせる。
- **結論の前にセグメント化する。** すべてのユーザーにわたる平均は、サービスが機能しないグループを隠す。
- **数字を上げるために利用を強制してはならない。** 義務化は数字を生み、導入を生まない。
- **低い利用を、オーナーとユーザーへの問いとして扱う。** サービスが必要とされていないことを意味するかもしれない。

## 推奨事項

### サービスとユーザーを知る

**1. 各サービスの意図した対象者を定義する。** 導入を測る前に、サービスが誰のためのもので、なぜ代替手段の代わりにそれを使うのかを書き下します。財務スタッフのために作られた新しいアナリティクスサービスは、財務スタッフだけが使うはずだったのなら、「導入が低い」わけではありません。定義された対象者がなければ、導入率は誰についてでもない数字です。

**2. 代替手段を記録する。** 各主要サービスについて、それを使わないときに人々が今していることを列挙します。同僚に尋ねる、電子メールを送る、ツールを買う、スプレッドシートを動かす。代替手段を、重要な意味での競合として扱います。サービスがより難しいとき、ユーザーが行く先です。設計とレビューの間に、両方の経路の労力を比較します。

**3. アイテムをユーザーの言葉で記述する。** 「ソフトウェアアクセス（標準）」や「ノートパソコンの交換（破損）」のようなタイトルは、社内の名前より見つけやすいものです。数人のユーザーに短いシナリオからアイテムを見つけてもらうことでタイトルをテストします。言葉遣いの問題は、検索ログにすぐ現れます。

**4. すべてのアイテムにオーナーを置く。** 各カタログアイテムには、名前付きのオーナー、レビュー日、対象者の説明、期待される量があります。オーナーのいないアイテムは漂流します。誰がアイテムを、なぜ使うのかを誰も言えなければ、削除の候補です。

### 旅路を測る

**5. ファネルを計装する。** 各重要なサービスについて、発見から完了した成果までのステップを記録します。アイテムを見つける、リクエストを開始する、フォームに記入する、送信する、結果を受け取る。[コンバージョンファネル（conversion funnel）](https://en.wikipedia.org/wiki/Conversion_funnel)の見方は、ユーザーがどこで去るかを示します。最大の落ち込みを先に直します。修正が、データを見栄え良くするだけでなく、フォームを短く、あるいは明確にすることを確認します。

**6. コホートを使って継続を見る。** [コホート分析（cohort analysis）](https://en.wikipedia.org/wiki/Cohort_analysis)は、ユーザーを最初にサービスを使った時期でグループ化し、各グループを追跡します。ユーザーを保持するサービスと、一度だけ引きつけて失うサービスを分けます。サービスデスクのポータルやデプロイのパイプラインのような、繰り返し使われるべきサービスに使います。

**7. 検索ログから、人々が見つけられないものを読む。** 結果のない検索や、異なる言葉で繰り返される検索は、名前、内容、あるいはカタログそのもののギャップを指します。結果ゼロの上位の検索を毎月レビューし、それぞれについて決めます。アイテムの名前を変える、同義語を加える、記事を書く、新しいアイテムを作る。[ウェブ解析（web analytics）](https://en.wikipedia.org/wiki/Web_analytics)のツールがこれを供給でき、ポータル自身のログも同様です。

**8. グループ別にセグメント化する。** 合法的かつ倫理的にその情報にアクセスできるところでは、導入と放棄を、役割、場所、デバイス、アクセシビリティの必要性別に分解します。集約が健全に見えても、夜勤のスタッフやモバイルデバイスのユーザーが2倍の率で失敗しているかもしれません。人々を守るために小さなグループを抑制し、前のトピックの体験の測定値と組み合わせます（トピック 6.2「体験レベル合意」を参照）。

### カタログを誠実に保つ

**9. 予定に従って刈り込む。** 四半期ごとにカタログをレビューします。利用のないアイテムを削除または統合し、廃止されたサービスのアイテムを廃止し、放棄の高いアイテムを直します。小さく正確なカタログは、完全で古くなったものよりユーザーによく役立ちます。削除を通常のこととして扱い、理由を記録します。

**10. 需要の形を見る。** ほとんどのカタログでは、少数のアイテムがリクエストの大半を占め、このパターンはしばしば[パレートの法則（Pareto principle）](https://en.wikipedia.org/wiki/Pareto_principle)を通じて記述されます。それを使って、設計の労力を頻繁なアイテムに集中させ、定型的なものを自動化します（トピック 3.7「セルフサービスと自動化のメトリクス」を参照）。まれなアイテムはそれを必要とする人々にとって非常に重要でありうるので、見ずにロングテールを落としてはいけません。

**11. 導入を強制しない。** サービスが必要なら、簡単になればユーザーは来ます。統制や監査の理由で組織がチャネルを要求するところでは、そう述べ、その数字が好みではなくルールを反映していることを率直にします。電話番号を隠す、代替手段をより難しくするといった[ダークパターン（dark pattern）](https://en.wikipedia.org/wiki/Dark_pattern)は、利用を上げて信頼を下げるので避けます。

**12. オーナーとユーザーとの輪を閉じる。** ファネル、検索のギャップ、古くなった一覧を、毎月アイテムのオーナーと共有します。アンケートとレビューで、ユーザーになぜサービスを使うか、避けるかを尋ねます（トピック 6.1「顧客満足度のメトリクス」を参照）。何を変えたかを台帳に記録し、それが起きたことをユーザーに伝えます。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 導入率 | 利用を義務化する、ログインやページビューを利用として数える、すでに使っている人に「対象ユーザー」を狭める | 完了した成果の定義。満足度と労力の評価と比較する。対象ユーザーの規則を公開する |
| アクティブな利用率 | ユーザーがアクティブに見えるよう自動登録する、活動として数えられる通知を送る | ユーザーが始めた完了した行動のみを数える。離脱したユーザーへのインタビューの抽出 |
| カタログの網羅率 | すべてのリクエストを汎用のカタログアイテムに押し込む、電子メールのリクエストを「ポータルをご利用ください」でクローズする | リクエストの放棄率と満足度。別のチャネルで再度出されるリクエストの数を数える |
| リクエストの放棄率 | 必要なフォームの項目を取り除いて、作業を履行に移す、長い窓の後にだけ放棄されたリクエストを数える | 履行での手戻りと確認の率（トピック 3.5「サービスリクエスト履行のメトリクス」を参照） |
| 検索の成功率 | あらゆるクリックを成功として数える、すべてのクエリに一致する無関係な記事を加える | 結果が使われたことを確認する（リクエストが出された、記事が役に立つと評価された）。結果ゼロの検索を読む |
| 古くなったアイテムの割合 | 読まずにアイテムをレビュー済みとする、レビュー日を一括でリセットする | レビューされたアイテムの正確さを抽出する。最後の本当の変更日を示す |
| リクエストの集中 | 人気のアイテムを多数に分割する、ロングテールの需要を隠すために無関係なアイテムを統合する | 変更履歴を伴う固定のアイテム分類。区分別にテールを見る |

健全な読みは、最も使われるアイテムがうまく機能して容易になりつつあり、ユーザーが代替手段より優れているからサービスを選び、アイテムの廃止が日常的なカタログです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| 義務化されたチャネル | 予測可能な量、監査しやすい | 憤慨、回避策、水増しされた数字 |
| 自発的な導入 | 価値の誠実なシグナル | より遅い。一部のサービスは決して導入されないかもしれない |
| 大きなカタログ | 完全で、まれな必要をカバーする | 検索しにくい。古くなる |
| 小さなカタログ | 見つけやすく維持しやすい | まれな必要が外れる。ユーザーが電子メールに頼る |
| ファネルの測定値 | ユーザーがどこで離脱するかを特定する | 計装が要る。成果を犠牲にしてフォームを最適化することを促しうる |
| 理由を尋ねるアンケート | 行動を説明する | 誰が答えるかで偏る。スケールしにくい |

散文での答えは、明確な品質上の優位に裏付けられた自発的な導入を優先し、統制やコンプライアンスが要求するところでのみ義務化を使い、数字にそのようにラベルを付けることです。カタログを維持できるだけ小さく保ち、テールを、百の半端に使われるアイテムではなく、検索できるナレッジベースに置きます。

## チームで話し合う問い

**1. 主なサービスはそれぞれ誰のためのものか、使っているかをどうやって知るか？**
チームが最も時間を使う五つのサービスを列挙し、それぞれの意図した対象者を書きます。それから、それらの導入をどう測れるかを尋ねます。ファシリテーターは、誰も対象者に名前を挙げられないサービスを探してください。それらは導入計画を持たない可能性が高いからです。

**2. 私たちのサービスを使わないとき、人々は何をしていて、なぜか？**
導入の低いサービスを一つ選び、それを避けるユーザー数人にインタビューまたはアンケートをします。代替手段は通常、示唆に富みます。より速い、より慣れている、より柔軟かもしれません。サービスを改善するか、代替手段を変えるか、サービスが必要ないことを受け入れるかを決めます。

**3. 最もリクエストされるアイテムで、ユーザーはどこで離脱するか？**
最初の閲覧から送信まで、上位のアイテムのファネルを示します。チームに最大の落ち込みがどこかを推測してもらい、それから比較します。試す変更を一つ合意し、問題を別の場所に動かさずに、それが役立ったかをどう確認するかを述べます。

**4. 思い切れるなら、カタログから何を削除するか？**
1年間リクエストのないアイテムの一覧を印刷します。それぞれが消えたら何が起きるかを尋ねます。対話は、アイテムが、誰かがかつて頼んだから存在することをしばしば見いだします。最初の五つを削除または統合する日付と、ユーザーへのメモに合意します。

**5. ユーザーを誘導したり強制したりしているのはどこで、そのコストに見合うか？**
ルールや設計がユーザーをチャネルに押し込んでいるすべての場所を列挙します。どれが本当に必要で、どれが習慣かを尋ねます。ファシリテーターは、ユーザーがそれぞれをどう体験しているか、結果の数字がリーダーの考えることを意味しているかを探ってください。

**6. 人々が検索しているのに、私たちが持っていないものは何か？**
結果ゼロの上位の検索をレビューします。それぞれについて、アイテムを加えるか、記事を書くか、サービスが存在しないことを説明するかを決めます。このレビューを誰が所有し、どのくらいの頻度で行うかを尋ねます。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、意味を持つために導入を必要とするサービスと機能を作ります。最初に対象者を定義し、利用の測定値をサービスに組み込み、立ち上げ後にファネルをレビューするべきです。導入のデータは仕事へのフィードバックであり、リファインメントとレビューに属します。チームは、出荷されたときにリリースが完了したと宣言するのを避けるべきです。完了とは、意図したユーザーが便益を得ていることを意味します。

### サービスと運用のチーム

運用チームはカタログを運営し、あらゆるチャネルで届くリクエストを見ます。カタログを最新に保ち、それを迂回するリクエストにタグを付け、理由を尋ねるべきです。リクエストをリダイレクトしてクローズしてはいけません。シグナルを隠すからです。検索のギャップと放棄は、ポータルの改善の最良の源です。

### リーダーシップとガバナンス

リーダーは、導入が対話かノルマかを決めます。サービスが何のためのもので、誰を助け、なぜ人々がそれを選ぶのかを問うべきです。個々のチームへの導入の目標を設定するのを避け、使われないサービスの廃止を支え、導入が満足度と労力と並んで示されることを期待するべきです。義務化が正当化されるところでは、リーダーはそれをユーザーに説明するべきです。

### 顧客とユーザー

ユーザーは、わずかな労力で必要なものを得たいと思っています。彼らは、ポータルが検索しにくいとき、フォームが組織がすでに知っていることを尋ねるとき、古い方法のほうが速いときに気づきます。彼らの行動と言うことが、最も誠実な導入のシグナルです。サービスをなぜ避けるかを尋ねられ、その結果何が変わったかを伝えられるべきです。

## 実践：サービスマネジメントの例

国の交通機関のIT部門が、サービスデスク、約140アイテムのカタログを持つセルフサービスポータル、いくつかのプロダクトチームを運営しています。以下の数字は例示です。

ポータルは1年前に立ち上がり、リーダーシップはリクエストの80パーセントをそれ経由とする目標を設定しました。月次のレポートは78パーセントの網羅率を示し、サービスマネジメントの責任者は、ユーザーアンケートのコメントを読むまで満足していました。地方事務所のスタッフは、ポータルが遅く、フォームが長いと言っています。彼女はカタログの管理者に、ファネルと検索ログを見るよう頼みます。

「新入社員の機器」のファネルは、四半期に1,100件の開始と640件の送信、放棄率42パーセントを示します。フォームには23の項目があります。検索ログは、「ノートパソコン」という語が八つのアイテムを返し、「VPN」という語が、最も検索された語であるのに何も返さないことを示します。140のカタログアイテムのうち、38は12か月間リクエストがなく、21はレビュー日を過ぎています。上位五つのアイテムがリクエストの61パーセントを占め、さらに15パーセントのリクエストが電子メールで届き、手作業で記録されています。

チームは四つの変更を行います。人事システムがすでに持つデータを使って、新入社員のフォームを9項目に削減する。VPNの記事と、同義語を持つアイテムを加える。八つのノートパソコンのアイテムを二つに統合する。そして、使われていないアイテムのうち19を、オーナーへのメモとともに廃止する。また、月次のレポートの読み方も変えます。網羅率は、放棄率とアンケートの質問「必要なものを得るのはどれだけ容易でしたか？」とともに示されます。三か月後、新入社員アイテムの放棄は24パーセントに下がり、ポータルの網羅率は74パーセントになり、地方事務所からの労力の評価が上がります。責任者は、なぜ網羅率が下がったのかを尋ねます。サービスマネジメントの責任者は、以前は電子メールのリクエストが強制的にクローズされていたこと、そして低い数字のほうがより誠実で、体験が良くなっていることを説明します。判断ログは、目標が方向に置き換えられたことを記録します。放棄を減らし、労力の評価を上げる。網羅率はレビューされるが、目標にはしない。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

カタログを、ユーザーとともにリファインされるバックログとして扱い、誰も使わないアイテムを削除します。注意点は、カタログのアイテム数の目標は、乱雑さを加えることです。

### AI

AI検索とアシスタントは、人々がサービスを見つける方法を変え、それが導入と放棄の数字を動かします。検索の成功を、放棄率と、AIの提案のうち受け入れられて完了した割合と組にします。注意点は、モデルがその人がリクエストできないサービスを推奨しうるため、適格性の規則を確認することです。

### 自動化

検索、閲覧、リクエストのイベントを自動で取得し、古くなったカタログアイテムを人の判断のためにフラグ付けします。履行の自動化を失敗率で測ります。注意点は、アイテムを取り除く自動の整理が、人々がまれに、しかし必要とするサービスを隠しうることです。

### アナリティクス

導入と放棄をカタログアイテム別に件数とともに、そしてリクエストの集中を示します。これが情報を与える判断は、どのアイテムを再設計または廃止するかです。注意点は、少量のアイテムの率はノイズが多いことです。

## 業種別の視点

**スタートアップ。** カタログがないことがよくあります。「Xを入手する方法」の単純なページと共有チャネルで十分です。人々が何を頼むかを見て、上位五つのリクエストを短いガイドに変えます。ユーザーに尋ねて社内ツールの導入を測り、正式なファネルは省きます。

**中小企業。** ITを提供する人は少なく、リクエストはあらゆるチャネルから届きます。10から20アイテムの控えめなカタログが、ほとんどの必要をカバーします。扱うリクエストより維持にコストのかかるポータルに、ユーザーを強制してはいけません。年に二度、一覧をレビューします。

**大企業。** 規模は、ガバナンスが要るほど大きなカタログをもたらします。オーナー、レビュー日、分類。導入を事業部門とリージョン別にセグメント化し、現地の必要を無視する企業全体の義務化を避けます。カタログアイテムが数えられても使われていない供給者に注意します。

**政府・公共部門。** サービスは職員だけでなく一般市民にも届き、アクセシビリティ、言語、平等なアクセスについての義務があります。デジタルの導入が排除を隠さないよう、支援されたチャネル（電話、対面）を測定値に含めます。法律や方針の規則がチャネルを要求するところでは、レポートにそう述べます（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは控えめです。利用ログとリクエストのデータは通常すでに存在します。ファネルと検索の分析には、ほとんどの基盤が提供するポータルのアナリティクスへのアクセスが要ります。主な時間のコストは、四半期ごとのカタログのレビューと、検索のギャップと離脱の毎月の確認で、それぞれ数時間です。フォームの修正とアイテムの統合には、設計と設定の時間がかかります。

見返りは、使われるサービス、完了するリクエスト、履行での無駄の減少から来ます。放棄を削減する短いフォームは、繰り返しの問い合わせと手作業の処理を減らします。使われていないアイテムの刈り込みは、保守を減らします。自分たちの数字からケースを築きます。放棄率、電子メールで届いたリクエストあたりの手作業の処理時間、使われていないアイテムを維持するコストを、変更の前後で。ポータルのROIについての、たどれない公表された主張は避けてください。組織と方法に依存するからです。

## アンチパターンと落とし穴

- **立ち上げを導入として数える。** サービスが導入されたのは、意図したユーザーがそれで成果を完了したときである。告知ではなく、利用を測る。
- **数字を上げるためにチャネルを義務化する。** ユーザーはそれを回避する。サービスを改善し、数字が後に続くようにする。
- **アイテムを加えて、一つも削除しない。** カタログが検索不能になる。四半期ごとに刈り込む。
- **合計だけを見る。** グループ別にセグメント化し、ファネルを見る。
- **電子メールのリクエストをリダイレクトでクローズする。** 需要を隠し、ユーザーを苛立たせる。リクエストを処理し、経路を直す。
- **ページビューを利用として使う。** 完了した成果を数える。
- **低い利用を、ユーザーの失敗として扱う。** サービスが必要で使いやすいかを問う。
- **アイテムのオーナーを失効させる。** すべてのアイテムにオーナーとレビュー日を割り当てる。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| カタログの設計 | 依頼によって育った一覧 | カタログはあるが、言葉遣いが一貫しない | オーナーとレビュー日を持つ、ユーザーの言葉のアイテム | 四半期ごとの刈り込み。分類が管理される | カタログがチームと供給者の間で共有され、アイテムがユーザーと共同設計される |
| 導入の測定 | 逸話 | アイテム別のリクエスト数 | 対象ユーザーと完了した成果で定義された導入 | ファネル、コホート、セグメントが毎月レビューされる | 導入が、サービスにまたがって体験と成果に結び付く |
| 改善 | アドホックな修正 | 苦情の後の修正 | 検索のギャップと離脱が毎月レビューされる | 修正が優先順位付けされ、バックログで追跡される | 改善がユーザーとともに調整され、廃止されたサービスが公然と報告される |

## チェックリスト

- [ ] 各主要サービスに、書面の意図した対象者と代替の経路がある。
- [ ] 導入が、対象ユーザーによる完了した成果として定義されている。
- [ ] カタログアイテムに、オーナー、ユーザーの言葉の説明、レビュー日がある。
- [ ] 最もリクエストされるアイテムのファネルが計装されている。
- [ ] 結果ゼロの検索が毎月レビューされている。
- [ ] 導入と放棄がグループ別にセグメント化され、小さなグループが抑制されている。
- [ ] カタログの外で届くリクエストがタグ付けされ、数えられている。
- [ ] カタログが四半期ごとに刈り込まれ、理由が記録されている。
- [ ] 導入が満足度または労力の測定値の隣に示されている。
- [ ] 個々のチームや人に導入の目標が設定されていない。

## AIプロンプト

**リクエストのファネルを分析する。**

```text
[組織の種類] のカタログアイテム [アイテム名] について、[期間] のポータルのデータは次のとおりです：閲覧 [数]、開始 [数]、送信 [数]、履行 [数]。フォームには [数] 個の項目があります：[一覧]。ユーザーがどこでつまずきやすいかを述べ、試す三つの変更を提案し、問題を履行に動かさずに、各変更が役立ったかをどう確認するかを述べてください。ベンチマークの値を捏造しないでください。前提と、必要な追加のデータを列挙してください。
```

**検索ログをカタログのギャップについてレビューする。**

```text
以下は [期間] の上位 [数] 件のカタログ検索と結果の件数です：[データを貼り付け]。それらをテーマにグループ化し、何も返さない、または多すぎるアイテムを返す検索に印を付け、それぞれが新しいアイテム、名前の変更、同義語、ナレッジ記事のどれを必要とするかを提案してください。私たちが提供していないかもしれないサービスについて推測しないでください。前提と、アイテムのオーナーに尋ねるべき問いを列挙してください。
```

**カタログの刈り込みレビューを計画する。**

```text
[数] 件のアイテムのカタログを管理しています。これらのアイテムそれぞれについて、12か月のリクエスト数、レビュー日、オーナーがあります：[要約を貼り付け]。アイテムを削除、統合、維持する基準、オーナーへの短いメモ、まれだが重要なアイテムを落とさない方法を提案してください。単にリクエストを電子メールに移していないことの確認を含めてください。前提を列挙してください。
```

**サービスの導入の定義を起案する。**

```text
サービス：[名前]。意図したユーザー：[役割]。今日の代替の経路：[今していること]。対象ユーザー、何が完了した利用に数えられるか、データソース、テストと自動化されたトラフィックの除外方法、測定値がどう悪用されうるか、防護柵をカバーする1ページの導入の定義を起案してください。目標を捏造しないでください。前提と、私が確認すべきことを列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：導入またはカタログのメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：新しいカタログのメトリクスの項目に、悪用の手口と防護柵があるかを確認するときに使います。

## 要点

- 導入とは、意図したユーザーがサービスで成果を完了することなので、対象者を定義し、完了を数える。
- ファネル、検索のギャップ、ユーザーの継続を測り、グループ別にセグメント化する。
- サービスを、ユーザーが今日持つ代替手段と比較する。
- カタログを小さく、オーナーがおり、四半期ごとに刈り込まれた状態に保つ。
- 数字を上げるために利用を強制せず、導入を満足度と労力と組にする。
- 低い利用を、必要性と容易さについての問いとして扱い、ユーザーの失敗としては扱わない。
