# サービスデスクのメトリクス

**サービスデスクは、人々が仕事に戻れるようどれだけ助けているか、組織の他の部分にどれだけ学びを提供しているかで測る。電話の件数や通話の分数は、そのどちらをも犠牲にして、速さと量を報いてしまうからだ。**

## 概要と動機

ほとんどのユーザーにとって、サービスデスクこそがサービスです。エンジニアに会うこともパイプラインを見ることもめったになく、何かがうまくいかないときに答えてくれる人に会います。[ヘルプデスク（help desk）](https://en.wikipedia.org/wiki/Help_desk)とは、通常はコンピューターの問題について、支援と情報を提供する部署または人です。[ITサービスマネジメント（IT service management、ITSM）](https://en.wikipedia.org/wiki/IT_service_management)の用法では、サービスデスクは提供者とそのユーザーとの間の単一の窓口で、インシデント（サービスに対する計画外の中断または中断の可能性）とサービスリクエスト（サービスが通常提供するものに対する日常的なリクエスト）の両方を扱います。[ITIL](https://en.wikipedia.org/wiki/ITIL) 4では、サービスデスクのプラクティスはインシデント管理とサービスリクエスト管理の隣に位置し、固定された測定値の一覧ではなく、その目的と成果によって記述されます。したがってこのトピックは、フレームワークの要件ではなく、実際的な指針を提供します。

デスクの周りで育った測定値は、主に[コールセンター（call center）](https://en.wikipedia.org/wiki/Call_centre)の伝統に由来します。いくつの問い合わせが届いたか、人々がどのくらい待ったか、いくつが諦めたか、各問い合わせにどのくらいかかったか、いくつが最初の試みで解決されたか。それらの測定値は有用で安価ですが、本書の中でサービスを損なう目標に最も変えやすいものでもあります。短い通話は、同じユーザーが三回かけ直すまでは効率的に見えます。低い放棄率は、エージェントが素早く答えて何も解決しないまでは、思いやりがあるように見えます。このトピックの仕事は、各測定値を記述し、その時計を述べ、それが何を報い、何を隠すかを述べることです。

アジャイルの見方は、第二の目的を加えます。すべての問い合わせは、ユーザーが何を分かりにくいと感じ、何が壊れ、サービスに何をしてほしいと願っているかについての証拠です。頻繁にリリースするアジャイルのチームには、その証拠が、チケットではなくサービスの水準で、素早く必要です。そのためデスクは二度測られます。人々にうまく応答する運営として、またバックログに供給するセンサーとして。量は両者の橋渡しです。件数の増加は、成長、悪いリリース、欠けている記事、新しいチャネルを意味しえて、メトリクスだけではどれかを言えません（区分と優先度別の件数の読み方は、トピック 3.2「インシデントの件数と優先度」を参照）。

重要な用語です。[初回通話での解決（first-call resolution）](https://en.wikipedia.org/wiki/First_call_resolution)は、最初の問い合わせで解決された問い合わせの割合です。[自動着信呼分配装置（automatic call distributor）](https://en.wikipedia.org/wiki/Automatic_call_distributor)は、着信を利用可能なスタッフに振り分けます。[サービスレベルアグリーメント（service-level agreement、SLA）](https://en.wikipedia.org/wiki/Service-level_agreement)は、提供者と顧客の間のコミットメントです。[パーセンタイル（percentile）](https://en.wikipedia.org/wiki/Percentile)は、観測値の与えられた割合がそれを下回る値なので、処理時間の85パーセンタイルは、問い合わせの85パーセントがそれ以内に終わる所要時間です。そして[顧客満足度（customer satisfaction）](https://en.wikipedia.org/wiki/Customer_satisfaction)（トピック 6.1「顧客満足度のメトリクス」を参照）は、サービスがユーザーの期待をどれだけ満たすかです。

「問い合わせ（contact）」と「チケット（ticket）」という用語は同じではありません。問い合わせとは、電話、チャット、メール、ポータル、窓口、メッセージングなどのチャネルを通じて、人がデスクに連絡しようとする一回の試みです。チケット（レコードとも呼ばれる）は、ITSMツールが仕事を追跡するために作成するものです。一つのチケットに多くの問い合わせが関わることがあり、その場で答えられるパスワードのリセットのように、記録のためだけにチケットを作る問い合わせもあります。この二つを混ぜることが、デスクのレポートで最もよくある混乱の原因なので、以下の定義はこの二つを別に数えます。

## 主要な原則

- **問い合わせとチケットを別に数え、両方を定義する。** 問い合わせはデスクに連絡しようとする試みで、チケットは仕事の記録である。それらを混ぜたレポートは、突合できない。
- **時間は分布として報告する。** 平均だけでなく、中央値と85または95パーセンタイルのような高いパーセンタイルを示す。ごく長い、あるいはごく短い少数の問い合わせが平均をゆがめるからだ。
- **すべての速さの測定値を、アウトカムの測定値と組にする。** 応答の速さ、放棄、処理時間は労力を記述する。解決と再問い合わせは、ユーザーが助けられたかを記述する。
- **量を利用状況に対して正規化する。** ユーザー数が増えたために増えた件数は、ユーザーあたりで増えた件数とは別の話である。
- **チャネルとサービスを測り、人は測らない。** これらのメトリクスは、デスク、キュー、サービス、チャネルを記述する。個々のエージェントに順位を付けたり、懲戒したりするためには決して使わない。
- **デスクをセンサーとして扱う。** 各メトリクスは、上流で何を直し、文書化し、自動化するかについて、デリバリーのチームへの問いにつながるべきである。

## 推奨事項

### 最初から問い合わせとチケットを分ける

**問い合わせとチケットに、それぞれ独自の定義、識別子、件数を与える。** 問い合わせはデスクに連絡しようとした試みの記録で、チケットは仕事の記録です。同じ件についての再問い合わせが見えるよう、ツールでそれらを紐づけます。二つを混ぜたレポートは、電話のプラットフォームと突合できない量の数字を与えます。

### 量を、チャネル、区分、正規化した率で報告する

**総量、チャネル別の量、区分別の量、100ユーザーあたりの問い合わせ率を示す。** 総量だけでは、成長とトラブルが混同されます。電話の量の低下はチャットへの移行かもしれず、ポータルの問い合わせの増加は、セルフサービスの意図した成功かもしれません。学期の始まりや会計年度末のような季節性が見えるよう、少なくとも一年にわたって系列をプロットします。

### すべての時間の測定値に分布を使う

**応答までの時間と処理時間について、中央値と高いパーセンタイルを報告する。** 偏った分布の平均は、ほとんど誰の体験も記述しません。中央値は典型的な問い合わせを示し、85または95パーセンタイルは遅い裾がどれだけ悪いかを示します。その数字が何件の問い合わせに基づくかを述べ、期間内にキューがごく少数の問い合わせしか扱わなかったときは、その読みを信頼できないものと印してください（トピック 1.6「サービスメトリクスのための統計リテラシー」を参照）。

### 放棄を需要と人員配置のシグナルとして扱う

**放棄を、応答までの時間と到着パターンと併せて読む。** 人々は、待ちが期待より長いと諦めるので、率は待ちとともに上がり、待ちは到着がキャパシティを超えると上がります。[待ち行列理論（queueing theory）](https://en.wikipedia.org/wiki/Queueing_theory)は、キューが満稼働に近づくと待ちが急激に増える理由を説明しており、100パーセント近く忙しく運営されるデスクが常に長い待ちと高い放棄を持つ理由です。月次の平均ではなく、時間帯と曜日ごとの到着パターンに合わせて人員を配置し、放棄を時間帯別に示します（トピック 2.3「仕掛かり作業と待ち行列」を参照）。

### 初回問い合わせでの解決を慎重に定義し、ユーザーの側から測る

**再問い合わせに基づく定義を使い、ユーザーへの短い質問で確認する。** 述べた窓内に戻ってこない問い合わせだけを数えるほうが、クローズ時にエージェントが立てるフラグよりも水増ししにくくなります。「問題は解決しましたか？」のような一問の確認を加え、再問い合わせの数字と比較します。両者が食い違うときは、ユーザーの答えのほうがよい指針で、そのギャップはクローズが早すぎる箇所を指し示します。

### 処理時間は計画に使い、目標には使わない

**処理時間を、キャパシティの入力と診断として扱い、エージェントが超えるべき目標は決して設定しない。** 処理時間の目標は、急ぐこと、早期の引き継ぎ、薄い記録に報酬を払います。問い合わせの種類別の分布を、人員配置の計画と、似たものよりはるかに長くかかる問い合わせを見つけるために使います。それは、欠けている記事、扱いにくいツール、不明確なプロセスを指し示すことがよくあります。エージェントではなく、システムの原因を狙ってください。

### デスクのメトリクスをデリバリーの仕事に結び付ける

**問い合わせの上位の区分を、サービスを所有するチームとレビューする。** 毎月、100ユーザーあたりで最も多くの問い合わせを生んだ五つの区分を取り、上流でどんな変更がそれらを取り除くかを尋ねます。修正、記事、より良いエラーメッセージ、セルフサービスの経路。答えを、所有するチームのバックログに記録します。これにより、デスクの数字が改善の仕事に変わり、データの最も明確なアジャイル的な使い方になります（トピック 3.6「ナレッジマネジメントのメトリクス」とトピック 3.7「セルフサービスと自動化のメトリクス」を参照）。

### すべてのチャネルを同じ定義に含める

**電話、チャット、メール、ポータル、窓口、メッセージングに、同じ時計と数え方の規則を適用する。** 非同期のチャネルにはライブのキューがないので、応答までの時間は、それぞれで意味が異なります。チャネルごとに時計を定義し、組み合わせる前に、それぞれを別に報告します。最良のチャネルだけを公開するデスクは、他のすべての人々の体験を隠します。

### メトリクスをユーザーの体験に結び付ける

**運用の測定値を、問い合わせ後の満足度の質問と自由記述の促しと組にする。** 無礼な、あるいは役に立たない問い合わせへの速い応答は悪い結果であり、時計にはそれが見えません。ユーザーのうち自己選択した一部しか返信しないため、点数の隣に回答率と回答者の構成を示します（トピック 1.5「データソースと計装」を参照）。コメントは、問い合わせに答える人々とともに、チームの場で読みます。

### メトリクスをチームとキューのレベルに保つ

**キュー、チャネル、サービス、チームごとに報告し、個々のエージェントのデータは、エージェント本人が参加するコーチングの対話のために保つ。** 処理時間や解決率で個々のエージェントに順位を付けると、簡単な問い合わせの選り好みと、難しいものの回避を促します。また、データへの信頼を損ない、ユーザーはその結果を助けの質として感じます。チームレベルの数字を、システムが何を必要としているかを問うために使います。

| 初回問い合わせでの解決率 | 結果にかかわらず通話中にチケットをクローズする、「同じ件」を狭く読む、難しい問い合わせを「解決を期待されない」と分類する | 再問い合わせ率、ユーザーによる一問の確認、チームによる除外の定期的な監査 |

健全な読みとは、互いに一致する数字の集合です。応答までの時間と放棄は一緒に動き、処理時間はその日の目標ではなく問い合わせの種類によって変わり、初回問い合わせでの解決と再問い合わせは、その上限付近で合計される鏡像であり、「問題は解決しましたか？」へのユーザーの答えが再問い合わせの数字と一致します。他が横ばいのまま一つの数字が急に改善したときは、祝う前に、それがどう集められているかを調べる理由です。悪用されたデスクは、通常、再問い合わせ、量における繰り返される区分、増える苦情にその症状を示します。

| 見出しとしての平均処理時間 | 単純で、あらゆるプラットフォームにあり、説明しやすい | 急ぐことを報い、裾を隠し、解決を損なう目標を招く |
| 時間の測定値に中央値と85パーセンタイル | 典型的な事例と遅い裾を記述する | 安定するだけの問い合わせ数と、少しの説明が必要 |
| エージェントのクローズフラグによる初回問い合わせでの解決 | 集めやすい | 水増ししやすく、デスク間で比較しにくい |
| 再問い合わせの窓による初回問い合わせでの解決 | 悪用しにくく、ユーザーの体験に近い | ツールでの良好な紐づけと、報告できるようになる前に窓が過ぎるのを待つことが必要 |
| 猶予期間付きの放棄 | 偶発的な切断を取り除く | 猶予期間は、数字を良く見せるために延ばせる |
| 100ユーザーあたりの問い合わせ率 | 成長とトラブルを分ける | 信頼できるユーザー数と、「アクティブ」の明確な定義に依存する |
| 問い合わせ後のアンケート | 時計にはとらえられないものをとらえる | 回答率が低く不均一で、強い感情を持つユーザーに偏る |
| チームとキューのみでの報告 | 信頼を守り、システムに焦点を当てる | 個人のコーチングには詳細が少ない。これには別の、非公開のプロセスが要る |

どんな測定値の集合も、速さと丁寧さの間の緊張を取り除きません。すべての問い合わせに数秒で答えて何も解決しないデスクは、キューは良いがサービスは貧弱で、きちんと解決するために時間をかけるデスクは、処理時間も待ちも長く見えます。通り抜ける道は、今四半期に最も重要なアウトカムに合意し、トレードオフを明示し、それをバランスさせる測定値の組をレビューすることです。速いことが良いのは、解決が保たれている間だけです。

## チームで話し合う問い

**1. ここでの「問い合わせ」とは何を意味し、私たちの数は、電話のプラットフォームとITSMツールがそれぞれ報告するものと一致しているか？**
グループに、一日分の問い合わせをすべてのチャネルでたどり、二つのシステムの件数を比較してもらいます。チケットにならない問い合わせと、問い合わせとして始まらないチケットを記録します。ファシリテーターは、最初はギャップがあることを想定し、それを人々の過失ではなく、定義についての発見として扱ってください。次のレポートの規則と、それを誰が所有するかに合意します。

**2. 問い合わせが初回で解決されたと言うとき、ユーザーが同意するだろうとどうやって知るか？**
初回問い合わせでの解決と印が付いた最近の問い合わせを十件レビューし、ユーザーのうち同じ件で戻ってきた人がいないかを確認します。戻ってきたものについて、エージェントが違ってできたことは何かを尋ねます。この議論は、通常、ユーザーの準備ができる前にクローズされる箇所を示します。一問の確認を加えるか、再問い合わせの窓をどうするかを決めます。

**3. 保留中の人には何が起きていて、いつ諦めるのか？**
待った時間別の放棄の曲線を見ます。ほとんどのデスクは、それを超えると人が大量に去る点を見つけ、その点がキューの実用上の限界です。どんなコールバック、チャット、自動応答が提供されているか、問題が解決されていないのに応答済みとして数えられているものがないかを尋ねます。ファシリテーターは、これを、月次ではなく時間帯ごとの人員配置についての議論を開くのに使えます。

**4. 問い合わせ後の作業と待ちに注意を払ったら、処理時間の数字のどれが変わるか？**
時計が何を含み、何を除くかを列挙します。通話を短くする圧力を感じた人がいないか、そのとき何をしたかを尋ねます。この問いは、レポートよりチームの中のほうが答えやすいので、人々が帰属なしに話せる機会を与えます。定義と、処理時間を計画のためだけに使うかどうかに合意します。

**5. 先四半期に100ユーザーあたりで最も多くの問い合わせを生んだ五つの区分はどれで、それぞれの修正を誰が所有するか？**
区分のデータと、基盤となるサービスのオーナーを同じ席に持ち寄ります。各区分について、最善の対応が、修正、記事、より良いメッセージ、セルフサービスの経路のどれかを尋ねます。ポイントは、バックログにアイテムと名前付きのオーナーを持って帰ることです。次の四半期に一覧を見直し、どれが動いたかを確認します。

**6. これをチームとキューのレベルで報告していて、誰かがそれで個人を比較していないか？**
これらの数字のどれかが人を判断するのに使われたか、その影響は何だったかを、グループに直接尋ねます。個人の比較がなくなったら、デスクが何をやめ、何を始めるかを話し合います。ファシリテーターは、あらゆる例を記録し、方針についての判断のため、メトリクスのオーナーに持ち込んでください。狙いは、データがシステムを記述するという書面の約束です。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、デスクから自分たちのサービスの最良の見方を得ます。リリース後の100ユーザーあたりの問い合わせは、変更が人々を混乱させたかを素早く示し、区分は次に何を直すかを示します。チームは、上位の区分の月次レビューを想定し、それをバックログの入力として扱うべきで、ユーザーが伝えたことを報告したデスクに非難は付きません。件数に加えて問い合わせの抽出もデスクに求めてください。ユーザーが使う言葉は、ラベル付けや設計の問題をしばしば明らかにするからです。

### サービスと運用のチーム

デスクのスタッフとそのリーダーには、目標になることなく、計画と改善を助ける数字が必要です。到着パターンからの時間帯ごとの人員配置、再問い合わせのレビュー、記事の要望が、最も有用なアウトプットです。時計がどこで誤解を招くかを知っているので、スタッフにはメトリクスの定義の仕方に意見を言う権利があるべきです。自分のチームの数字を最初に見て、それに異議を唱えられるべきです。

### リーダーシップとガバナンス

リーダーに必要なのは、互いに一致する短い数字の集合です。量と問い合わせ率、応答までの時間と放棄、初回問い合わせでの解決と再問い合わせ、そして回答率付きのユーザー満足度のスコア。分布と定義変更の注記を求め、処理時間や量に単一の目標を設定することには抵抗するべきです。速さだけに置いた目標は、上述の悪用を招きます。ガバナンスは、各定義を誰が所有するかを記録するべきです（トピック 1.4「メトリクスのガバナンスとオーナーシップ」を参照）。

### 顧客とユーザー

ユーザーが気にするのは、つながったか、きちんと扱われたか、問題が直ったままかです。処理時間は気にしません。デスクが何を測っているかを伝え、彼らのフィードバックに基づいて行動することは信頼を築き、彼らが好むチャネルが測られ、人員配置されていることを確かめることもそうです。サービスを購入する顧客は、SLAや体験に関する合意の明確なコミットメントによって支えられます（トピック 5.1「SLA、OLA、XLAのメトリクス」とトピック 6.2「体験レベル合意」を参照）。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

デスクのフィードバックを、継続的改善の入力として扱います。上位の問い合わせの理由のステークホルダーとの定期的なレビューと、原因を取り除く変更を一つ。注意点は、処理時間の目標がエージェントに急ぐことを促すため、個人の評価に使わないことです。

### AI

AIによるトリアージと起案された返信は、人に届くものを変えながら、応答までの時間と処理時間を削減できるため、残った問い合わせはより難しくなり、平均は誤解を招きます。速さを、再問い合わせ率と、エージェントが大きく変更したAI起案の返信の割合と組にしてください。注意点は、会話を終えた仮想エージェントは、解決された問題ではないことなので、戻ってくる問い合わせを数えます。

### 自動化

問い合わせ、キュー、ステータスのイベントを、電話とチケットのシステムから自動で収集し、振り分けの自動化を、誤った振り分けとキュー間を行き来する問い合わせで測ります。注意点は、自動の分類はずれるため、区分が正しかったかをチケットの抽出で確認することです。

### アナリティクス

応答時間にパーセンタイルを使い、各率の背後にある問い合わせの数を示し、判断がどの原因を取り除くかになるよう、問い合わせの理由を分解します。注意点は、小さなキューはノイズの多いパーセンテージを生むため、量の少ないサービスには区間または件数を示すことです。

## 業種別の視点

**スタートアップ。** デスクは、手が空いている人が扱う共有の受信箱やチャットのチャネルであることがよくあります。チャネル別に問い合わせを数え、区分にタグを付け、毎月プロダクトを作る人々と上位の五つを見ます。量が正当化する前にコールセンターのプラットフォームを買わず、二人がすべての問い合わせに答えるときに速さの目標を設定しないでください。

**中小企業。** 通常、一人または外部の提供者がホスト型のサービスデスクを運営します。ツールの標準レポートを使い、供給者に問い合わせ、解決、放棄の定義を書面で求め、ときどき生のデータをエクスポートします。「問題は解決しましたか？」のようなユーザーへの短い繰り返しの質問は、長いダッシュボードよりも多くの洞察を与えます。

**大企業。** 多くのキュー、言語、ツール、供給者が、同じ言葉の異なる定義につながります。問い合わせ、初回問い合わせでの解決、再問い合わせの共有の定義と、チャネルの共通の集合に合意します。キューとサービスごとに、リーダーシップ向けの標準ビューとともに報告し、到着パターンに合わせて人員を配置するためにワークフォースマネジメントのデータを使います。キュー同士の比較は、同じ定義を使っていることを確認してから行います。

**政府・公共部門。** レコードには、保持、アクセス、監査、プライバシーの義務があり、契約が外部委託されたデスクのメトリクスと目標を固定することもあります。契約のメトリクスを批判的に読み、要求されていなくても、防護柵の測定値をレポートに加えます。定義変更の監査証跡を保ち、不要な個人データの収集は避けます。公共サービスは、チャネルの選択肢が限られたユーザーを対象とすることが多いため、各チャネルのアクセシビリティが全体像の一部です（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

より良いデスクのメトリクスの動機は、より安く、より良いサービスであり、見返りは三か所に現れます。第一に、繰り返しの問い合わせの減少。再問い合わせはどれも、デスクが行う必要のなかった仕事であり、ユーザーが費やしたくなかった時間です。第二に、上流の修正。デリバリーのチームが行動すれば、デスクの区分のデータは、問い合わせの種類全体を取り除けます。第三に、より良い人員配置。到着パターンのデータにより、マネージャーはユーザーが必要とするときに人を配置でき、放棄と遊休時間が同時に下がります。

電話のプラットフォームとITSMツールがすでにイベントを記録していれば、収集のコストは控えめです。主なコストは、定義に合意し、問い合わせとチケットの間の紐づけを直し、短い問い合わせ後の質問を加え、デリバリーのチームとデータをレビューする時間です。

公表された数字は組織と方法によって異なり、このトピックのために検証されたものがないため、見返りの数字は提示しません。見返りは、自分たちのデータから見積もってください。再問い合わせの件数と測定された処理時間を取り、エージェントの時間あたりのコストを掛け、修正のコストと比較します。結果を、前提を付けた見積もりとして記述し、変更後に見直します（トピック 7.7「投資対効果とビジネスケース」を参照）。

## アンチパターンと落とし穴

- **平均処理時間を目標にする。** 急ぐことと早期の転送を報いる。問い合わせの種類別の分布を計画に使い、初回問い合わせでの解決と再問い合わせと組にする。
- **エージェントが設定するクローズフラグを初回問い合わせでの解決として数える。** 結果にかかわらず設定できる。再問い合わせの窓とユーザーの確認を使う。
- **個々のエージェントに順位を付ける。** 選り好みと防衛的な行動を促す。チームとキューごとに報告し、個人との対話は非公開で支援的に保つ。
- **最も弱いチャネルを隠す全チャネルの平均を報告する。** 電話、チャット、メールは異なる振る舞いをする。組み合わせる前に、各チャネルを別に報告する。
- **分母なしで量を読む。** 増加は成長かもしれない。100ユーザーあたりの問い合わせと区分の構成を示す。
- **デスクをデリバリーの判断から外す。** ダッシュボードに報告されて、プロダクトチームと議論されない件数は無駄である。上位の区分を、そのオーナーと毎月レビューする。

## チェックリスト

- [ ] 問い合わせとチケットが別に定義され数えられ、件数が突合している。
- [ ] すべてのチャネルに、応答までの時間の書面の時計と、自動返信の扱い方の明記がある。
- [ ] 時間の測定値が、標本の大きさとともに、中央値と高いパーセンタイルで報告されている。
- [ ] 放棄に書面の猶予期間があり、応答までの時間とともに示されている。
- [ ] 初回問い合わせでの解決が、再問い合わせの窓と、「同じ件」の明記された意味を使っている。
- [ ] 一問のユーザーの確認が収集され、その回答率が示されている。
- [ ] 100ユーザーあたりの問い合わせ率が、「アクティブユーザー」の書面の定義とともに報告されている。
- [ ] エージェントに処理時間の目標が設定されておらず、個人に順位を付けるメトリクスはない。
- [ ] 上位の問い合わせの区分が、所有するチームと毎月レビューされ、アクションがバックログに入る。
- [ ] 定義がバージョン管理され、各変更に日付が付いている。

[期間] の私たちのサービスデスクの数字は次のとおりです：[量、応答までの時間のパーセンタイル、放棄、処理時間のパーセンタイル、初回問い合わせでの解決、再問い合わせなどの数字を貼り付け]。定義は [定義を貼り付け] です。サービスが改善したからではなく、収集の仕方のために数字が改善したことを示唆するパターンを探し、それぞれについてデータで何を確認すべきかを提案してください。個人を非難せず、しきい値を捏造しないでください。前提と、示されたデータから判断できなかったことを列挙してください。

**上位の問い合わせの区分の月次レビューを準備する。**

```text
[サービスまたはチーム] のサービスデスクの問い合わせの区分の月次レビューを準備しています。直近三か月の [区分別の件数と100ユーザーあたりの問い合わせ] があります。議題、短い表のテンプレート、原因、修正、記事、セルフサービスの選択肢について各サービスのオーナーに尋ねる問いの一覧を起案してください。アクションをバックログに記録する方法を提案してください。数字や原因を捏造しないでください。前提と、私が持参すべきデータを列挙してください。
```

## 要点

- 問い合わせとチケットを別に数え、両方を定義し、量をユーザーの母数の大きさに対して正規化する。
- 時間を中央値と高いパーセンタイルで報告し、各数字が何件の問い合わせに基づくかを述べる。
- 応答の速さ、放棄、処理時間を労力のしるしとして読み、アウトカムのしるしとしての初回問い合わせでの解決と再問い合わせと組にする。
- 初回問い合わせでの解決を、ユーザーが戻ってくるかで定義し、一問の確認で裏付ける。
- デスクをセンサーとして使う。上位の区分を、サービスを所有するチームと毎月レビューする。
- キュー、チャネル、サービスを測り、個々のエージェントには決して順位を付けない。
