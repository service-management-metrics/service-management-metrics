# ユーザー体験と従業員体験

**人々は、周りのツール、デバイス、サポートが問題なく機能するときに最良の仕事をする。したがって、同僚が出会う摩擦を測り、答えを障害を取り除く理由として扱い、そのデータを決して監視や人の順位付けに変えない。**

## 概要と動機

アジャイル宣言の背後にある第5の原則は、意欲に満ちた人々を中心にプロジェクトを構成し、彼らに必要な環境と支援を与え、仕事が成し遂げられると信頼することを述べています。社内ITを使う人々にとって、環境とは、ノートパソコン、サインイン、コラボレーションのツール、アクセスのプロセス、サービスデスクです。それらが遅い、あるいは混乱を招くとき、意欲のある人々は時間と善意を失い、回避策を発明します。したがって、その環境を測ることは、人々を支える方法です。人々を見張る方法ではありません。

[従業員体験（employee experience）](https://en.wikipedia.org/wiki/Employee_experience_management)は、組織にいる期間を通じた、従業員の職場とのやり取りの総和です。ITが形作る部分は、デジタル従業員体験と呼ばれることがあり、[デジタルワークプレース（digital workplace）](https://en.wikipedia.org/wiki/Digital_workplace)は、人々が仕事に使う技術の集合です。この部の前のトピックは、満足度のアンケート（トピック 6.1「顧客満足度のメトリクス」を参照）と体験レベル合意（トピック 6.2「体験レベル合意」を参照）を扱いました。このトピックは、同じ注意を内側に向け、それらを構築し運営するエンジニアとオペレーターを含む、毎日ITサービスを使う同僚に向けます。

社内ユーザーは、測定にとって重要な四つの点で、外部の顧客と異なります。

- **去れない。** 従業員には乗り換える競合がないので、沈黙は満足ではない。諦めか、回避策を意味するかもしれない。
- **特定されうる。** 数百人の会社では、アンケートの答えの小さなグループが、一人を指しうる。プライバシーの設計が最初に来る。
- **同僚でもある。** 貧弱な体験データは関係と士気を損ない、良いデータは公然と共有し、一緒に行動できる。
- **デリバリーと運用のチームを含む。** 開発者やサービスデスクのスタッフが使うツールは体験の一部で、その摩擦は、より遅い修正を通じてユーザーに達する。

二つのテーマがこのトピックを貫きます。第一は**摩擦（friction）**です。人と仕事の間に立ちはだかる、避けられる労力、遅れ、割り込み。割り込みと精神的なオーバーヘッドは、時計の時間が示すよりコストがかかります。ワーキングメモリへの負担である[認知負荷（cognitive load）](https://en.wikipedia.org/wiki/Cognitive_load)の考え方は、混乱するフォームや予期しない強制再起動が、かかる分数以上にコストがかかる理由を説明し、没頭した集中の状態である[フロー（flow）](https://en.wikipedia.org/wiki/Flow_(psychology))の考え方は、知的労働にとって中断のない時間を守ることがなぜ重要かを説明します。第二のテーマは**倫理**です。プライバシーを侵害せずに体験を学ぶ方法。[従業員の監視（employee monitoring）](https://en.wikipedia.org/wiki/Employee_monitoring)技術は多くを測れ、支援と取り締まりの間の線は越えやすいものです。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、ここでは人間的な形で当てはまります。人を判断するのに使われるスコアは、人々に問題を隠すことを教えます（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

## 主要な原則

- **人ではなく、環境を測る。** 分析の単位は、サービス、デバイスの種類、グループであり、個人では決してない。
- **摩擦を敵として扱う。** 失われた時間、割り込み、混乱は、取り除くべきコストである。
- **尋ね、観察し、測る。** 人々が言うことを、システムが記録することと、仕事が行われるのを見て分かることと組み合わせる。
- **プライバシーを設計要件にする。** 問いに答える最小のデータを集め、早く集約し、小さなグループを抑制する。
- **すべての人を含める。** アクセシビリティの必要性、リモートやシフトの働き手、新入社員は、最悪の体験に出会うことが多い。
- **集中を守る。** 変更、更新、通知を、人々の仕事を中心に計画する。
- **何を集め、なぜかを言う。** 透明性が、誠実な答えが依存する信頼を築く。

## 推奨事項

### 人々とその仕事から始める

**1. 同僚と一日を歩く。** 異なる役割、場所、シフトの数人と座り、彼らが働くのを見ます。あらゆる待ち、回避策、混乱の瞬間に注意します。最初に何を直したいかを尋ねます。人々は慣れてしまった摩擦に気づかなくなるため、観察はアンケートが見逃す問題を見つけます。何を記録し、どう使うかを事前に合意します。

**2. 重要な瞬間をマップする。** スタッフにとって、影響の大きい瞬間は、通常、初日、ノートパソコンの故障、チーム間の異動、アクセスの依頼、組織を去ることです。それぞれのステップと、誰がそれを所有するかを書き留めます。マップは、遅れが隠れるチーム間の引き継ぎを示し、後の部の協働の測定値に結び付きます（トピック 9.3「協働と引き継ぎのメトリクス」を参照）。

**3. 周縁の人々を含める。** アクセシビリティの必要性を持つスタッフ、シフトで働く人々、リモートや現場のスタッフ、契約者は、平均の中で見えなくなることがよくあります。安全にできるところでは結果をセグメント化し、最も支援の行き届いていないグループをそれ単独でレビューします。アクセシビリティを第一級の要件として扱います。Web Content Accessibility Guidelinesのような[ウェブアクセシビリティ（web accessibility）](https://en.wikipedia.org/wiki/Web_accessibility)の規格は、社内ツールのための具体的なチェックリストを与え、アクセシビリティの問題は、多くの法域で法的、倫理的な問題です。

### 注意して測る

**4. 三種類の証拠を組み合わせる。** 名前付きのツールと瞬間についての短いパルスの質問、強制的な中断の分数やオンボーディングの完了のようなシステムの測定値、そして対話を使います。二種類が食い違うときは調査します。優れた稼働率と貧弱なパルススコアを持つツールは、稼働率には語れないことを語っています（トピック 5.3「可用性のメトリクス」を参照）。

**5. ITについてではなく、ツールについて尋ねる。** 「ファイルシステムで文書を見つけるのはどれだけ容易ですか？」は、「ITはどうですか？」よりも良い答えを得ます。誰も四半期に一、二度より多く尋ねられないよう、パルスでツールを入れ替え、傾向が意味を持つよう文言を安定に保ちます。

**6. 人々が失う分を数える。** 失われた時間は、スコアより理解しやすいものです。再起動の促しやサインインの失敗など、システムから見積もれるところではそうし、できないところでは人々におおよその数字を尋ねます。グループについて、月あたり一人あたりで、方法とともに示し、前提も述べない限り、劇的な数字を作るために給与を掛けるのは避けます。

**7. 最小化して集約する。** [データ最小化（data minimization）](https://en.wikipedia.org/wiki/Data_minimization)の原則に従います。必要なものだけを集め、必要な間だけ保ち、できるだけ早く集約します。誰かを特定しうるデータには、[仮名化（pseudonymization）](https://en.wikipedia.org/wiki/Pseudonymization)がリスクを減らします。報告される各グループに少なくともk人が含まれることを要求する[k-匿名性（k-anonymity）](https://en.wikipedia.org/wiki/K-anonymity)のような規則は、小さなセルを抑制する単純な方法を与えます。kの値を台帳に述べます。

**8. 監視に対して明確な線を引く。** 体験のデータ、エンドポイントのテレメトリ、センチメントを、個人を評価する、誰が「関与が低い」かを検出する、あるいは業績評価に入れるために使ってはいけません。書面でそう述べ、そのような組織があれば、スタッフの代表や労使協議会にデータ計画をレビューしてもらいます。行動のデータを集める前に、現地の法律とプライバシーの専門家を確認します。信頼は、一度失われると、その後のすべてのアンケートをより不誠実にします。

### 学んだことに行動する

**9. 最大の摩擦を先に直し、そう言う。** 問題を、失われた時間、人数、影響を受ける人々にとっての深刻度で順位付け、上位のものに資金を付けます。何を直し、何を選ばなかったかを、理由とともに人々に伝えます。目に見える修正が、問題を報告し続けることへの最も強い励ましです。

**10. 中断を仕事を中心に計画する。** 多くの強制的な中断は避けられます。集中の時間の外に更新を予定し、限度内で延期を提供し、再起動をまとめます。一部の更新は素早く行わなければならないため、トレードオフが明示されるよう、セキュリティの目標の隣で強制的な中断の分数をレビューします（トピック 4.3「変更実現のメトリクス」を参照）。

**11. 回避策を設計へのフィードバックとして扱う。** 人々が未承認のツールを使うとき、それが何をより良くするのかを尋ねます。答えは、公式のツールが見逃した要件です。[シャドーIT（shadow IT）](https://en.wikipedia.org/wiki/Shadow_IT)にはセキュリティとコストの実際のリスクがあり、懲罰的な対応はそれを地下に潜らせます。良い考えを取り入れるか、リスクを説明して安全な代替手段を提供するほうが望ましい。

**12. プログラムを、それが仕える人々と共有する。** 結果をスタッフに示し、代表との短いレビューを開き、次の四半期に何を変えるかを尋ねます。プログラムは、ITとそのユーザーの間の継続的な協働の一形態であり、環境の継続的な改善が成果です。次の部の人々の測定値に結び付けます（トピック 9.2「満足度とウェルビーイングのメトリクス」を参照）。

| 回避策の蔓延 | 結果をほのめかして誠実な答えを妨げる、満足しているグループにだけ尋ねる | 匿名性の声明。回答率と回答者の構成。プライバシー保護の順守 |

| プライバシー保護の順守 | 独立したレビューなしに順守を報告する、問題を隠すためにグループを広げる | チーム外の誰かによる定期的なレビュー。規則（kの値と抑制）を公開する |

健全な読みは、初日に働ける新入社員、減る強制的な中断の件数、より良い公式のツールにつながる回避策、そしてプログラムが自分たちの答えで何をするかを見たので、それを信頼していると言うスタッフです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| パルスアンケート | 直接の声、安価、繰り返しやすい | アンケート疲れ。回答バイアス |
| システムのテレメトリ | 客観的、継続的、アンケートの負担なし | プライバシーのリスク。イベントは示すが、感情は示さない |
| 観察とインタビュー | 隠れた摩擦を見つける。関係を築く | 時間がかかる。小さな標本 |
| 細かいデータ | 精密な診断 | 人を特定する。信頼を損なう |
| 抑制を伴う集約データ | 共有し行動しても安全 | 詳細が少ない。苦労しているかもしれない小さなグループを隠す |
| デバイスへの厳格な統制 | セキュリティとコンプライアンス | より多くの強制的な中断。より多くの回避策 |

散文での答えは、三種類の証拠すべてをグループのレベルで使い、診断が必要とする間だけ詳細を保ち、セキュリティと体験をオープンに議論するトレードオフとして扱うことです。狙いは、意欲のある人々がわずかな労力で必要なものを得られる職場です。

## チームで話し合う問い

**1. 新しい同僚の初日はどんなもので、どうやってそれを知るか？**
チームに、内定から最初の実際のタスクまでの経路をたどってもらいます。誰が何をし、どこで待つか。最近の新入社員に会話に加わってもらいます。ファシリテーターは、その人を待たせたり恥ずかしい思いをさせたりした瞬間に焦点を当て、次の新入社員の日を改善する変更を一つ合意してください。

**2. 人々が使う回避策のうち、使ってほしくないものはどれで、それは何を教えているか？**
チームが見てきた非公式のツールと手作業のステップを列挙します。それぞれについて、どんな必要を満たすかを尋ねます。対話は、公式のサービスが見逃した要件をしばしば見いだします。どの回避策を取り入れ、どれをより良い公式の選択肢に置き換え、どれを説明付きで禁止するかを決めます。

**3. 私たち自身の行動は、毎月同僚から何分を奪っているか？**
典型的な人の強制再起動、更新、促しを見積もります。ユーザーが言うことと比較します。ファシリテーターは、その数字が公表されたら何が変わるかを尋ねられます。今四半期に減らす、あるいは再スケジュールする中断を一つ合意します。

**4. 同僚についてどんなデータを集められ、それで何をしないと約束すべきか？**
二つの一覧を作ります。技術的に可能なことと、チームが実際に集めること。目的と限度の短い声明を起案します。スタッフの代表に反応してもらいます。議論は、監視に対する線がどこにあるか、それをどう説明するかを示します。

**5. 私たちのツールで最も苦労するのは誰で、その人々は私たちのデータにいるか？**
アクセシビリティの必要性、シフトの働き手、リモートのスタッフ、新しい人々について考えます。アンケートとログが彼らに届いているか、小さなグループの規則が彼らを隠していないかを確認します。最も支援の行き届いていないグループに直接耳を傾ける方法を一つ合意します。

**6. 先四半期に、同僚が教えてくれたことをもとに何を直したか、彼らはそれを聞いたか？**
修正と、それがどう告知されたかを列挙します。一覧が短いなら、何が行動を妨げているかを話し合います。オーナーシップ、資金、あるいは恐れ。次のアンケートの前に提供する目に見える修正を一つと、それを説明するメッセージに合意します。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、社内ツールのユーザーであり、作り手でもあります。遅いビルド、不安定な環境、アクセスの遅れなど、彼ら自身の摩擦が、提供するすべてを遅くし、このトピックの測定値は彼らにも当てはまります。社内ツールを、オーナーとユーザーを持つプロダクトバックログの一部とし、同僚としてパルスとレビューに参加するべきです（トピック 9.1「チームの健全性と開発者体験」を参照）。

### サービスと運用のチーム

運用とサービスデスクは、体験の多くを形作り、独自のツールと作業負荷を持つスタッフです。ユーザーの集中に配慮して変更を送り、アクセシビリティの経路を応答性の高いものに保ち、回避策をフィードバックとして使うべきです。また、自分たちの同僚が体験データで順位付けされるのを守るべきです。サポートのスタッフも意欲のある人々です。

### リーダーシップとガバナンス

リーダーは、測定の文化を設定します。スコアを上げるのではなく、摩擦を取り除くことを求め、修正に資金を付けるべきです。プライバシーのコミットメントを書面で守り、個人にデータを使う依頼に抵抗し、セキュリティの統制には比較すべき体験のコストがあることを受け入れるべきです。ガバナンスは、あらゆる体験のレポートの一部として、プライバシーの規則とそのレビューを期待するべきです。

### 顧客とユーザー

社内ITを使う人々は、体験の作者です。機能する初日、集中を尊重するツール、自分たちについて何が集められるかの誠実な説明、可能なところでのオプトアウトの方法、声を上げることが変化につながるという証拠に値します。アクセシビリティの必要性を持つ同僚には、サービスをどう機能させるかを尋ねるべきで、特別な事例として扱うべきではありません。

## 実践：サービスマネジメントの例

大学の中央IT部門が、6,000人のスタッフを支え、サービスデスク、プラットフォームチーム、いくつかのプロダクトチームを運営しています。以下の数字は例示です。

新しいIT責任者は、サービスデスクの解決時間が目標内にあるのに、なぜオンボーディングへのスタッフの不満が続くのかを知りたいと考えています。彼女はサービスマネージャーに、新入社員とコラボレーションの主要ツールの体験プログラムを、スタッフ評議会とともに構築して試行するよう頼みます。評議会の条件は、個人についてのデータを使わないという書面の約束で、計画をレビューすることに同意します。

チームは、オンボーディングの追跡と、新入社員とそのマネージャーからの一問の確認を使って、先四半期の140人の新入社員について、初日の準備と生産的になるまでの時間を測ります。初日にすべての合意した項目が動いていた新入社員は46パーセントだけで、生産的になるまでの時間の中央値は4日、85パーセンタイルは9日でした。インタビューからの理由は、それぞれ異なるチームを待つ三つの別々の依頼と、金曜に遅く終わるノートパソコンのイメージングのステップです。スタッフの入れ替わる10分の1に送り、最小のグループサイズを10とした、コラボレーションツールの短いパルスは、夜間や週末に働くスタッフの間でより低い評価を示します。建物とシフト別に集約したエンドポイントのログは、月平均38分の強制的な再起動と更新の促しを示し、夜勤のスタッフには長い裾があります。他の人が眠っている間にデバイスが更新されるため、彼らは勤務時間中に再起動があるのです。

チームは三つの変更を行います。三つの依頼に代わる、名前付きのオーナーを持つ一つのオンボーディング依頼。イメージングのステップを平日の時間帯に移す。更新のスケジューリングに、ユーザーの勤務時間に結び付いた延期の窓を加える。メトリクス台帳にプライバシーの規則を公開します。最小のグループサイズ10、どのレポートにも個人のデータなし、生のログに6か月の保持の限度。三か月後、初日の準備は81パーセントに上がり、生産的になるまでの時間の85パーセンタイルは5日に下がり、夜勤のスタッフの強制的な中断の分数は約半分に下がります。IT責任者は、あるマネージャーから、フォローアップのためにチームの名前を挙げて、どの部署に最も多くの苦情があるかを報告するよう求められます。彼女は部署に順位を付けることを断り、代わりにグループレベルのパターンを共有し、原因を直すことを提案します。判断は判断ログに記録され、評議会は、プログラムを二つ目のツールに拡張するよう求めます。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

継続的改善の精神で、摩擦を小さなステップで直し、何が変わったかを人々に示します。注意点は、目に見える行動なしに繰り返し人々にアンケートすると、信頼が壊れることです。

### AI

AIアシスタントは従業員の日々の仕事を変えるので、AI支援のタスクの摩擦と失われた時間を測り、利用を、ユーザーが報告した便益と組にします。注意点は、個人についてのAIの利用データは業績の判断に誤用されうるため、集約して統制することです。

### 自動化

デバイスとアプリケーションの健全性を、明確なプライバシーの限度のもとで自動で集め、収集を網羅率と、直された問題の数で測ります。注意点は、技術的なテレメトリは仕事がどう感じられるかを見逃しうるため、短いアンケートと組み合わせることです。

### アナリティクス

準備と生産的になるまでの時間を、件数とともに報告し、個人別には決して報告しません。これが情報を与える判断は、障害をどこで取り除くかです。注意点は、小さなチームは特定可能なデータを生むため、報告の前に最小のグループサイズを設定することです。

## 業種別の視点

**スタートアップ。** 皆が皆と話すので、観察と対話が摩擦のほとんどを見つけます。初日の体験を、それが調子を決めるので優れたものにし、テレメトリは最小限に保ちます。チームが小さくても、プライバシーの約束を早く書き留めます。

**中小企業。** 一人の管理者がオンボーディングとサポートを扱うことがあります。単純なチェックリストを使い、各新入社員に何が欠けていたかを尋ねます。小さなグループのデータには注意します。十数人のスタッフでは、ほとんどあらゆる内訳が誰かを特定するため、対話に頼ります。

**大企業。** 大きく多様な環境は、セグメント化を有用で、同時に危険にします。チームではなく、役割の系統、拠点の種類、デバイスのクラスでセグメント化し、最小のグループサイズを適用し、スタッフの代表を関与させます。最初からセキュリティ、法務、プライバシーの機能とプログラムを整合させます。

**政府・公共部門。** アクセシビリティ、平等、プライバシーについての義務はしばしば法定で、労使協議会や労働組合に正式な役割があるかもしれません。アクセシビリティのテストと協議を、プログラムの必須の部分として扱い、プライバシーの規則を公開し、明確に必要でないデータを集めるのは避けます。スタッフのデータが規制の対象となるところでは、データ保護責任者を関与させます（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは控えめです。パルスアンケートと観察には人々の時間とアンケートのツールが要ります。エンドポイントのデータは通常、すでに展開されたツールから来ますが、分析とプライバシーのレビューには労力がかかります。最大のコストは、見つけたものを直す意志で、それはチームにまたがるオンボーディングのプロセス、デバイスのポリシー、更新の実践を変えることを意味するかもしれません。

見返りは、取り戻される時間、新入社員のより速い立ち上がり、避けられる摩擦による少ないサポートの問い合わせ、少ないシャドーITとして現れます。自分たちの数字からケースを築けます。一人あたりの強制的な中断の分数、新入社員の生産的になるまでの日数、修正が取り除いた問題についてのサポートの問い合わせ。給与と分数から導いた単一の生産性の数字には慎重であってください。取り戻された一分がどれだけの価値があるかについての前提に依存するからです。台帳の反対側にも、リスクのコストがあります。スタッフについてのデータを集めすぎると、法的なリスクが生じ、信頼を損なうことがあります。それを総所有コストに含めてください。

## アンチパターンと落とし穴

- **体験のデータで個人を判断する。** 支援プログラムを監視に変え、誠実なフィードバックを終わらせる。集約し、小さなグループを抑制し、そう述べる。
- **平均だけを測る。** 最悪の体験をしている人々が隠れる。裾と、最も支援の行き届いていないグループを見る。
- **可能だからといってすべてを集める。** より多くのデータはより多くのリスクをもたらす。問いに答えるものを集める。
- **容赦なくアンケートする。** 人々は答えるのをやめる。ツールを入れ替え、短く保つ。
- **回避策を罰する。** 人々はそれを隠し、根底の必要が満たされないままになる。そこから学ぶ。
- **セキュリティと体験を別々の部屋に置く。** 一部の統制はコストに見合い、多くはそうでない。数字でトレードオフを議論する。
- **初日を他人の問題として数える。** オンボーディングは人事、IT、マネージャーにまたがる。一つのオーナーを与える。
- **苦情が来るまでアクセシビリティを無視する。** 最初から影響を受ける人々とともに作り、テストする。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| 摩擦の理解 | 苦情のみ | 時折のインタビューまたはアンケート | 主要なツールと瞬間の定期的な観察とパルス | アンケート、システム、対話の証拠を組み合わせ、安全にセグメント化する | 人事、施設、供給者との共同の見方。スタッフが優先順位を共同で所有する |
| プライバシーと倫理 | 述べられた規則なし | 非公式な配慮 | 書面の目的、最小化、グループサイズの規則 | 規則が独立してレビューされる。順守が測定される | 規則がスタッフの代表と共同設計され、供給者にまたがって監査される |
| 行動 | 苦情による修正 | アドホックな修正 | 上位の摩擦が、オーナーとともにバックログにある | 修正に資金が付き、追跡され、告知される。中断が仕事を中心に計画される | 体験の改善が、チームと供給者にまたがる計画に組み込まれる |

## チェックリスト

- [ ] 重要な瞬間（初日、デバイスの故障、アクセスの依頼、異動、退職）が、オーナーとともにマップされている。
- [ ] 初日の準備と生産的になるまでの時間が、書面の一覧と時計で測定されている。
- [ ] 短いパルスが、名前付きのツールを入れ替えながらカバーしている。
- [ ] 強制的な中断の分数が、グループ別に測定され、セキュリティとレビューされている。
- [ ] アクセシビリティの依頼がタグ付けされ、追跡され、依頼者が確認している。
- [ ] レポートが最小のグループサイズを使い、個人を決して示さない。
- [ ] 体験のデータについての書面の目的と限度の声明があり、共有されている。
- [ ] そのような組織があるところでは、スタッフの代表がデータ計画をレビューしている。
- [ ] 回避策が集められ、フィードバックとしてレビューされている。
- [ ] 結果と修正が四半期ごとにスタッフと共有されている。

## AIプロンプト

**重要な瞬間をマップする。**

```text
[組織の種類] で、[瞬間。例：新入社員の初日] を改善したいと考えています。今日のステップは次のとおりです：[ステップと各オーナーの一覧]。引き継ぎと待ちを示すテキストのマップを描き、摩擦がありそうな箇所を示唆し、各主要ステップについて、人々が言うこと、システムが記録すること、観察から一つずつの測定値を提案してください。数字を捏造しないでください。前提と、スタッフに尋ねるべき問いを列挙してください。
```

**体験プログラムのプライバシーの声明を起案する。**

```text
[法域] の [組織の種類] の体験プログラムについて、スタッフ向けの1ページの平易な言葉の声明を起案してください。集めるもの：[データの一覧]。目的は [目的] です。しないこと（たとえば個人のデータを使う）、最小のグループサイズ [数]、保持 [期間]、生のデータを見られる人、スタッフが懸念を提起する方法を含めてください。プライバシーの専門家やスタッフの代表とレビューすべきことに印を付けてください。法的な結論を出さないでください。前提を列挙してください。
```

**ツールについてのパルスのコメントを分析する。**

```text
以下は [期間] の [ツール] についての [数] 件の匿名化したコメントです：[個人データを除いたコメントを貼り付け]。摩擦のテーマにグループ化し、各テーマを数え、それぞれに二つの代表的な引用を挙げ、どのテーマが修正可能な原因を指し、どれが研修の必要を指すかを示唆してください。個人を特定したり、動機を推測したりしないでください。前提と、行動する前に人が確認すべきことを列挙してください。
```

**中断の削減を計画する。**

```text
私たちのエンドポイントは、一人あたり月平均 [数] 件の計画された中断を受けています：[種類と頻度の一覧]。セキュリティ要件：[一覧]。要件を満たしながら、集中の時間への中断を減らす方式（たとえば延期の窓、まとめ、勤務時間による予定）を提案し、個人を追跡せずにそれが機能するかをどう測るかを述べてください。前提と、セキュリティと話し合うべきトレードオフを列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：体験または摩擦のメトリクスを公開する前に、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：改訂した体験のメトリクスの項目が、悪用の手口、防護柵、プライバシーの規則を保っているかを確認するときに使います。

## 要点

- 狙いは、意欲のある人々に必要な環境と支援を与えることなので、摩擦を測り、取り除く。
- パルスの質問、システムの測定値、観察を組み合わせ、周縁のグループを見る。
- ITの自らの行動が引き起こす失われた分と割り込みを数え、人々の集中を中心に計画する。
- プライバシーを設計の規則にする：最小化し、集約し、小さなグループを抑制し、個人を決して判断しない。
- 回避策をフィードバックとして扱い、何を直したかをスタッフに伝える。
- 最初からアクセシビリティを含め、プログラムを、それが仕える人々とレビューする。
