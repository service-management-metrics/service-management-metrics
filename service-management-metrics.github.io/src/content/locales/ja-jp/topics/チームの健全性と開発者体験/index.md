# チームの健全性と開発者体験

**チームは、フィードバックが速く、心への負荷が管理でき、長い集中の時間を見つけられるときに最良の仕事をする。したがって、それらの条件をチームとともに測り、それが明らかにする障害を取り除き、数字を人々の順位付けには決して使わない。**

## 概要と動機

アジャイル宣言の原則は、意欲に満ちた個人を中心にプロジェクトを構成し、彼らに必要な環境と支援を与え、仕事が成し遂げられると信頼することを私たちに求めます。また、スポンサー、開発者、ユーザーが一定のペースを無期限に保てること、そしてチームがより効果的になる方法を定期的に振り返ることも求めます。チームの健全性と開発者体験の測定値は、それらの原則を確認可能にする方法です。ここで働くのがどんなものか、何が妨げになっているかを問います。

[開発者体験（developer experience）](https://en.wikipedia.org/wiki/Developer_experience)は、開発者が一緒に働くツール、プロセス、人々とのやり取りの総和です。この考え方は、ソフトウェアエンジニアリングより広いものです。オペレーター、サービスデスクのスタッフ、アナリスト、サービスを構築または運営するその他の人々は、自分たちの環境の体験を持っています。このトピックは、エンジニアには「開発者体験」を、より広いグループには「チームの健全性」を使い、同じ測定値が両方に当てはまります。

広く引用される二つの研究の枠組みがあります。2021年にニコール・フォーズグレンらが発表したSPACEフレームワークは、開発者の[生産性（productivity）](https://en.wikipedia.org/wiki/Productivity)が一つの数字に還元できないと論じ、五つの次元を提案します。満足度とウェルビーイング、パフォーマンス、活動、コミュニケーションと協働、効率とフロー。アビ・ノダ、マーガレット＝アン・ストーリー、ニコール・フォーズグレン、ミカエラ・グライラーによる2023年の続編「DevEx: What Actually Drives Productivity」は、開発者が感じられ、組織が変えられる三つの次元に焦点を当てます。フィードバックのループ、認知負荷、フロー状態。両方の論文は、認識についてのアンケートのデータを、ワークフローについてのシステムのデータと組み合わせることを推奨し、どちらも、単一の測定値、特に活動の件数を生産性の代理として使うことに警告します。

DevExの三つの次元は、実際的な出発点です。

- **フィードバックのループ。** 人は自分のしたことの結果をどれだけ速く知るか。遅いビルド、遅いテスト、遅いレビュー、遅い承認は、それぞれ待ちを加え、待ちは集中を壊す。速いフィードバックは、継続的デリバリーの中核の支えでもある。
- **[認知負荷（cognitive load）](https://en.wikipedia.org/wiki/Cognitive_load)。** 何かを成し遂げるために、人は心にどれだけ保持しなければならないか。複雑なシステム、貧弱な文書、不明確なオーナーシップ、多くのツールが負荷を上げる。それを減らすと、重要な仕事のためのキャパシティが解放される。
- **[フロー状態（flow state）](https://en.wikipedia.org/wiki/Flow_(psychology))。** 人は、集中できる中断のない時間を見つけられるか。会議、通知、計画外の依頼、コンテキストの切り替えは、すべてそれを侵食する。

この領域の測定値は、異常に誤用されやすいものです。コミット、プルリクエスト、クローズされたチケット、オンラインの時間の件数は、活動の測定値です。集めやすく、人々が良い仕事をできているかについてはほとんど語らず、悪用を招きます。認識の測定値は主観的で価値がありますが、人々が誠実な答えの結果を恐れると歪められます。人についてのあらゆる測定値は、監視に滑り込みえます。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、倫理的な鋭さを伴って当てはまります。人についての測定値が目標になると、人々は自分の仕事について真実を語るのをやめます（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

このトピックは、前に述べた社内ユーザーの体験の上に築かれ（トピック 6.4「ユーザー体験と従業員体験」を参照）、ウェルビーイング、協働、スキル、改善についての次のトピックに続きます。

## 主要な原則

- **人ではなく、条件を測る。** 環境とその障害について尋ね、チームのレベルで報告する。
- **認識とワークフローのデータを組み合わせる。** 人々が感じることとシステムが記録することは、それぞれ絵の一部を見逃す。
- **チームに自分たちの健全性の確認を所有させる。** 仕事に最も近い人々が質問を選び、結果を最初に読む。
- **これらの測定値で個人に順位を付けたり評価したりしない。** それは誠実な答えを終わらせる。
- **活動の件数を生産性として避ける。** コミット、チケット、時間の件数は成果ではない。
- **聞いたことに目に見える形で行動する。** 障害を直すか、なぜそうしないかを言う。
- **持続可能なペースを守る。** 無期限に熱くなって走るチームは、自分の将来から借りている。

## 推奨事項

### 人々が働く条件から始める

**1. チームに、何が自分たちを遅くするかを尋ねる。** アンケートではなく、対話から始めます。何があなたの時間を無駄にし、何が理解しにくく、何が最もあなたを中断させるか。答えをチームの言葉で書き下します。対話は、ダッシュボードでは見つからない問題を見つけ、後のアンケートが必要とする信頼を築きます。測る二つか三つに合意します。

**2. DevExの三つの次元をレンズとして使う。** フィードバックのループ、認知負荷、フロー状態のそれぞれについて、認識の質問を一つと、可能ならシステムの測定値を一つ選びます。フィードバックのループには、「ビルドにかかる時間にどれだけ満足していますか？」を、ビルドの所要時間と組にします。認知負荷には、名前付きのシステムを理解し変更するのがどれだけ難しいかを尋ねます。フローには、人々がどのくらいの頻度で中断なしに働けるかを尋ねます。人々が言うことをシステムが記録することと組にし、食い違いを見ます。

**3. SPACEの複数の次元をカバーする。** どの単一の種類のデータも支配しないよう、五つの次元のうち少なくとも三つから測定値を選びます。満足度とウェルビーイング、協働、効率とフローが、サービスを運営するチームにとって最も重要なことがよくあります。活動の測定値を大きな注意をもって扱い、文脈としてのみ使います。次元の網羅の測定値が、これを誠実に保ちます。

### 注意して測る

**4. チームに健全性の確認を所有させ、最初に結果を読ませる。** チームの健全性の確認は、楽しさ、支援、速さ、学び、リリースの容易さなど、チームが選ぶ次元についての短い自己評価です。チームは、他の誰かが要約を見る前に、自分たちの結果を読んで議論します。他の人々が見るのは、比較するスコアではなく、傾向と、チームが助けを求める障害です。これはツールを学びの補助に保ち、人々が声を上げても罰されないという共有された信念である[心理的安全性（psychological safety）](https://en.wikipedia.org/wiki/Psychological_safety)に依存します。

**5. 重要なフィードバックのループの時間を測る。** 人々が不満を言うループの所要時間を測ります。ローカルのビルド、テストスイート、コードレビューの待ち、テスト環境へのデプロイ。遅い裾は平均が示唆するより痛手なので、中央値と85パーセンタイルを報告します。数字をパイプラインを所有するチームと共有し、改善を定期的な仕事として設定します（トピック 2.7「プルリクエストとコードレビューのメトリクス」を参照）。

**6. 集中を守り、穏やかに測る。** パルスで集中について尋ね、中断の原因を見ます。会議の負荷、通知、計画外の依頼。チームがカレンダーのパターンを見たいなら、彼らの合意のもとで行い、結果を集約します。個人の活動や在席を決して追跡してはいけません。狙いは、文書で済む会議のような、取り除くべき構造的な中断を見つけることです。

**7. 障害の解決までを追跡する。** チームが挙げた障害の見える一覧を保ち、それらが解決される、あるいは意識して脇に置かれるまでの時間を測ります。決して縮まない長い一覧は、問題を挙げることが無意味だと人々に教えます。障害を取り除かないという、理由を伴う判断は、解決として数えます。

### 結果を使って改善する

**8. 一度に一つか二つのことに行動する。** 最も価値の高い障害を選び、直し、チームに伝えます。目に見える行動は、長いレポートより信頼に効果があります。一度に多くの取り組みを始める誘惑に抵抗します。

**9. 人の測定値を成果の測定値と組にする。** フィードバックのループと認知負荷が、デリバリーと安定性の成果とどう関係するかを見ます（トピック 2.8「DORAメトリクス」を参照）。自分たちのデータの相関から因果を主張してはいけません。組み合わせを使って、レビューが遅いチームはサイクルタイムも長いかなど、探る問いを見つけます。

**10. 活動の件数を対話の外に置く。** 個人別のコミット、コードの行数、クローズされたチケットを報告してはいけません。チームの出力の件数はフローに有用でありえますが、健全性についてはほとんど語りません。誰かが個人の活動のメトリクスを求めるなら、研究を説明し、代わりに条件の測定値を提案します。

### 人々を守る

**11. 集める前にプライバシーの規則を設定する。** 何が集められ、なぜか、誰が見るか、どのくらい保持されるか、何が決して行われないかを書き下します。チームのレベルで集約し、小さなグループを抑制し、関係する人々の代表に規則をレビューさせます。このデータを、業績評価、昇進、懲戒に使ってはいけません。

**12. 持続可能なペースを既定にする。** チームが熱くなって走っているしるしに注意します。時間外のインシデントの長い連続、永続的な緊急の状態、増える障害の一覧、下がる満足度。これらを、範囲、人員、優先順位で直すシステムの問題として扱います。人々が保てる一定のペースは設計の目標で、品質、学び、定着を支えます（トピック 9.2「満足度とウェルビーイングのメトリクス」を参照）。

| --- | --- | --- |
| フィードバックのループ時間 | 遅い事例を除外する、ほとんどの仕事が通らない速い経路を測る | 85パーセンタイルを報告する。台帳に各ループの開始と終了を定義する |
| 集中時間の割合 | 集中せずにカレンダーの時間をブロックする、マネージャーを喜ばせるために水増しした集中を報告する | チームが所有するパルス。中断の原因と比較する。個人の報告なし |
| 認知負荷の評価 | 精査を避けるためにシステムを低く評価する、簡単なシステムを選んで評価する | 固定のシステムの一覧を評価する。オンボーディングの時間とインシデントのパターンと比較する |
| 障害の解決時間 | 直さずに障害をクローズする、障害を記録するのを拒む | チームが解決を確認する。再オープンされた障害の率 |

| ツールとプロセスの満足度 | 満足しているユーザーにアンケートする、スタッフに上手に答えるよう訓練する | 回答率と構成。コメントを読む。システムの測定値に結び付ける |
| 次元の網羅 | 形だけの測定値で次元を数える | 数えた各測定値が判断に使われていることを確認する |

健全な読みは、より短く安定したフィードバックのループ、主要なシステムで下がる認知負荷、本当の集中を報告するチーム、挙げられて解決される障害、チームが信頼する健全性の確認、そして個人へのデータの使用がないことです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| 認識のアンケート | システムにできないことをとらえる。低コスト | 主観的。恐れと疲れに弱い |
| ワークフローの測定値 | 客観的。継続的 | 感情と原因を見逃す。監視のリスク |
| チームが所有する健全性の確認 | 誠実でチームに有用 | 比較しにくい。スケールしにくい |
| 標準の全社アンケート | チーム間で比較できる | 関連性が低い。順位付けに使われる |
| 活動の件数 | 集めやすい | 代理として貧弱。簡単に悪用される |
| 条件に焦点を当てた測定値 | 直せる原因を指す | フォローアップの労力が要る |
| 頻繁なパルス | 適時 | アンケート疲れ |
| 年次のアンケート | 負担が少ない | 遅い。古くなる |

散文での答えは、チームが所有する健全性の確認と短いパルスを、人々が不満を言うループのワークフローの測定値と組み合わせ、活動の件数を避け、プライバシーを守ることです。全社の比較は控えめに使い、チームに順位を付けるためには決して使いません。

## チームで話し合う問い

**1. 私たちの働く日の最も遅いフィードバックのループは何で、実際にどれだけかかるか？**
人々が最も不満を言うループを選びます。システムから時間を測り、人々が言うことと比較します。ファシリテーターは、どちらの方向であれ、驚きに注意してください。それを短縮する変更を一つと、誰が所有するかを合意します。

**2. 私たちが変更を恐れるシステムはどれで、何がそれを難しくしているか？**
システムに名前を付けます。難しさはコード、文書、ツール、あるいは少数の頭の中の知識にあるか。どの改善が負荷を最も下げるかを尋ねます。それが機能したかをどう知るかを計画します。

**3. 私たち各自が最後に中断のない長いブロックを持ったのはいつで、失敗したものを何が中断したか？**
正直に、非難なく共有します。中断を列挙し、構造的なもの（会議、通知、計画外の依頼）と偶発的なものに分けます。減らす構造的な中断を一つ選びます。

**4. 結果なしに一度ならず挙げた障害はどれか？**
障害の一覧を見ます。長く残る各アイテムについて、誰が解決でき、何がその人をブロックしているかを尋ねます。チームが障害を挙げるのをやめたなら、その理由を話し合います。証拠とともにエスカレーションする一つに合意します。

**5. 健全性の確認で誠実に答えるのをためらわせるものは何か？**
結果がどう使われうるかへの恐れを話し合います。ファシリテーターは、懸念を記録し、規則に合意してください。誰がデータを見るか、それで何が決して行われないか。規則が信頼されないなら、そう述べ、何が信頼を獲得するかを決めます。

**6. 私たちの測定値のうち、仕事が悪くなりながら上がりうるものはどれか？**
測定値を列挙し、それぞれが誰の助けにもならずに改善されうる方法を考えます。それぞれに防護柵を割り当てます。判断に使われない測定値は取り除きます。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、何が自分たちを遅くするかを最もよく知り、自分たちの健全性の確認のオーナーです。障害に名前を付け、制御するループの時間を測り、何を先に直すかをチームとともに決めるべきです。個人の活動を報告する圧力に抵抗し、チームレベルの測定値を主張するべきです。

### サービスと運用のチーム

運用チームは、集中とペースを侵食するオンコール、割り込み、計画外の仕事を担います。構造的な負荷をシステムの問題として挙げ、自分たちのツールのループを測り、持続可能なローテーションを保つべきです。多くの障害が境界をまたぐので、デリバリーのチームと共有の障害の一覧から恩恵を受けます。

### リーダーシップとガバナンス

リーダーは条件を設定し、データがどう使われるかを決めます。条件の測定値が明らかにする修正に資金を付け、プライバシーの規則を守り、比較するスコアの代わりに傾向と障害を求めるべきです。ガバナンスは、個人の活動のメトリクスの依頼を、規則を見直す理由として扱い、改善の仕事が目に見えることを期待するべきです。

### 顧客とユーザー

ユーザーは、冷静に働き素早く学べるチームから恩恵を受けます。彼らの問題がうまく解決されるからです。また、チームが圧倒されているときにも気づきます。遅い回答、繰り返される間違い、高い離職。彼らのフィードバックは、外からのチームの健全性についての証拠であり、彼らは修正の優先順位がどう付けられるかについて、誠実さに値します。

## 実践：サービスマネジメントの例

国の保険会社の技術グループには、保険契約と請求のサービスを構築し運営する14のチームがあります。リーダーシップは、開発者の生産性のダッシュボードを求めます。最初の依頼は、個人別のコミットとクローズされたチケットです。エンジニアリング効果の責任者は、別のアプローチを提案します。以下の数字は例示です。

彼女は、五つのチームでの対話から始めます。三つの障害が繰り返し挙がります。テストスイートに70分かかる、二人の上級レビュー担当者に依存するチームではコードレビューが長く待たされる、そして誰もレガシーな請求計算サービスを変更できると感じていない。彼女はシステムから測れるものを測ります。ビルドとテストのループの中央値は58分で、85パーセンタイルは92分です。最初のレビューまでの待ちの中央値は9営業時間、85パーセンタイルは31時間です。彼女は、DevExの三つの質問を含む短い四半期ごとのパルスを、最小の報告グループを5として加えます。請求計算サービスの認知負荷の評価は、5が非常に難しい5段階の尺度で4.4で、保険契約のポータルの2.6に対する値です。チームが報告する集中時間は1日あたり約3時間で、会議と計画外の依頼が主な原因です。各チームは、自分たちが選んだ次元で自分たちの健全性の確認を実行し、結合した傾向だけを読みます。

グループは、チームとともに四つのアクションに合意します。テストスイートが分割されて並列化され、85パーセンタイルは2か月以内に92分から41分に下がります。レビューの当番表が負荷を二人の上級レビュー担当者の外に広げ、85パーセンタイルの待ちは14時間に下がります。三つのチームは、会議のない週次のブロックに合意し、一つのチームは計画外の依頼が届く方法を見直します。請求計算サービスは、ペアリングと文書を伴う共有の学習プロジェクトになり、その認知負荷の評価は二四半期で3.5に下がります。報告された集中時間は約4時間に上がります。

上級マネージャーが再び個人別のコミット数を求めると、エンジニアリング効果の責任者はSPACEとDevExの研究を説明し、条件のダッシュボードを提案します。判断は、個人の活動が評価に使われないというプライバシーの規則とともに記録されます。あるチームは、今四半期は健全性の確認の結果をリーダーシップ向けに要約しないよう求め、その要求は認められます。関わったチームの離職率は翌年に下がり、彼女は、そのつながりを証明できず、主張もしないと記します。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

フィードバックのループや集中時間などの条件をチームとともに測り、それが明らかにする障害を取り除きます。注意点は、数字を人の順位付けに使うと、データが壊れることです。

### AI

AIのコーディングと文章のアシスタントは、良くも悪くも、フィードバックのループと認知負荷を変えます。チームに便益と負担を尋ね、利用を手戻りとウェルビーイングと組にします。注意点は、個人別に報告される利用統計は、監視に変わることです。

### 自動化

ビルド、テスト、レビューの時間の収集を自動化し、ツールチェーンを遅さと失敗で測ります。注意点は、速いツールも遅い組織を隠しうるため、データをチームとの対話と組み合わせることです。

### アナリティクス

傾向をチーム別に回答数とともに示し、最小のグループサイズを設定します。これが情報を与える判断は、次にどの障害を取り除くかです。注意点は、小さなチームは匿名にできないことです。

## 業種別の視点

**スタートアップ。** 皆が皆を知っているので、アンケートより対話が勝ります。主なフィードバックのループの時間を測り、ビルドを速く保ち、少数の人が多くを担うため、持続不可能なペースのしるしに注意します。大きなアンケートのプログラムを持ち込まないでください。

**中小企業。** 小さなチームは、構築とサポートの両方を行う一人か二人かもしれません。主なリスクは中断と個人への依存です。単純な障害の一覧を保ち、不在のカバーを確保し、何が妨げになっているかを互いに定期的に尋ねます。個人レベルのデータは本質的に特定可能なので、対話に頼ります。

**大企業。** 規模は多様性と比較の誘惑をもたらします。チームが自分たちの健全性の確認を所有できるようにしながら、共通のツールキット（パルスの質問、ループの計測）を提供します。注意して集約し、修正を広げるためにチーム間でパターンを共有し、ランキングを外します。そのような機関があれば、労使協議会や従業員の代表を関与させます。

**政府・公共部門。** 調達、セキュリティの規則、承認の連鎖がフィードバックのループを長くし、スタッフは監視について強い保護を持つかもしれません。ループを測り、データの規則の設定に代表を関与させ、所見を使ってプロセスを簡素化します。サービスの価値に動機づけられた公務員は、目に見える障害の除去から恩恵を受けます（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは、健全性の確認とパルスのためのチームの時間、パイプラインとレビューツールの少しの計装、結果の解釈と進行を助けるアナリストまたはコーチ、障害を取り除くエンジニアリングの時間です。これらのコストのほとんどは、多くの人々にわたって掛け合わされる遅いループのコストに比べて小さいものです。

見返りは、取り戻された時間、少ない手戻り、より良い定着、より速い学びから来ます。自分たち自身のデータから見積もります。グループ全体でビルドとレビューの待ちで毎週失われる時間、去る人々を置き換えるための採用とオンボーディングのコスト、過負荷のチームに結び付いたインシデントや欠陥のパターン。分をお金に変えることには慎重になり、前提を述べます。方法と適合をたどれない限り、公表された研究の生産性向上の主張は避けます。間違えたときのコストを忘れないでください。監視と見られるプログラムは、信頼と、その後のあらゆるアンケートの質を損ないます（トピック 7.7「投資対効果とビジネスケース」を参照）。

## アンチパターンと落とし穴

- **個人の生産性ダッシュボード。** 活動を測り、悪用を招き、信頼を損なう。チームのレベルで条件を測る。
- **健全性の確認のスコアでチームを比較する。** チームがスコアを管理するようになる。チームに結果を所有させる。
- **行動のないアンケート。** 人々は答えるのをやめる。各周期で目に見えるものを直す。
- **オンラインの時間や在席を測る。** 可視性を報い、集中を罰する。ループと障害を測る。
- **すべてに一つの測定値。** 絵のほとんどを見逃す。複数の次元をカバーする。
- **裾を無視する。** 中央値は痛手となる遅いループを隠す。パーセンタイルを報告する。
- **システムの問題で人を責める。** 障害は通常、構造的である。構造を直す。
- **熱くなって走ることを通常とする。** 永続的な緊急は人を燃え尽きさせる。持続した過負荷を、計画の失敗として扱う。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| 条件の理解 | 逸話 | 時折のアンケート | フィードバックのループ、負荷、フローについての定期的な対話とパルス | 認識とワークフローのデータを組み合わせ、チームレベルの傾向がある | チームと供給者にまたがる条件の共有の見方。チームが測定値を共同設計する |
| オーナーシップと倫理 | 経営層がすべてを読む | 非公式な配慮 | チームが所有する健全性の確認。書面のプライバシーの規則 | 代表とともに規則をレビューする。個人への利用の禁止が徹底される | 規則と実践が独立して監査される。チームがデータの共有を制御する |
| 行動 | 苦情が対処されない | アドホックな修正 | オーナーを伴う障害の一覧。周期ごとに一つか二つの修正 | 修正が追跡され成果に結び付く。持続可能なペースが監視される | 障害の除去が計画に組み込まれる。学びが広く共有される |

## チェックリスト

- [ ] チームが、何が自分たちを遅くするかを自分たちの言葉で述べている。
- [ ] フィードバックのループ、認知負荷、フローのそれぞれを、少なくとも一つの認識の質問と一つのシステムの測定値がカバーしている。
- [ ] 測定値が少なくとも三つのSPACEの次元から来ている。
- [ ] 各チームが自分たちの健全性の確認を所有し、結果を最初に読む。
- [ ] フィードバックのループ時間が、中央値と85パーセンタイルとして報告されている。
- [ ] オーナーを伴う見える障害の一覧があり、解決時間が追跡されている。
- [ ] 結果が、最小のグループサイズでチームのレベルで報告されている。
- [ ] 個人のデータが評価に使われないことを述べた書面のプライバシーの規則がある。
- [ ] 活動の件数が生産性として報告されていない。
- [ ] チームが周期ごとに少なくとも一つの修正を目にする。

## AIプロンプト

**DevExの三つの次元のためのパルスの質問を起案する。**

```text
[チームの種類] のための、フィードバックのループ、認知負荷、フロー状態をカバーする、六問以内の短いパルスを起案してください。中立の言葉遣い、一貫した尺度、一つの自由記述を使ってください。各質問について、比較できる対応するシステムの測定値を提案してください。研究結果を主張しないでください。前提と、質問が誤読されうる方法を列挙してください。
```

**障害の一覧のパターンを分析する。**

```text
以下は直近の [期間] のチームの障害の一覧で、挙げられた日付、解決された日付、短い説明を伴います：[無害化して貼り付け]。障害を原因別にグループ化し、長く残るアイテムとパターンを指摘し、最初に取り組む一つか二つとその理由を示唆してください。動機を推測したり、個人の名前を挙げたりしないでください。前提と、チームが確認すべきことを列挙してください。
```

**チームの健全性プログラムのプライバシーの規則を書く。**

```text
[組織の種類] のチームの健全性と開発者体験のプログラムの、1ページの規則を起案してください。何が集められるか、目的、誰が何を見るか、最小のグループサイズ、保持、個人のデータが業績評価に使われないという約束、スタッフが懸念を挙げる方法をカバーしてください。法務、プライバシー、従業員の代表とレビューすべきことに印を付けてください。法的な結論を出さないでください。前提を列挙してください。
```

**条件を成果と比較する。**

```text
[数] のチームについて、条件の測定値（フィードバックのループ時間、認知負荷の評価、集中時間）と成果の測定値（サイクルタイム、変更失敗率、インシデント）があります：[表を貼り付け]。パターンを述べ、データが何も結論できないほど疎な箇所を述べ、チームとテストする仮説を示唆してください。因果を主張しないでください。前提と注意を列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：チームの健全性または開発者体験のメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：人に関するメトリクスの項目が、悪用の手口、防護柵、プライバシーの規則を備えているかを確認するときに使います。

## 要点

- 人々が働く条件を測る。フィードバックのループ、認知負荷、フロー。
- 人々が言うこととシステムが記録することを組み合わせ、食い違いを見る。
- チームに自分たちの健全性の確認を所有させ、チームのレベルで報告し、データを個人に使わない。
- 活動の件数を生産性の代わりとして避ける。
- 一度に一つか二つの障害に目に見える形で行動し、障害が解決するまでの時間を追跡する。
- チームが無期限に保てるペースを守る。
