# FinOpsとクラウドコストのメトリクス

**クラウドの支出は、エンジニアが毎日決めている。したがって、サービスを構築し運営する人々に、コストのデータ、文脈、それに基づいて行動する権限を与え、信頼性に払うのと同じ注意で、無駄、配賦、ユニットコストを測る。**

## 概要と動機

データセンターでは、支出は発注書によって決められ、いくつかの大きな段階として到来します。クラウドでは、開発者が数行の設定で組織に継続的な課金をコミットさせることができ、忘れられたテスト環境が何か月もお金をかけ続けることがあります。[クラウドコンピューティング（cloud computing）](https://en.wikipedia.org/wiki/Cloud_computing)は、計算資源へのオンデマンドのアクセスを提供し、それに伴う[従量課金（pay-as-you-go）](https://en.wikipedia.org/wiki/Pay_as_you_go)のモデルは、請求書が利用に従うことを意味します。それは強力で、同時にリスクがあります。チームが数分でスケールできる同じ柔軟性が、誰も気づかないよりも速くコストを増やさせます。

FinOpsは、財務（finance）と運用（operations）の短縮形で、クラウドのコストを管理するための実践であり文化です。FinOps Foundationは、それを、エンジニアリング、財務、調達、事業のチームが、データに基づく支出の判断で協働する運用のフレームワークとして記述しています。その中心的な考え方は、クラウド資源を使う人々が自分たちのコストを見て所有するべきであり、財務が構造、予測、コミットメントを提供するというものです。これは、ステークホルダー間の継続的な協働と、自分たちのサービスを所有するチームというアジャイルの狙いに合い、サービス財務管理に対するITILの関心にも合います。このトピックは、その実践を具体的にする測定値を扱います。前のトピックの一般的な原価計算の考え方の上に築かれています（トピック 7.5「サービスコストとユニットエコノミクス」を参照）。

クラウドのコストには、独自の測定値を要する特徴があります。

- **弾力性。** [オートスケーリング（autoscaling）](https://en.wikipedia.org/wiki/Autoscaling)は資源を需要に合わせて調整し、それがコストを変動させ、時に驚くものにする。[サーバーレスコンピューティング（serverless computing）](https://en.wikipedia.org/wiki/Serverless_computing)は、実行ごとに課金し、注意をサーバーからリクエストに移す。
- **多くの小さな判断。** インスタンスの大きさ、ストレージの階層、リージョン、アーキテクチャの各選択がコストを変える。支出は多くの人が下す何百もの判断に分散しており、タグと良いレポートなしには見えにくい。
- **価格モデル。** オンデマンドの価格は柔軟で、最も高い。予約容量やセービングプランのような[ボリュームディスカウント（volume discount）](https://en.wikipedia.org/wiki/Volume_discount)と引き換えのコミットメントは、利用の約束と引き換えに単価を下げる。スポットまたは中断可能な容量は安く、回収されうる。各モデルにはリスクがあり、適切な組み合わせは、ワークロードがどれだけ予測可能かに依存する。正確な条件はプロバイダーによって異なり、頻繁に変わるので、詳細に頼る前に現行のプロバイダーの文書を確認する。
- **共有でタグのないコスト。** オーナーや目的のタグのない資源は帰属できない。共有プラットフォームは、異なる形で消費するチーム間にコストを分散させる。
- **環境コスト。** クラウドのワークロードはエネルギーを消費し排出を引き起こし、ワークロードの[カーボンフットプリント（carbon footprint）](https://en.wikipedia.org/wiki/Carbon_footprint)は、報告を求められることが増えている。それを見積もる方法はまだ発展しており、数字は方法とともに示すべきである。

クラウドのコストの測定値は、近道で簡単に良く見せられます。監視を止める、あるいはサービスが倒れるまで資源を縮めることで支出を削れば、請求書は低く、サービスは悪くなります。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵が当てはまります。ここのすべてのコストの測定値は信頼性や品質の測定値の隣に置かれ、請求書でチームに順位を付けることはありません（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

## 主要な原則

- **コストはエンジニアリングのメトリクスである。** サービスを構築し運営するチームが、そのコストを見て、所有する。
- **オーナーに配賦する。** すべての1ドルは、チームか宣言された共有プールに対応づけられるべきである。
- **コストを品質と信頼性と組にする。** サービスを壊す節約は、節約ではない。
- **継続的に、小さなステップで最適化する。** 無駄を定期的にレビューし、通常の仕事の一部として行動する。
- **範囲で予測する。** 変動する需要は、単一の数字の予測を脆くする。
- **機能を越えて協働する。** エンジニアリング、財務、調達、事業が一緒に決める。
- **請求書でチームに順位を付けない。** サービスは異なり、成長は無駄ではない。

## 推奨事項

### コストを見えるものにし、所有させる

**1. 小さな必須のタグの集合を強制する。** すべての資源に、オーナー、サービス、環境のタグを持たせることを求め、事後の整理ではなく、作成時にポリシーで強制します。配賦の網羅率が、これがどれだけうまく機能しているかを測ります。タグ付けに失敗する資源はブロックするか、1日以内にアカウントのオーナーにフラグ付けできます。人々が従うよう、タグの集合を小さく保ちます。

**2. チームに自分たちのコストの見方を与える。** 各チームに、サービスと環境別の支出の、傾向と異常を伴う日次または週次の見方を提供します。人々は、見て理解できるデータに反応します。月次で財務にしか行かないレポートは、ほとんど何も変えません。

**3. 共有コストのプールとそのドライバーを定義する。** 共有プラットフォーム、ネットワーク、サポート料金には、どう分けるかの規則が要ります（トピック 7.5「サービスコストとユニットエコノミクス」を参照）。規則を公開し、チームとレビューし、プールを小さく保ちます。人々がたどれる規則は、誰も理解しない公正なものより多くの信頼を得ます。

**4. 短い定期的なコストの対話を持つ。** エンジニアリング、財務、プロダクトオーナーを、大きな支出者には毎週または隔週、他には毎月、30分、安定した頻度で集めます。傾向、異常、最適化のバックログをレビューします。これは実践における継続的な協働であり、重いプロセスなしにコストを議題に保ちます。

### 支出だけでなく、価値を測る

**5. 単位あたりのコストで表現する。** クラウドの総支出は、成功とともに上がります。重要なのは、アクティブな顧客あたり、取引あたり、ビルドあたりのコストです。サービスにとって意味のある単位を選び、時間とともに追跡し、変更に注釈を付けます。総支出が上がりながら下がる単位コストは健全なパターンで、利用が横ばいの中で上がる単位コストは、調査への促しです。

**6. コストの隣に、信頼性と品質を示す。** コストを同じサービスの可用性、レイテンシ、エラー率とともに表示します（トピック 5.2「SLI、SLO、エラーバジェット」を参照）。エラー率を上げるコスト削減は、ユーザーへのコストの転嫁です。エラーバジェットのアプローチは、トレードオフを明示にできます。サービスが必要よりはるかに良いときは支出を減らし、そうでないときは投資する。

**7. 明示的な規則で無駄を追跡する。** 遊んでいる（たとえば、ある期間に意味のある利用がない）と、過大（たとえば、プロビジョニングされた容量よりはるかに低い使用率が一貫している）を定義し、それぞれへの支出を報告します。規則には注意が要ります。耐障害性のための待機システムは設計上遊んでいるように見えるため、除外してラベル付けすべきです。規則が誤検知を生むときは、見直します。

### 見つけたものに行動する

**8. 通常の仕事の中でサイズを適正化し、整理する。** 無駄の除去を、チームのバックログの常設の項目にし、継続的改善の一部として小さなステップで取り組みます。本番外の環境を勤務時間外に停止するよう予定し、接続されていないストレージを削除し、適切なストレージの階層を選び、最大の明細項目を先にレビューします。小さな定期的な変更は、圧力が高まると忘れられがちな、まれな英雄的な整理に勝ります。

**9. 価格モデルをワークロードに合わせる。** 定常的なベースラインの利用にはコミットメント、変動する負荷にはオンデマンド、中断に耐える仕事には中断可能な容量を使います。少量ずつ段階的にコミットし、網羅率と利用率の両方を追跡します。過剰なコミットメントはお金を無駄にし、過小なコミットメントは割増を払います。財務と調達を関与させ、条件は変わるのでプロバイダーとともに再確認します。

**10. 異常を検出して対応する。** 支出に異常検出を使い、ベースラインに対する急な変化にフラグを付けます。[異常検出（anomaly detection）](https://en.wikipedia.org/wiki/Anomaly_detection)のツールには、単純な閾値から統計モデルまでの幅があります。オーナーのチームにアラートを出し、確認応答して判断するまでにかかる時間を測ります。設定を誤ったジョブは数時間で大きな請求を積み上げうるので、速度が重要です（トピック 5.5「監視とアラート品質のメトリクス」を参照）。

### 予測し、計画する

**11. ドライバーと範囲で予測する。** 予想されるユーザー数や取引数などの需要のドライバーを、単位コストとともに使って予測を構築します。[差異分析（variance analysis）](https://en.wikipedia.org/wiki/Variance_analysis)を使って、予測と実際の違いを説明し、ボリューム、価格、ミックスによるものを分けます。範囲を示し、前提を述べます。予測の差異は、モデルが改善するにつれて縮むはずです。

**12. サステナビリティを絵に含める。** プロバイダーのレポートや公表された方法論など、文書化された方法を使って、主要なワークロードに関連する排出量を見積もり、見積もりの限界を述べます。リージョン、インスタンスの種類、スケジュールの選択を、コストと排出量の両方で比較します。単位あたりの排出量を、単位あたりのコストの相棒として扱い、方法が支えられない精度を主張しません。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 配賦の網羅率 | すべてを万能のオーナーにタグ付けする、大きな金額を共有として宣言する | 万能のオーナーが持つ支出の割合。共有プールの大きさとレビュー。オーナー確認の抽出 |
| クラウドの単位コスト | 安く増える単位を選ぶ、コストを削るために信頼性を削る | 固定の単位の定義。信頼性と品質の相棒 |
| 無駄の率 | 「遊んでいる」の定義を狭める、範囲外のアカウントに無駄を移す | 台帳にある規則。すべてのアカウントをスキャンする。規則が除外する資源を抽出する |
| コミットメントの網羅率 | 高いパーセンテージを追うために、水増ししたベースラインにコミットする | コミットメントの利用率。ベースラインを利用の履歴と照らして確認する |
| コミットメントの利用率 | コミットメントを満たすために、必要のない対象の利用を加える | 実際の需要の成長と比較する。単位コスト |
| 予測の差異 | 予測に余裕を上乗せする、遅くに修正する | 開始時に予測を記録する。範囲の幅と的中率を追跡する |
| 異常への確認応答時間 | 見ずにアラートを確認応答する、アラートを自動でクローズする | 判断と結果を記録する。対応の質についてアラートを抽出する |

健全な読みは、ほぼすべての支出が所有され見えていて、説明のつく理由で動く単位コスト、障害なしに縮む無駄、使われているコミットメント、そして時間とともに誤差が狭まる予測です。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| 中央のクラウドチームが支出を統制する | 一貫性と交渉力 | 遅い。エンジニアリングの判断から遠い |
| チームが自分たちのクラウドコストを所有する | 速く、情報に基づく判断 | データ、研修、防護柵が要る |
| オンデマンドのみ | 柔軟 | 単価が最も高い |
| 重いコミットメント | 単価が低い | 需要が減るとロックインと無駄 |
| 厳格な予算の上限 | 超過を防ぐ | 停止を引き起こしたり、正当な仕事をブロックしたりしうる |
| アラートとレビュー | 速度を保つ | 適時の応答に依存する |
| 積極的なサイズの適正化 | お金を節約する | やりすぎるとパフォーマンスへのリスク |
| SLOを伴う測定されたサイズの適正化 | バランスが取れている | 信頼性のデータと注意が要る |

散文での答えは、チームにデータとオーナーシップを与え、サービスが重要なところでは、厳格な停止ではなくアラートや予算などの防護柵を設定し、定常的なベースラインに段階的にコミットし、常にコストを信頼性と組にすることです。

## チームで話し合う問い

**1. クラウドの請求書のどれだけを、今日オーナーに帰属させられるか、そして誰が見つからないか？**
有効なタグを持つ支出の割合と、最大のタグのない項目を見ます。それぞれを誰が所有するかを尋ねます。ファシリテーターは、誰も主張しない項目がいくつあるかに注意してください。作成時に強制するタグポリシーのステップを一つ合意します。

**2. 直近6か月で、単位あたりのコストはどう動き、それはなぜか？**
単位コストをグラフにし、アーキテクチャ、価格、ボリュームの変更に注釈を付けます。どの変更が意図したものだったかを尋ねます。傾向が驚きなら、どんなデータが欠けているかを話し合います。グラフに品質の測定値を加えます。

**3. 思い切れるなら、明日どの資源を止めるか？**
候補を列挙します。遊んでいる環境、過大なデータベース、忘れられたストレージ。それぞれについて、リスクは何で、誰が決めるかを尋ねます。まずスケジュールやスナップショットを取るなど、一つを取り除くことを試す安全な方法に合意します。

**4. ジョブのコストが10倍になり始めたら、1日以内にどうやって分かるか？**
請求書からオーナーまでのアラートの経路を通して確認します。過去の例でテストします。対話は、遅れとオーナーシップのギャップを明らかにするはずです。確認応答と判断の目標時間と、担当者を合意します。

**5. ベースラインの利用のどれだけを安全にコミットでき、何が私たちを間違いにするか？**
定常的な下限の利用履歴と、それへのリスクを調べます。プロダクトの変更、移行、価格の変更。最初の控えめなコミットメントとレビュー日を決めます。対話に財務を含めます。

**6. コストと信頼性の間で、偶然どんなトレードオフをしているか？**
最近の節約とインシデントをレビューします。関係するものはあったか。たとえばコストのレビューをエラーバジェットに結び付けることで、トレードオフを明示にする方法を話し合います。信頼性に影響する削減を、誰が承認できるかを決めます。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、コストを動かす判断を下し、それを減らすのに最適な立場にあります。作成時にタグ付けし、コストの見方を定期的に確認し、設計の議論にコストを組み込み、無駄の削減を通常の仕事として扱うべきです。変更の効果を、行った後すぐにコストに見られるべきで、それは速い学びを支えます。

### サービスと運用のチーム

運用とプラットフォームのチームは、共有サービスを運営し、ポリシーを強制し、異常アラートを運用します。タグの遵守を簡単に保ち、セルフサービスのレポートを提供し、共有コストの明確な規則を公開するべきです。提供するプラットフォームのコストと信頼性の両方を見て、関門にならずにチームが行動する助けになるべきです。

### リーダーシップとガバナンス

リーダーと財務は、予測可能な支出と良い価値を望みます。コストの仕事のツールと時間に資金を付け、予測の範囲を受け入れ、チームのランキング表を避け、品質の隣に単位コストを求めるべきです。ガバナンスは、コミットメントがデータで行われ、サステナビリティの主張が方法を述べていることを確認するべきです。

### 顧客とユーザー

ユーザーは、クラウドコストを間接的に、価格、機能、サービスの安定性を通じて感じます。節約が改善に資金を付けるときに恩恵を受け、削減が品質を下げるときに被害を受けます。利用量に対して課金されるユーザーは、明確な請求書と、それに影響できることを望みます。

## 実践：サービスマネジメントの例

地域のオンライン小売業者が、六つのエンジニアリングチームで、パブリッククラウド上で店舗と注文基盤を運営しています。以下の数字は例示です。

クラウドの支出は1年間着実に上がり、財務責任者は削減を求めます。FinOpsのリードが請求データを引きます。配賦の網羅率は68パーセントで、タグのない支出の3分の1はテストアカウントにあります。完了した注文あたりのコストは0.31米ドルで、6か月前の0.27米ドルから上がり、その間に注文量は15パーセント増えました。チームの規則による無駄の率は、範囲内の支出の14パーセントで、ほとんどは夜間と週末に動く本番外の環境と、いくつかの過大なデータベースです。コミットメントの網羅率は定常的なベースラインの20パーセントで、購入したものの利用率は97パーセントです。直近の四半期のプラス18パーセントの予測の差異は、プラットフォームチームに誰も伝えていなかったマーケティングキャンペーンに続きました。一つのアカウントで暴走したデータのジョブが、誰も気づく前に2日間動きました。

リードは、エンジニアリングチームと四つの変更に合意します。タグポリシーが、オーナーとサービスのタグのない新しい資源をブロックし、2週間の猶予期間を設けます。各チームが週次のコストの見方と、隔週のコストの対話の中の短い枠を受け取ります。本番外の環境は勤務時間外に停止するよう予定され、三つの過大なデータベースは、サービスレベル目標に照らしてパフォーマンスを確認した上でサイズが変更されます。最初のコミットメントは定常的なベースラインの60パーセントをカバーし、3か月後にレビューします。異常アラートは、4時間以内に記録された判断を期待して、オーナーのチームに行き、計画カレンダーは今ではマーケティングキャンペーンを含みます。

一四半期後、配賦の網羅率は93パーセント、無駄の率は6パーセントに下がり、注文あたりのコストはチェックアウトのレイテンシやエラー率の変化なしに0.26米ドルに下がり、予測の差異はプラス5パーセントです。コミットメントの網羅率は55パーセントで、利用率は96パーセントです。異常への確認応答時間の中央値は2時間で、85パーセンタイルは6時間です。財務責任者は、チームごとのコストを示すランキング表を求めます。FinOpsのリードは、チームが異なる成長を伴う異なるサービスを運営していることを説明して断り、代わりに各チームの単位コストの傾向と信頼性の測定値を提案します。判断は記録され、次のレビュー日が設定されます。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

エンジニアにコストのデータと行動する権限を与え、信頼性と同じ頻度でレビューします。注意点は、文脈なしに設定されたコストの目標は、信頼性を下げたり、有用な仕事を遅らせたりすることです。

### AI

AIサービスはクラウドコストの急速に増える割合になりうるので、独自の配賦、単位コスト、異常アラートを与えます。リクエストあたりのコストを、答えの品質と届けられた価値と組にします。注意点は、より弱いモデルに切り替えてAIのコストを削ると、人による手戻りが増えうることです。

### 自動化

タグ付けの確認、異常アラート、サイズ適正化の提案を自動化し、自動化を誤警報と、実際に実現した節約で測ります。注意点は、遊んでいる資源の自動の停止が、必要だったものを取り除きうることです。

### アナリティクス

単位コストと無駄を、予測の差異とデータの鮮度とともに示します。これが情報を与える判断は、どこを最適化し、何にコミットするかです。注意点は、コミットメントの判断は予測に依存するため、その不確実性を述べることです。

## 業種別の視点

**スタートアップ。** クレジットと低い請求書は、規模が大きくなると高くつく悪い習慣を隠しうるものです。初日からタグを付け、本番外の資源をスケジュールし、顧客あたりのコストを早期に追跡します。需要が予測可能なときにのみコミットします。

**中小企業。** 単一のアカウントと少数のサービスが、タグ付けとレビューを単純にします。請求書をシステムを構築する人と毎月レビューし、忘れられた資源を取り除き、長いコミットメントには注意します。予算アラートは、最も価値のある単一の統制です。

**大企業。** 多くのアカウント、チーム、プロバイダーは、チームを統制するのではなく可能にする、中央のFinOps機能を要求します。プロバイダー間でタグと請求のエクスポートを標準化し、コミットメントを中央で交渉し、チームに自分たちのデータを与えます。マルチクラウドのレポートの違いに備えます。

**政府・公共部門。** 調達の枠組み、データの所在、固定された年間の予算が選択を制約します。コストとリージョンの判断を文書化し、変動する支出が充当にどう影響するかをモデル化し、監査証跡を保ちます。サステナビリティについての公的なコミットメントは、方法とともに報告された排出量を要求するかもしれません（トピック 8.5「規制対応・行政向け報告」を参照）。

## ビジネスケース：動機、ROI、TCO

FinOpsの実践のコストは、レポート、タグのポリシー、定期的な対話を運営する数人の時間、クラウド基盤が提供するか購入されるツール、所見に基づいて行動するエンジニアリングの時間です。小さな実践は、請求のエクスポートとスプレッドシートで始められます。

見返りは、減った無駄、コミットメントによるより良い価格、少ない驚き、アーキテクチャについてのより良い判断から来ます。自分たち自身の数字からケースを築きます。最初のレビューでの無駄の率とそのコスト、本番外の環境のスケジュールによる節約、コミットした部分へのコミットメントの割引、早期に捉えた異常の避けられたコスト。たどれる出典と方法なしに、業界全体の無駄のパーセンテージや節約の数字を引用するのは避けます。実践のコストと、過剰なコミットメントのリスクを含めます。改善一般の財務的なケースは、次のトピックで扱います（トピック 7.7「投資対効果とビジネスケース」を参照）。

## アンチパターンと落とし穴

- **ノーと言う中央のチーム。** 仕事を遅くし、チームはそれを回避する。データと防護柵でチームを可能にする。
- **信頼性を見ずにコストを削る。** 節約はインシデントとして返ってくる。コストをサービスレベルの測定値と組にする。
- **コミットメントの網羅率を追う。** 利用率の低い高いパーセンテージは無駄である。両方を追跡する。
- **財務だけへの月次のレポート。** エンジニアはそれを決して見ない。チームに日次または週次の見方を与える。
- **整理プロジェクトとしてのタグ付け。** 劣化する。作成時にタグを強制する。
- **支出でチームに順位を付ける。** 成長が無駄に見える。文脈とともに単位コストの傾向を示す。
- **単一の数字を予測する。** 変動する需要がそれを壊す。範囲とドライバーを使う。
- **正確な排出量を主張する。** 見積もりの方法は不確かである。方法と限界を述べる。

## チェックリスト

- [ ] 小さな必須のタグの集合（オーナー、サービス、環境）が、資源の作成時に強制されている。
- [ ] 配賦の網羅率が、最大のタグのない項目を列挙して、毎週報告されている。
- [ ] 各チームに、傾向と異常を伴う週次のコストの見方がある。
- [ ] エンジニアリングと財務の定期的なコストの対話がカレンダーにある。
- [ ] クラウドの単位コストが、可用性、レイテンシ、エラー率の隣で追跡されている。
- [ ] 無駄の規則が書き下され、除外がラベル付けされて適用されている。
- [ ] コミットメントが、定常的なベースラインの利用に対して段階的に行われ、網羅率と利用率が追跡されている。
- [ ] 予測がドライバーと範囲を使い、差異が分析されている。
- [ ] 異常アラートが、判断までの期待時間とともにオーナーに届く。
- [ ] 排出量の見積もりを報告する場合は、その方法と限界を述べている。

## AIプロンプト

**コストの傾向を分析する。**

```text
以下は、[期間] の [サービス] のクラウドのコストと利用の要約です：[月次のコスト、ボリューム、既知の変更を貼り付け]。データが許す限り、コストの変化をボリューム、価格、ミックスの効果に分け、次に何を確認すべきかを示唆し、品質の相棒を伴う単位コストを提案してください。価格や割引を捏造しないでください。前提と、より確実にするために必要なデータを列挙してください。
```

**タグポリシーを起案する。**

```text
[クラウドプロバイダー] を使う [組織の種類] のタグポリシーを起案してください。最小限の必須のタグ、許される値、作成時にどう強制するか、違反をオーナーにどう報告するか、猶予期間を含めてください。エンジニアが従えるほど短くしてください。前提と、現行の文書で私が確認すべきプロバイダーの機能に依存するものを列挙してください。
```

**無駄の規則を定義する。**

```text
[環境の種類] で、クラウドの資源を遊んでいる、または過大と分類する規則を、使うメトリクス、時間の窓、除外（たとえば耐障害性の待機）、誤検知のレビューのプロセスを含めて提案してください。信頼性を損なうのをどう避けるかを述べてください。自分たちのデータからどう較正するかを述べずに、数値の閾値を設定しないでください。前提を列挙してください。
```

**最初のコミットメントを計画する。**

```text
直近の [期間] の私たちの定常的なベースラインの利用は [要約] で、需要のリスクは [一覧] です。最初のコミットメントのための慎重な計画の概要を示してください。ベースラインの見積もり方、どれだけコミットするか、利用率をどうレビューするか、何が私たちを止めさせるか。特定のプロバイダーの割引や条件を仮定しないでください。前提と、財務や調達への問いを列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：クラウドコストのメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：クラウドコストのメトリクスの項目が、悪用の手口、防護柵、信頼性の相棒を備えているかを確認するときに使います。

## 要点

- コストを見えるものにし、所有させる。作成時にタグを強制し、各チームに自分たちの週次の見方を与える。
- 単位あたりのコストを、信頼性と品質の隣で測り、単独では決して測らない。
- 書面の規則に導かれ、通常の仕事の一部として無駄を取り除く。
- 定常的なベースラインに段階的にコミットし、網羅率と利用率の両方を追跡する。
- ドライバーと範囲で予測し、異常を速い対応で見張る。
- 支出でチームに順位を付けず、排出量の見積もりの方法と限界を述べる。
