# 協働と引き継ぎのメトリクス

**仕事は、持ち主が変わるところで遅くなり、質が下がる。したがって、引き継ぎ、その間の待ち、特定の個人への依存を測り、誰が誰と話しているかを数えるのではなく、数字を、適切な人々を集めるために使う。**

## 概要と動機

アジャイル宣言の原則は、ビジネスの人々と開発者が、プロジェクトの全体を通じて毎日一緒に働かなければならないと述べています。その背後にある観察は古く、頑健です。サービス組織の遅れの大半は、人々がゆっくり働くことからは来ません。人々の間で仕事が待つことから来ます。リクエストはサービスデスクから第二線のチームへ、アプリケーションのチームへ、データベース管理者へと動き、各ステップでキューに入り、文脈を失い、差し戻される危険があります。関わる人々はそれぞれ素早いかもしれません。システムが遅いのです。

ITILによって体系化されたITサービスマネジメント（ITSM）は、長い間、サポートを階層とチームに組織し、エスカレーションを、問題をそれを解決できる誰かに動かす仕組みとしてきました。その構造には便益があります。専門化、明確なオーナーシップ、制御されたアクセス。また、引き継ぎを生み、引き継ぎにはコストがあります。アジャイルとDevOpsの実践は、より多くの仕事をエンドツーエンドで担うクロスファンクショナルなチームを築き、リアルタイムでの協働を促すことで応えます。二つの伝統は、似た結論に達します。より少ない引き継ぎ、その間のより短い待ち、そして問題を一緒に解決できる人々が、その上で働くこと。

測定に役立つ考え方がいくつかあります。

- **引き継ぎとキュー。** 仕事があるチームから別のチームに渡るたびに、通常キューで待つ。待つ時間は、働く時間よりはるかに大きいことが多い。これが、前に導入したフロー効率が通常低い理由である（トピック 2.2「リードタイム、サイクルタイム、フロー効率」を参照）。[ボトルネック（bottleneck）](https://en.wikipedia.org/wiki/Bottleneck_(production))は、プロセス内の容量が限られた点で、全体のスループットを決める。
- **構造がコミュニケーションを形作る。** [コンウェイの法則（Conway's law）](https://en.wikipedia.org/wiki/Conway%27s_law)は、組織が自らのコミュニケーション構造を映すシステムを設計すると述べる。逆もまた実際的である。依存関係の少ないシステムを望むなら、チーム間の依存関係を減らすようにチームを配置する。チームの境界は引き継ぎを作り、引き継ぎはアーキテクチャを形作る。
- **依存関係。** [依存関係（dependency）](https://en.wikipedia.org/wiki/Dependency_(project_management))は、ある仕事が別のものが終わるまで進められない関係である。チーム間の依存関係は遅れの主な源で、マップし、数え、減らすことができる。
- **調整のコストは人とともに増える。** フレデリック・ブルックスのソフトウェアプロジェクトについてのエッセイからの[ブルックスの法則（Brooks's law）](https://en.wikipedia.org/wiki/Brooks%27s_law)は、遅れているプロジェクトに人を加えるとさらに遅れうると観察し、それは部分的にコミュニケーションのオーバーヘッドが増えるからである。対話の人数が多いことは、自動的に良いわけではない。
- **個人への依存。** [バスファクター（bus factor）](https://en.wikipedia.org/wiki/Bus_factor)は、プロジェクトを止めるのに、利用できなくなる必要のある人数で、通常、知識が一人の頭の中にあるときのリスクを指摘するために使われる。それは知識の分布の性質であり、個人の評価ではない。

協働の測定値には暗い面があります。メッセージ、会議、ネットワークのリンクを数えることを協働の測定値とするのは簡単で魅力的であり、すぐに人々のコミュニケーションの監視に滑り込みます。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵は、グループとプライバシーに当てはまります。「協働」が目標になると、人々は見える活動を生み、それが監視になると、公然と話すのをやめます（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。したがって、ここの測定値は、作業アイテム、引き継ぎ、依存関係、チームレベルのパターンを見ます。メッセージを読んだり、個人に順位を付けたりしません。

このトピックは、第2部のフローの測定値、第3部のインシデントとリクエストの測定値、前の部の供給者との引き継ぎに結び付きます（トピック 8.4「サプライヤーと契約のメトリクス」を参照）。

## 主要な原則

- **会話ではなく、仕事を測る。** 引き継ぎ、待ち、依存関係は、作業アイテムとチームの性質である。
- **より速い引き継ぎより、より少ない引き継ぎ。** 最良の引き継ぎは、起きないものである。
- **適切な人々を集める。** リアルタイムの協働は、待ちの連鎖全体をしばしば取り除く。
- **依存関係を見えるものにし、減らす。** それらをマップし、数え、最も痛手となるところでチームの境界やアーキテクチャを変える。
- **意図して知識を広げる。** 知識の単一の点はリスクであり、共有は設計の活動である。
- **集中を守る。** すべての時間を会議で埋める協働は、仕事をする時間を壊す。
- **ステークホルダーを継続的に関与させる。** 数時間で答えられる質問は、週次の会議で集められる答えよりよく役立つ。

チーム、キュー、サービスのレベルで集約し、個人別には決して報告しません。引き継ぎの回数は、オーナーのチームを変えない自動の割り当てを除外します。待ちの割合は、アイテムが受け手のチームに割り当てられたときに始まり、その最初の記録された行動で終わります。知識の網羅は、コンポーネントを運用できる人についてのチーム自身の判断を使い、チームとレビューし、個人に順位を付けません。協働のデータは、メッセージを読むのではなく、アイテムのタグと記録から来ます。

## 推奨事項

### 引き継ぎをマップする

**1. 典型的なアイテムの経路を描く。** 一般的な種類のリクエストまたはインシデントを選び、最初の接触から解決までの経路をたどります。各チーム、各キュー、各待ち。公式のプロセス図ではなく、実際の例について追跡システムの履歴を使います。地図は、仕事がどこで待ち、どこではね返るかを示します。関わるチームと共有し、彼らが見る無駄を特定してもらいます。

**2. 作業アイテムの履歴から、引き継ぎと待ちを測る。** 割り当てと活動のタイムスタンプを使って、アイテムの種類ごとに、引き継ぎの回数、待ちの割合、再割り当ての率を計算します。分布を見ます。ほとんどのアイテムは一度だけ渡され、長い裾が何度もはね返るかもしれません。裾が、最大の遅れと最も多くのフラストレーションがある場所です。

**3. 仕事をする人々とデータを読む。** 高い再割り当ての率は、不明確なオーナーシップ、欠けている情報、あるいは正当なトリアージを反映しているかもしれません。結論を出す前にチームに尋ねます。彼らは、アイテムがなぜはね返り、何がそれを止めるかを知っています。

### 引き継ぎと待ちを減らす

**4. 能力を仕事に移す。** 多くのアイテムが単純な行動のために第二のチームに行くところでは、最初のチームに、知識、アクセス、自動化を与えて、それができるかを問います。セルフサービスと手順書は、引き継ぎ全体を取り除けます（トピック 3.7「セルフサービスと自動化のメトリクス」を参照）。仕事を移すことが、単に最初のチームを過負荷にしないよう注意します。

**5. 順次のエスカレーションの代わりに協働を使う。** 複雑または緊急のインシデントでは、チケットを階層に通す代わりに、一人が調整して、関係する人々をリアルタイムで集めます。スウォーミングとしばしば呼ばれるこの実践は、階層的なエスカレーションが生む待ちと文脈の喪失を取り除きます。協働による解決の率を追跡し、成果と満足度が改善するかを見ます（トピック 3.4「重大インシデントのメトリクス」を参照）。

**6. 境界でオーナーシップを明確にする。** 各サービスとコンポーネントについて、誰が所有し、どう連絡し、引き継ぎで何が要るかを述べます。受け手のチームと合意した、必要な情報の短いテンプレートは、欠けた詳細による差し戻しを減らします。再割り当ての事例をレビューして、オーナーシップのギャップを見つけます。

**7. 最も痛手となるところで依存関係を減らす。** チーム間の依存関係をマップし、それぞれがどのくらいの頻度で遅れを引き起こすかを数え、最悪のものに取り組みます。選択肢には、アーキテクチャの変更、チームが待ち続けている能力をそのチームに与えること、サービスを中心にチームを再編成することがあります。サービスを最初から最後まで届けるのに必要な技能を含む[クロスファンクショナルなチーム（cross-functional team）](https://en.wikipedia.org/wiki/Cross-functional_team)は、依存関係を最小にし、継続的な協働を構造に持ち込みます。コンウェイの法則は、構造と設計を一緒に変えるべきことを示唆します。

### 知識と関与を広げる

**8. 知識の網羅を見えるようにして改善する。** 重要なコンポーネントと、それぞれを運用し変更できる人々の単純な地図を保ちます。一人に知られているコンポーネントを探し、それを広げるためにペアリング、文書、ローテーションを計画します。結果をシステムへのリスクとして扱います。狙いは、耐障害性と、最も知る人々の持続可能なペースです。唯一の専門家である人は、休暇を取れないからです。

**9. ステークホルダーを継続的に巻き込む。** ステークホルダーにどう質問を届け、どれだけ速く答えが来るべきかに合意します。ある詳細についての決定を1週間待つチームは、ステークホルダーを待っており、そのコストは現実です。質問と答えを記録し、応答時間を測り、ステークホルダーの関与についての対話で使います。

**10. 集中した仕事のための時間を守る。** 協働は目的を持つべきです。カレンダーを埋める会議をレビューし、それぞれがどんな判断を支えるかを尋ねます。ブルックスの法則に沿って、必要のない対話の人数を減らします。これを、チームの健全性についての前のトピックの集中の測定値と組にします（トピック 9.1「チームの健全性と開発者体験」を参照）。

### 誠実に保つ

**11. コミュニケーションの量を測らない。** メッセージ、会議、ネットワークのリンクを数えることは、人々がうまく一緒に働いているかについてほとんど語らず、個人の監視を招きます。チームが、情報の流れを理解するために社会ネットワーク分析を使うことを選ぶなら、同意を得て、グループのレベルで、チーム自身の学びのために行い、個人を評価するためには決して行いません。

**12. 引き継ぎの測定値を、チームと供給者とレビューする。** 関わるチームと供給者のパターンを共有し、共同の改善を一つか二つ合意します。引き継ぎの回数と待ちが下がるかを追跡します。供給者との境界には、共同のレビューに測定値を含めます（トピック 8.4「サプライヤーと契約のメトリクス」を参照）。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 引き継ぎの回数 | 他のチームが仕事をする間、アイテムを一つのチームに割り当てたままにする、数えないよう共有のキューに再割り当てする | チーム別の実際の活動を確認する。割り当てだけでなく、活動で引き継ぎを数える |
| 引き継ぎの待ちの割合 | 単なる確認応答である最初の行動を記録する、適切なチームへの割り当てを遅らせる | 「最初の行動」を実質的なステップと定義する。満足度と解決時間と比較する |
| 再割り当ての率 | 間違っていても再割り当てを拒む、別のチームのもとでアイテムをクローズして再オープンする | 解決の質と再オープン率。はね返ったアイテムを抽出する |
| 依存関係による遅れ | ブロックされた状態を記録しない、間違った依存関係に名前を付ける | サイクルタイムとアイテムの年齢と比較する。依存関係の欄をチームとレビューする |
| 協働による解決の率 | すべてのインシデントを協働とタグ付けする、実際の仕事のない共有のチャネルを作る | 通話やチャネルに解決する人々が含まれていたかを確認する。解決時間と成果 |
| 知識の網羅 | 理論上その仕事ができる人を列挙する、地図を水増しする | ペアリングや訓練の証拠。直近の変更を実際に行った人を尋ねる |
| ステークホルダーの応答時間 | 質問を遅く記録する、使えない答えを受け取ったと印を付ける | ステークホルダーが答えが使えるものと確認する。質問を抽出する |

健全な読みは、一般的なアイテムの少ない引き継ぎ、残る境界のより短い待ち、少ないはね返ったアイテム、縮む依存関係、一緒に働く人々が解決するより多くのインシデント、複数の人に知られている重要なコンポーネント、そして数時間で答えるステークホルダーです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| エスカレーションを伴う階層的なサポート | 専門化、アクセスの統制 | 引き継ぎ、待ち、文脈の喪失 |
| クロスファンクショナルなチーム | 少ない引き継ぎ、共有のオーナーシップ | 広い技能が要る。専門家が重複しうる |
| 協働による解決 | 速く、より良い学び | 複数の人を同時に引き込む。調整が要る |
| 順次のエスカレーション | 専門家の効率的な利用 | 複雑な問題には遅い |
| 中央集権的な専門家チーム | 専門知識の深さ、一貫した基準 | ボトルネック、キュー |
| 組み込まれた専門家 | 素早いアクセス | 孤立。不均一な基準 |
| 重い会議の文化 | 共有された認識 | 集中を食う。仕事を遅くする |
| 非同期の文書によるコミュニケーション | 集中を保つ。判断を記録する | 緊急または曖昧な事柄には遅い |

散文での答えは、深さが重要なところには専門家を保ち、複雑または緊急の問題にはリアルタイムで人々を集め、能力と明確なオーナーシップで引き継ぎを減らし、会議と守られた集中のバランスを取ることです。

## チームで話し合う問い

**1. チーム間ではね返った直近のインシデントまたはリクエストをたどる。どこで待ち、なぜか？**
アイテムの履歴を使います。各引き継ぎと待ちに印を付けます。ファシリテーターは、欠けている情報、不明確なオーナーシップ、誰も見ていないキューを探してください。はね返りを止めたであろう変更を一つ合意します。

**2. 私たちが最も頻繁に待つチームはどれで、彼らが速くなるために私たちに何を必要とするか？**
依存関係とそれが引き起こす遅れを列挙します。他のチームを対話に招く、あるいは彼らへの質問を準備します。引き継ぎのテンプレートまたは作業合意の変更に合意します。

**3. 私たちのうち一人か二人しかやり方を知らないことは何で、その人が不在のときに何が起きるか？**
コンポーネントやタスクに名前を付けます。知識を広げる計画が何かを尋ねます。ペアリング、文書、ローテーション。ファシリテーターは、これをシステムへのリスクと、専門家の作業負荷の問題として扱うよう注意してください。

**4. 一緒にリアルタイムで問題を解決することが、渡していくよりうまくいったのはいつか？**
例を思い出します。何がうまくいかせたか。適切な人々、調整役、共有された見方。このアプローチをいつ使い、どう可能にするかを話し合います。常設のチャネルと誰が参加するかの規則など。

**5. ステークホルダーからの答えをどのくらい待ち、それにいくらかかるか？**
未解決の質問とその年齢を見ます。何が答えを遅くしているかを話し合います。対応可能性、不明確な質問、不明確な権限。ステークホルダーとの期待と、それを追跡する方法に合意します。

**6. 私たちの会議のうち、文書や判断に置き換えられるものはどれか？**
定例の会議を列挙し、それぞれについて、どの判断を支え、誰がいる必要があるかを尋ねます。一つをキャンセルまたは短縮します。会議のない時間のブロックを守ることに合意します。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、多くの依存関係を持ち、待ちを感じます。依存関係をマップし、待ち続けている能力を求め、単一の点を避けるために知識を共有し、ステークホルダーを近くに保つべきです。クロスファンクショナルな構成が、最大の遅れをしばしば取り除きます。

### サービスと運用のチーム

運用とサポートのチームは、引き継ぎの中心にいます。受け取り、ルーティングし、解決します。明確なオーナーシップの情報を維持し、難しい問題にはリアルタイムの協働を使い、引き継ぎを正確に記録するべきです。どの境界が最も痛みを生むかを知っており、どの情報が差し戻しを防ぐかを言えます。

### リーダーシップとガバナンス

リーダーは、引き継ぎを生む構造を形作ります。チームと資金付けを設計するときに引き継ぎと依存関係のデータを見て、役立つところではクロスファンクショナルなチームを支え、コミュニケーションの量の測定値を避けるべきです。ガバナンスは、一つの境界での繰り返される遅れを、直すべき構造的な問題として扱うべきです。

### 顧客とユーザー

ユーザーは、引き継ぎを、たらい回しにされること、繰り返し説明すること、待つことと感じます。誰が自分の問題を所有するかを伝えられ、情報を知らされ続けるべきです。はね返される彼らの体験は、協働がどれだけうまく機能しているかの直接の測定値で、彼らのフィードバックは数字と並べて読まれるべきです（トピック 6.1「顧客満足度のメトリクス」を参照）。

## 実践：サービスマネジメントの例

国の小売業者のITグループが、サービスデスク、インフラチーム、アプリケーション基盤チーム、いくつかのプロダクトチームを運営しています。ユーザーは、販売時点管理システムについてのリクエストに時間がかかりすぎると報告します。以下の数字は例示です。

サービスマネージャーは、60件の最近のリクエストをたどります。リクエストの中央値は3つのチームを通過し、85パーセンタイルでは6つのチームを通過します。中央値の事例では、経過時間の71パーセントが、受け手のチームが行動する前の、引き継ぎ後の待ちに費やされています。リクエストの22パーセントが二度を超えて再割り当てされ、しばしばインフラと基盤のチームの間で、それぞれが相手が問題を所有すると信じています。別のチームを待つブロックされた時間は、証明書に関わるリクエストでは中央値3日、85パーセンタイルで8日です。基盤の証明書更新の知識は一人のエンジニアにあり、他の二つの重要なコンポーネントも、それぞれ一人にしか知られていません。店舗運用のステークホルダーが、デリバリーのチームからの質問に答えるのに、中央値26時間かかります。

グループは、チームとともに四つの変更に合意します。短いオーナーシップの表が、販売時点管理サービスの各コンポーネントをどのチームが所有し、引き継ぎに何の情報が必要かを述べます。サービスデスクが、一般的な引き継ぎを取り除く、証明書の更新のための手順書へのアクセスと自動化を得ます。優先度の高いインシデントでは、グループが常設のチャネルと、階層でエスカレーションする代わりに、インシデントの調整役が関係する人々をすぐに呼ぶという規則を設けます。基盤チームは、証明書のプロセスに第二、第三の人をペアにし、他の二つのコンポーネントについても同様のペアリングを、計画に守られた時間とともに計画します。デリバリーのチームと店舗運用は、ブロッキングの質問に当日の回答を合意し、質問ログで追跡します。

三か月後、リクエストの中央値は2つのチームを通過し、待ちの割合は38パーセントに下がり、再割り当ての率は9パーセントに下がります。証明書に関連するリクエストのブロックされた時間の中央値は1日未満です。重要なコンポーネントの知識の網羅は52パーセントから81パーセントに上がります。店舗運用の応答時間の中央値は7時間に下がります。IT責任者は、チームがどれだけコミュニケーションしているかの測定値を求められます。サービスマネージャーは、メッセージの量は仕事が流れているかについてほとんど語らず、それを追跡することは信頼を損ないうると説明し、代わりに引き継ぎと待ちの測定値を提案します。判断は記録され、オーナーシップの表がサービスの説明に加えられます。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

適切な人々を早く集め、引き継ぎをステークホルダーと定期的にレビューします。注意点は、会議やメッセージを数えることは、協働ではなく、活動を測ることです。

### AI

AIのエージェントとアシスタントは、人とソフトウェアの間に新しい引き継ぎを加えます。AIと人の間の引き継ぎを、訂正のために戻る割合を含めて測ります。注意点は、終えられないAIへの引き継ぎは、隠れたループを作ることです。

### 自動化

再割り当てと待ちを追跡システムから自動で取得し、自動のルーティングを誤ったルーティングで測ります。注意点は、個人についてのコミュニケーションのメタデータは監視なので、分析をチームのレベルに保つことです。

### アナリティクス

引き継ぎの回数と待ちの割合を、バリューストリーム別に件数とともに示します。これが情報を与える判断は、どの引き継ぎを取り除く、あるいは再設計するかです。注意点は、原因なしに引き継ぎを数えると、間違った理由でチームを統合することにつながることです。

## 業種別の視点

**スタートアップ。** 小さなチームは自然に協働し、引き継ぎは専門家が現れるときに現れます。チームを可能な限りクロスファンクショナルに保ち、オーナーシップを軽く文書化し、一人が持つ知識に注意します。階層的なサポートを早すぎる時期に持ち込まないでください。

**中小企業。** 一人か二人がすべてをカバーしているかもしれず、最大のリスクはその人々への依存です。単純な手順書で知識を共有し、不在をカバーします。供給者への引き継ぎが主な境界なので、明確な連絡先とエスカレーションの経路を保ちます。

**大企業。** 規模は、多くのチーム、階層、供給者を生み、引き継ぎが増えます。最も一般的なアイテムの経路をマップし、サービスを中心にチームの境界を設計し、チーム横断のインシデントに調整役を使います。境界が共同で注意を受けるよう、チーム間で引き継ぎのデータを共有します。

**政府・公共部門。** 責任は、機関、契約者、法的境界にまたがって分割されることが多く、引き継ぎには調達と正式な承認が関わります。オーナーシップの表を明示し、契約者との共同のレビューを使い、境界をまたぐインシデントには共有のチャネルを使います（トピック 8.4「サプライヤーと契約のメトリクス」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは、割り当て履歴を抽出して分析する労力、チームが経路をたどりオーナーシップに合意する時間、クロストレーニングのコスト、リアルタイムの協働のためのツールです。チームの再編成は、独自のコストを伴うより大きな判断です。

見返りは、解決と提供のより短い時間、はね返ったアイテムによる手戻りの減少、知識の単一の点によるリスクの低下、より穏やかな働く環境です。自分たち自身のデータからケースを築きます。待ちに費やされる経過時間の割合、はね返るアイテムの数、最悪の境界での遅れのコスト、過去のインシデントへの主要な人物の不在の影響。出典と文脈をたどれない限り、引き継ぎのコストについての公表された数字の引用は避けます。変更のコストを数え、取り除かれた遅れと比較します（トピック 7.7「投資対効果とビジネスケース」を参照）。

## アンチパターンと落とし穴

- **メッセージや会議を数える。** ノイズを報い、監視を招く。仕事の流れを測る。
- **各引き継ぎの速度を最適化する。** 狙いはより少ない引き継ぎである。可能なところで取り除く。
- **待ちで受け手のチームを責める。** 原因はキューと構造であることが多い。システムを見る。
- **既定でエスカレーションする。** 順次の階層は待ちを加える。複雑な問題には人々を集める。
- **不明確なオーナーシップ。** アイテムがはね返る。オーナーシップの表を公開し、最新に保つ。
- **英雄的な専門家。** 知識の単一の点はリスクであり負担である。意図して知識を広げる。
- **協働としての会議。** 仕事を押しのけうる。判断に照らして会議をレビューする。
- **知識の網羅を個人の評価として扱う。** ランキングになる。システムの測定値に保つ。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| 引き継ぎの可視性 | 逸話 | 少数のサービスの経路が描かれている | 履歴から引き継ぎの回数、待ちの割合、再割り当てが測定される | 測定値がチームとレビューされ、成果に結び付く | チームと供給者にまたがる共有の見方。データから境界が再設計される |
| 引き継ぎの削減 | 既定でエスカレーションする | 一部の手順書とテンプレート | オーナーシップの表。最初のチームに移された能力。難しい問題への協働 | 依存関係がマップされ減らされる。協働による解決が追跡される | 組織全体で依存関係が最小のサービスを中心に組織されたチーム |

## チェックリスト

- [ ] 典型的なアイテムの経路が、実際の追跡システムの履歴からたどられている。
- [ ] 引き継ぎの回数、待ちの割合、再割り当ての率が、アイテムの種類ごとに測定されている。
- [ ] 各サービスとコンポーネントのオーナーシップが公開され、最新である。
- [ ] 引き継ぎのテンプレートが、受け手のチームが必要とする情報を述べている。
- [ ] 複雑または緊急のインシデントが、調整役を伴うリアルタイムの協働を使う。
- [ ] チーム横断の依存関係がマップされ、最悪のものが減らされつつある。
- [ ] 重要なコンポーネントの知識の網羅がマップされ、それを広げる計画がある。
- [ ] ステークホルダーの質問が記録され、応答時間がレビューされている。
- [ ] どの測定値も、メッセージ、会議、個人のコミュニケーションを数えていない。
- [ ] 結果が、関わるチームと供給者と共有されている。

## AIプロンプト

**作業アイテムの経路を分析する。**

```text
以下は [数] 件の [アイテムの種類] の匿名化した割り当て履歴です：アイテム、チームの並び、割り当てと最初の行動のタイムスタンプ：[貼り付け]。引き継ぎの回数と待ちを計算または記述し、一般的な経路と長い裾を特定し、待ちとはね返りのありそうな理由を、チームに尋ねる問いとともに示唆してください。個人については何も推測しないでください。前提を列挙してください。
```

**オーナーシップの表を起案する。**

```text
次のコンポーネントとチームを持つサービス [名前] のオーナーシップの表を起案してください：[一覧]。各コンポーネントについて、オーナーのチーム、連絡方法、引き継ぎに含めるべきもの、エスカレーションの経路を含めてください。オーナーシップが不明確、あるいは共有されていそうなコンポーネントに印を付けてください。1ページに収めてください。前提と、チームへの問いを列挙してください。
```

**知識を広げる計画を立てる。**

```text
私たちの重要なコンポーネントと、それぞれを運用できる人数は：[貼り付け]。[数] 人未満にしか知られていないコンポーネントのために、知識を広げる計画を提案してください。ペアリング、文書、訓練、ローテーション。計画中に専門家の作業負荷をどう守り、個人に順位を付けずに進捗をどう追跡するかを示唆してください。前提とリスクを列挙してください。
```

**協働によるインシデントのアプローチを設計する。**

```text
[チーム] を持つ [組織の種類] で、優先度の高いインシデントのリアルタイムの協働による解決のための、軽量なアプローチを設計してください。共有の場の開き方、誰が調整するか、誰を招くか、何を記録するか、多すぎる人を巻き込むのをどう避けるかを含めてください。それが役立つかを知る測定値を含めてください。前提と注意を列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：引き継ぎまたは協働のメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：協働のメトリクスの項目が、個人ではなく仕事を測り、悪用の手口と防護柵を備えているかを確認するときに使います。

## 要点

- 遅れの大半は引き継ぎの間の待ちにあるので、作業アイテムの履歴から引き継ぎの回数、待ちの割合、再割り当てを測る。
- 能力を仕事に移し、オーナーシップを明確にし、依存関係をマップして削ることで、引き継ぎを減らす。
- 複雑または緊急の問題には、適切な人々をリアルタイムで集める。
- 重要なコンポーネントの知識を広げ、知識の単一の点をシステムのリスクとして扱う。
- ブロッキングの質問への素早い答えとともに、ステークホルダーを継続的に関与させる。
- コミュニケーションの量を決して測らず、協働で個人を評価しない。
