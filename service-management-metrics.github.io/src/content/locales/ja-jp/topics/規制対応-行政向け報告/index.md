# 規制対応・行政向け報告

**義務的な報告は、周りに設計すべき固定の要件である。したがって、サービスの運営に使うのと同じ記録からそれを作り、報告の見方を学びの見方から分け、仕事を行う人々を、それを歪める目標から守る。**

## 概要と動機

多くの組織は、自分たちで選ぶかどうかにかかわらず、サービスについて報告しなければなりません。規制当局は、インシデントの通知、可用性の数字、統制の証拠を求めます。政府は、機関に、パフォーマンスのデータ、支出、アクセシビリティの声明を公表することを求めます。資金提供者や監督機関は、コミットメントに対する成果を求めます。契約は、サービスのレポートを要求します。これらの場面では、報告は社内の管理上の選択ではありません。期日、定義、時に違約金を伴う義務です。

[公共部門（public sector）](https://en.wikipedia.org/wiki/Public_sector)には、特有の特徴があります。市民と選出された機関に対する[説明責任（accountability）](https://en.wikipedia.org/wiki/Accountability)は中核の義務で、監査、立法、[情報公開法（freedom of information laws）](https://en.wikipedia.org/wiki/Freedom_of_information_laws_by_country)、公表された結果を通じて果たされます。[オープンガバメント（open government）](https://en.wikipedia.org/wiki/Open_government)と[オープンデータ（open data）](https://en.wikipedia.org/wiki/Open_data)の実践は、精査と再利用のために情報を利用可能にします。[公共調達（public procurement）](https://en.wikipedia.org/wiki/Public_procurement)の規則は、何をどう購入できるかを形作り、[記録管理（records management）](https://en.wikipedia.org/wiki/Records_management)の義務は情報をどのくらい保持するかを規定します。[費用対効果（value for money）](https://en.wikipedia.org/wiki/Value_for_money)は公的支出の一般的なテストで、独立した機関が[パフォーマンス監査（performance audit）](https://en.wikipedia.org/wiki/Performance_audit)を行ってそれを調べます。詳細は国、政府の階層、分野によって異なり、このトピックは法的要件ではなく、測定の実践を記述します。法務、コンプライアンス、記録の同僚と確認してください。

金融、医療、エネルギー、通信などの規制された民間部門の組織は、これらの特徴の多くを共有しています。インシデント通知の義務、耐障害性の報告、監督上のレビューに直面します。共通の糸は、デリバリーのチームの外の誰かが、何をいつまでに報告しなければならないかを定義することです。

継続的デリバリーとITILの実践は、どちらも提供するものがあります。ステークホルダーとの継続的な協働というアジャイルの狙いは、正当な必要を持つステークホルダーである監督機関にも及び、彼らが何を要するかについての早期の対話は、手戻りを防げます。小さく動くインクリメントを継続的に届けるというアジャイルの習慣は、報告に合います。記録システムから自動で作られるレポートは、四半期ごとに手作業で組み立てられるものより正確で安価です。ITILの測定とレポートのプラクティスとサービスレベル管理は、何が測られ共有されるかを定義する語彙を与えます。

報告の義務は、三つのよく知られた危険を生みます。

- **目標による歪み。** 報告される数字が結果を伴うとき、仕事は数字に向かって曲がる。ジョン・セドンの公共部門のシステム思考についての著作や、ジェリー・ミュラーのメトリクス固執の分析を含む、公共部門の目標に関する文献は、目標の達成と国民への奉仕が乖離した多くの事例を記述している。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵が全面的に当てはまる（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。
- **二組の数字。** 数字の法定の定義は、チームが社内で使うものと異なることが多い。チームが一方で管理し他方を報告するなら、誰もどちらも信頼しない。両方を見えるようにし、突合し、違いを説明する。
- **負担としての報告。** 手作業で、繰り返される、一貫しない依頼は、熟練した人々を消耗させる。報告が英雄的なスプレッドシートの仕事に依存するほど、より多くのエラーと遅れが忍び込む。

このトピックは、この部のコンプライアンス、リスク、供給者の測定値（トピック 8.2「リスクと統制のメトリクス」、トピック 8.3「コンプライアンスと監査のメトリクス」、トピック 8.4「サプライヤーと契約のメトリクス」を参照）と、最初の部のデータの基盤（トピック 1.5「データソースと計装」を参照）の上に築かれています。

## 主要な原則

- **義務を設計への入力として扱う。** 定義、期日、オーナーとともに早期に列挙し、それを中心にデータ収集を設計する。
- **記録システムからレポートを作る。** 抽出を自動化し、系譜を見えるようにする。
- **報告の見方を学びの見方から分ける。** チームには、報告されるものに制約されない、率直な作業用の測定値が必要である。
- **定義を突合する。** 法定の数字がチーム自身の測定値とどう関係するかを示す。
- **悪い知らせを含め、誠実に報告する。** 訂正と文脈が信頼を築く。
- **人々を逆効果の目標から守る。** 法定の目標を相棒の測定値とともに使い、その限界を説明する。
- **公表されたデータを使えるものにする。** アクセシビリティ、明確さ、形式は、一般市民にとって重要である。

## 推奨事項

### 義務を設計への入力として扱う

**1. 報告義務の台帳を保つ。** それぞれについて、要件、法的または契約上の情報源、何を報告するか、定義、期日、受け手の機関、社内のオーナー、データソースを記録します。法律、契約、規制当局が変わったときにレビューします。早く知られた義務は設計に組み込め、遅く発見されたものは手作業で組み立てなければなりません。

**2. 監督機関を早く巻き込む。** 規制当局、監査人、資金提供者に、データで何をするか、何を必要とするかを尋ねます。定義を形作る助けになる、あるいはすでに作っている形でデータを受け入れる機関もあります。アジャイルの実践はステークホルダーとの協働を重んじ、監督機関はステークホルダーです。これらの対話の記録を保ち、重要なところでは独立性を保ちます。

**3. 最初から報告のためにデータ収集を設計する。** サービスを構築するとき、必要なレポートが要するイベントと項目を含めます。インシデントのタイムスタンプ、影響、区分、ユーザー数。後から加えるのは高コストです。一度定義し、定義の単一のオーナーとともにチーム間で定義を共有します（トピック 1.4「メトリクスのガバナンスとオーナーシップ」を参照）。

### 記録システムからレポートを作る

**4. 記録からレポートまでのパイプラインを自動化する。** インシデント、変更、サービスのシステムからスクリプト化したクエリで抽出し、文書化された変換を適用し、レビューされたテンプレートでレポートを作ります。自動化されたレポートは、手作業のものより再現可能で、速く、監査しやすい。過去のレポートが再現できるよう、クエリとテンプレートをバージョン管理します。

**5. 系譜を文書化する。** 報告される各数字について、どこから来て、どう計算され、誰が確認するかを記します。トレーサビリティの網羅率が、これがどれだけうまく行われているかを測ります。「この数字はどこから来たのか？」と尋ねる監査人やジャーナリストは、数分で明確な答えを得るべきです。

**6. 提出前に、独立した読み手とレビューする。** レポートを作ったチームの外の誰かに、定義、算術、説明を確認してもらいます。レビューはエラーと裏付けのない主張を捉えます。レビューを記録します。責任者の短い承認が、オーナーシップを明確にします。

**7. 公然と訂正する。** 提出後にエラーが見つかったときは、速やかに訂正し、何が変わったかを説明し、原因を記します。データが複雑なら、ゼロに近い訂正再提出の率は疑わしい。見える素早い訂正は、立ったままの数字より多くの信頼を築きます。

### 報告と学びを分けておく

**8. チームのための作業用の見方を維持する。** チームには、パーセンタイル、最も古いアイテムの年齢、品質の相棒など、改善に役立つ測定値が必要です。これらは法定の数字と同じであることはまれです。作業用の見方を報告されるものに限定せず、報告された数字だけで管理してはいけません。

**9. 法定の定義と社内の定義を突合する。** 必要な測定値がチームのものと異なるところでは、違いを文書化して両方を示します。たとえば、規制当局の可用性の数字は計画メンテナンスを除外するかもしれませんが、ユーザーはそれを停止時間として体験します。突合をメトリクス台帳とレポートの注記に示します。これは「二組の数字」の問題から守ります。

**10. 法定の目標を相棒と組にする。** 目標が課されるなら、歪みを明らかにする測定値を加えます。品質、ユーザー体験、除外された仕事。たとえば、最初の応答までの時間の目標を、解決と繰り返しの問い合わせの測定値と組にします（トピック 3.1「サービスデスクのメトリクス」を参照）。レポートで、数字をどう読むべきかを説明します。

### 市民のために公表する

**11. 公表された情報を使えるものにする。** 法律とプライバシーが許すところでは、明確な説明、定義、日付とともに、オープンで機械可読な形式で公表します。文書とウェブページのアクセシビリティ基準を満たします。人々が読めない、あるいは再利用できない形でデータを公表することは、形式を満たして目的を損ないます。支援技術を使う人々を含む、実際のユーザーでテストします（トピック 6.4「ユーザー体験と従業員体験」を参照）。

**12. 公表するものでプライバシーとセキュリティを守る。** 人を特定しうる少数を集約して抑制し、攻撃者を助ける詳細の公表を避け、開示の規則を専門家と確認します。情報公開法に基づく回答にも同じ注意を払います。黒塗りの判断とその理由を記録します。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 報告義務の網羅率 | 義務を狭く扱う、合意なしにオーナーを列挙する | コンプライアンスまたは内部監査による台帳のレビュー。オーナーからの確認 |
| レポートの適時性 | 日付に間に合わせるために不完全なレポートを提出する、下書きを提出として数える | 提出時の完全性の確認。受理されたレポートのみを数える。訂正再提出の率 |
| 訂正再提出の率 | 訂正を抑える、訂正を静かに行う | 独立した読み手がレビューする訂正ログ。低い率はトレーサビリティとともに読む |
| トレーサビリティの網羅率 | 系譜を表面的に文書化する、単純な数字だけを含める | 情報源から計算を再実行して系譜を抽出する |
| 定義の整合 | 突合なしに定義が整合していると宣言する、レポートでのみ法定の定義を採用する | 突合の文書をレビューする。両方の数字を並べて示す |
| 報告の労力 | 時間を記録しない、仕事を他のチームに移す | チームのフィードバックと比較する。見積もりにすべての貢献者を含める |
| 公表物のアクセシビリティ適合 | 一部の問題しか見つけないチェッカーを実行する、遅れる別のアクセシブルな版を公表する | 支援技術での手作業のテスト。版の間の同等性を確認する |

健全な読みは、すべての義務にオーナーがおり、レポートが適時で正確で訂正が見え、数字が記録システムにたどれ、法定の定義と社内の定義が突合され、報告の労力が下がり、公表された情報を市民が使えることです。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| レポートの手作業での組み立て | 柔軟。どんなデータでも機能する | 遅く、エラーが起きやすく、個人に依存する |
| 自動化された報告 | 再現可能で、監査でき、運用が安い | セットアップの労力。貧弱な定義を固定しうる |
| すべてに一組の測定値 | 単純 | 仕事を歪める。法定の数字がチームの必要に合うことはまれ |
| 報告と学びの別々の見方 | 率直な学び。誠実な報告 | 突合と規律が要る |
| 硬い法定の目標 | 明確な説明責任 | 逆効果。悪用 |
| 相棒と文脈を伴う目標 | 歪みを明らかにする | 説明すべきことが増える |
| 規制当局との早期の関わり | 驚きが少ない | 時間。維持すべき境界 |
| 距離を置いた関係のみ | 明確な独立性 | 遅いフィードバック。手戻り |

散文での答えは、記録システムからレポートを自動化し、チームの作業用の見方を報告の見方から分け、定義を公然と突合し、独立性を保ちながら監督機関と早期に関わることです。

## チームで話し合う問い

**1. どのレポートを、誰に、いつまでに負い、それぞれを誰が所有するか？**
その場で一覧を作成し、台帳と比較します。ギャップはよく現れます。契約上、資金提供者に対して、あるいはほとんどの人が知らない規則に基づいて負うレポート。ファシリテーターは、新しい項目を記録し、オーナーを割り当ててください。

**2. 報告されなければ、違う形で管理するであろう、報告された数字はどれか？**
法定または契約上の測定値を一つ選び、誰も測らなかったらチームが何をするかを尋ねます。答えは、数字と目的が乖離する箇所を明らかにします。違いを示す相棒の測定値が何かを話し合います。

**3. 先四半期のレポートを、今日、情報源から再現できるか？**
一つのレポートで試します。手作業、文書化されていない、失われたものに注意します。自動化または文書化する最初のステップと、誰が行うかに合意します。

**4. 提出後に見つかったエラーを、どう扱うか？**
プロセスと直近の例をレビューします。訂正は素早く公然としていたか。誰かが挙げるのを恐れたか。訂正を通常のことにするものに合意します。

**5. 支援技術を使う人は、私たちの公表されたレポートを読んで何を体験するか？**
公表された項目を一つ一緒にテストする、または最近のアクセシビリティの確認をレビューします。公表される文書のアクセシビリティを誰が所有するかを尋ねます。修正を一つと、再発を防ぐプロセスに合意します。

**6. 規制当局や監督機関は、私たちのデータで実際に何をしているか？**
多くのチームは知りません。それを見つけ、異なる形でも彼らに役立つかを尋ねる対話を計画します。ファシリテーターは、独立性の境界に注意してください。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、レポートが依存するイベントと項目を構築し、法定の目標の圧力を感じます。完了の定義に報告の必要を含め、率直な作業用の見方を保ち、目標が仕事を歪めるときにフラグを付けるべきです。報告する人々との早期の対話が、手戻りを防ぎます。

### サービスと運用のチーム

運用チームは、基になるデータの大半を生み出し、レポートを準備することがよくあります。系譜を文書化し、抽出を自動化し、訂正ログを保つべきです。数字をどう読むべきかを説明し、誤解を招くときに警告する立場にあります。

### リーダーシップとガバナンス

リーダーは、報告されることの正確さと誠実さに責任を負います。トレーサビリティと突合を求め、法定の数字を個人の目標に変えるのに抵抗し、エラーを挙げる人々を守り、監督機関との関わりを支えるべきです。ガバナンスは、義務の台帳と訂正再提出の履歴をレビューするべきです。

### 顧客とユーザー

一般市民と顧客は、サービスの説明責任を問うために、公表された情報に頼ります。見つけ、読み、再利用できるデータを、アクセシブルな形式で、それが何を意味するかの明確な説明とともに必要とします。また、規則が求めるように、インシデントが彼らに影響するときの速やかな通知にも値します。

## 実践：サービスマネジメントの例

国の機関が、年に数百万人が使うオンラインの許認可サービスを提供しています。省に毎月報告し、年次のパフォーマンスデータを公表し、重大なサービスインシデントを決められた時間内に規制当局に通知しなければなりません。以下の数字は例示です。

内部レビューは、機関が31件の異なる種類のレポートを負っていること、そのうち22件だけが、名前付きのオーナーと定義とともに義務の台帳にあり、網羅率は71パーセントであることを見つけます。月次の数字は、主に三つのシステムからスプレッドシートに引き出して、約60時間かけて手作業で組み立てられています。トレーサビリティは貧弱です。見出しの数字である可用性について、誰も昨年の数字を再現できません。省の可用性の定義は計画メンテナンスを除外し、機関自身の作業用の見方はそれを数えており、それが、ユーザーと省が異なる絵を見る理由を説明します。機関は毎月、最初の応答までの時間の目標を満たしており、サービスデスクはそれを達成するために依頼を自動で確認応答し始め、一方で解決までの時間は上がっています。公表された二つのレポートは、スクリーンリーダーで確認したとき、アクセシビリティのテストに失敗しました。

機関のサービスパフォーマンスの責任者は、省、デリバリーと運用のチームと変更に合意します。義務の台帳は、オーナー、定義、日付とともに完全になります。月次の数字は、文書化された変換とレビューされたテンプレートを伴う、インシデントと監視のシステムへのスクリプト化されたクエリから来て、労力を約8時間に削減します。突合の注記が、法定と社内の可用性の定義を述べ、レポートに両方の数字が示されます。最初の応答の目標は、作業用の見方で解決までの時間と繰り返しの問い合わせと組になり、省は相棒の測定値を見ることに合意します。機関はまた、前の四半期の可用性の数字を訂正し、原因を説明し、訂正を公表します。公表されるレポートはアクセシブルなテンプレートで作られ、スクリーンリーダーのテストがリリースのチェックリストに加えられます。

1年後、義務の網羅率は100パーセント、レポートは適時で、訂正再提出の率は低く、すべての訂正が説明され、トレーサビリティはすべての見出しの数字をカバーし、報告の労力は約85パーセント減りました。大臣室は、機関のリーダーが説明責任を負う、99.95パーセントの可用性という新しい目標を求めます。サービスパフォーマンスの責任者は、法定の数字とユーザーが体験する数字の違いを説明し、相棒の測定値とレビュー日を伴う目標を提案します。判断は記録され、省は次の報告年度の前に定義の共同のレビューに合意します。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

固定された報告要件に向けて設計し、報告の見方を学びの見方から分けておきます。注意点は、報告の目標が、それが記述する仕事を歪めうることです。

### AI

AIが規制されたプロセスを支えるところでは、レポートは判断がどうなされ、誰が責任を負ったかを示す必要があるかもしれません。要件を法律顧問と確認し、AIの利用の記録を保ちます。注意点は、申告に使われるAIの出力には、人による検証が必要なことです。

### 自動化

サービスの運営に使うのと同じ記録からレポートを作り、提出前に動く確認を自動化します。プロセスを訂正再提出で測ります。注意点は、自動化がエラーを多くのレポートに伝播させうることです。

### アナリティクス

使った定義とデータの日付とともに報告します。これが情報を与える判断は、何を報告しなければならないか、データがどこから来るかです。注意点は、定義は制度によって異なるため、一つが普遍的だと仮定しないことです。

## 業種別の視点

**スタートアップ。** 報告の義務は、最初のエンタープライズの顧客や規制当局とともに到来しうるものです。義務の短い一覧から始め、自分たちのシステムからレポートを作り、別個の報告プロセスを築くのを避けます。契約でサービスレベルを約束するときは注意します。

**中小企業。** 義務は、契約や単一の規制当局に結び付いていることがよくあります。カレンダーを保ち、テンプレートを使い、数字がどう作られるかを文書化します。小さく正確なレポートは、大きく慌ただしいものに勝ります。

**大企業。** 地域と制度にまたがる多くの義務は、中央の台帳、共通の定義、共有の抽出ツールを要します。同じチームへの重複した依頼に注意します。インシデントとサービスのデータの単一の信頼できる情報源を、各制度のための見方とともに使います。

**政府・公共部門。** これがこのトピックの本拠地です。立法、大臣からの依頼、監査、情報公開の請求、公的な精査に備えます。法が許すところではデータをオープンに公表し、アクセシビリティの義務を満たし、必要な期間記録を保ち、判断を文書化します。法定の数字を個人のパフォーマンスの目標に変えるのに抵抗し、目標が市民とスタッフに与える影響を考えます。

## ビジネスケース：動機、ROI、TCO

コストは、義務の台帳を構築し維持する労力、自動化された抽出とテンプレートのエンジニアリング、レビューの時間、アクセシビリティのテストです。手作業での組み立てと比べて、自動化は労力を繰り返される仕事から、一度限りの構築と軽い保守に移します。

見返りは、エラーと訂正の減少、組み立てに費やすスタッフの時間の減少、監督の依頼へのより速い応答、規制当局と市民とのより大きな信頼です。自分たち自身のデータからケースを築きます。前後のレポートあたりの時間、訂正再提出の件数と影響、監督の質問に答える時間、回避された違約金や重大な監査の所見のコスト。出典と方法をたどれない限り、コンプライアンスの負担の見積もりの引用は避けます。監督機関との継続的な関わりのコストを含め、驚きのコストと比較します（トピック 7.7「投資対効果とビジネスケース」を参照）。

## アンチパターンと落とし穴

- **法定の数字だけで管理する。** 仕事を歪める。相棒の測定値を伴う作業用の見方を保つ。
- **突合されていない二組の数字。** 信頼が崩れる。違いを文書化して示す。
- **システムとしての手作りのスプレッドシート。** 壊れ、個人に依存する。記録システムから自動化する。
- **日付に間に合わせるために不完全なレポートを提出する。** 一つの失敗を別の失敗と交換する。延長に合意するか、明確な注意書きとともに提出する。
- **静かな訂正。** 信頼を損なう。公然と訂正し、説明する。
- **法定の数字からの個人の目標。** 悪用を報い、誠実なスタッフを罰する。数字をサービスのレベルに保つ。
- **読めない公表物。** 形式上のコンプライアンスは、目的を損なう。使えるアクセシブルなデータを公表する。
- **公表でプライバシーを無視する。** 少数は人を特定しうる。集約し、開示をレビューする。

## チェックリスト

- [ ] 台帳が、すべての報告義務を、オーナー、定義、情報源、期日、受け手の機関とともに列挙している。
- [ ] 必要な項目とイベントが、最初からサービスに組み込まれている。
- [ ] レポートが、バージョン管理されたクエリとテンプレートによって、記録システムから作られる。
- [ ] 報告される各数字に、文書化された系譜と名前付きの確認者がある。
- [ ] 独立した読み手が、提出前にレポートをレビューする。
- [ ] 法定と社内の定義が突合され、両方が示されている。
- [ ] 訂正が記録され、説明され、速やかに公表される。
- [ ] 法定の目標に、相棒の測定値とレポートの文脈がある。
- [ ] 公表されたレポートとデータセットが、適用されるアクセシビリティ基準とプライバシーのレビューを満たしている。
- [ ] 各主要な監督機関との、その必要についての対話がカレンダーにある。

## AIプロンプト

**義務の台帳を築く。**

```text
以下は、負っていると思われるレポート、通知、公表物の一覧です：[情報源とともに平易な言葉で貼り付け]。それらを、要件、情報源、定義、データソース、期日、受け手の機関、オーナーの役割の項目を持つ台帳に構造化してください。欠けている情報と、チーム間で重複していそうな義務に印を付けてください。法的な結論を出さないでください。前提と、法務とコンプライアンスへの問いを列挙してください。
```

**二つの定義を突合する。**

```text
[測定値] の法定の定義は：[文面]。私たちの社内の定義は：[文面]。私たちのデータ項目は：[一覧]。違いを説明し、それぞれが数字にどう影響するかを述べ、レポートで両方をどう示すかを示唆し、読み手に違いを説明する短い注記を提案してください。与えられていない事実を仮定しないでください。前提を列挙してください。
```

**レポートの自動化を計画する。**

```text
[レポート] を、次の手作業のステップと情報源を使って毎月作成しています：[時間付きの一覧]。記録システムからそれを自動化する計画を、文書化されたクエリ、変換のステップ、系譜のメモ、レビュー、過去のレポートの再現可能性を含めて提案してください。何を手作業のままにすべきか、なぜかを示唆してください。特定のツールを仮定しないでください。前提とリスクを列挙してください。
```

**公表されたレポートの使いやすさをレビューする。**

```text
以下は公表を予定しているレポートのテキスト構造です：[見出しと、機微な内容を含まない表のサンプルを貼り付け]。平易な言葉、定義、数字の文脈、表とグラフのアクセシビリティ、少数からのプライバシーのリスクについてレビューしてください。改善を提案してください。支援技術でテストすること、開示の規則を専門家と確認することを私に思い出させてください。前提を列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：法定または規制された報告のメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：報告のメトリクスの項目が、定義、突合、悪用の手口、防護柵を示しているかを確認するときに使います。

## 要点

- 報告義務を、オーナー、定義、期日とともに列挙された設計への入力として扱う。
- 系譜と独立したレビューを伴って、記録システムからレポートを作る。
- 率直な作業用の見方を報告の見方から分けておき、定義を公然と突合する。
- 法定の目標を相棒の測定値と組にし、個人の目標には決して変えない。
- エラーを公然と素早く訂正する。
- 一般市民が見つけ、読み、再利用できる情報を、プライバシーを守って公表する。
