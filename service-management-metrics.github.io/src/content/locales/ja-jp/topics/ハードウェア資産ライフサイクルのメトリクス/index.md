# ハードウェア資産ライフサイクルのメトリクス

**デバイスは意欲のある人々の日々の道具であり、同時にコスト、リスク、無駄の流れでもある。したがって、更新を定期的な急変ではなく着実な流れとして計画し、年齢と故障を自分たち自身のデータから測り、安全な廃棄と再利用を仕事の一部として扱う。**

## 概要と動機

すべてのサービスの背後には、物理的なモノがあります。ノートパソコン、電話、サーバー、ネットワーク機器、プリンター、それらを束ねるケーブルとラック。ハードウェアには、ソフトウェアにないライフサイクルがあります。購入され、出荷され、イメージが書き込まれ、配られ、修理され、移され、廃止され、消去され、リサイクルされ、各ステップにコストとリスクがあります。顧客との通話中に故障するノートパソコンは、そのノートパソコン以上のコストがかかります。ディスクにデータを残したまま建物を出る廃止されたサーバーは、その再販価値よりはるかに多くのコストがかかります。使われていない電話の引き出しは、何もしていない資本です。

意欲のある個人を中心にプロジェクトを構成し、彼らに必要な環境と支援を与えるというアジャイルの狙いは、直接当てはまります。遅い、故障する、あるいはないデバイスの上で、人々は最良の仕事をできません。ITILの伝統は、ライフサイクルの見方とそれに伴う記録をもたらし、それは前のIT資産管理のトピックで扱いました（トピック 7.1「IT資産管理のメトリクス」を参照）。このトピックは、物理的な機器に固有の測定値を加えます。どれだけ古いか、どのくらいの頻度で故障するか、どれだけうまく使われているか、どう去るか。

ハードウェアの計画は、しばしば大きな周期で行われます。数年ごとにすべてを一つの大きな購入で置き換え、その結果と付き合う。継続的デリバリーの精神での、より着実な代替は、環境の一部を継続的に更新することです。それは支出をならし、イメージングと引き渡しの作業負荷を分散し、次を購入する前に各バッチから学べるようにします。また、各デバイスをいつ去らせるかを決めるために、年齢と故障のデータが必要になることも意味します。

三つの考え方が測定値を整理します。

- **年齢と故障。** デバイス集団の[故障率（failure rate）](https://en.wikipedia.org/wiki/Failure_rate)は寿命にわたって変化し、[平均故障間隔（MTBF：mean time between failures）](https://en.wikipedia.org/wiki/Mean_time_between_failures)は、修理可能なアイテムの一般的な要約である。平均は多くを隠す。欠陥のある部品を持つバッチは早く故障し、残りは問題ないかもしれない。故障をモデル、バッチ、年齢帯別に見て、計画には、メーカーの数字ではなく、自分たち自身の履歴を使う。
- **利用率。** 誰も使わないデバイスは無駄であり、過負荷のデバイスは摩擦の源である。機器が使われているか、仕事に合っているかを測る。
- **責任ある退出。** 廃止された機器は、機微なデータを保持し、価値のある、そして有害な物質を含み、電子廃棄物を増やしうる。[電子廃棄物（electronic waste）](https://en.wikipedia.org/wiki/Electronic_waste)は増大する環境上の懸念で、多くの法域がその扱い方を規制している。安全な[データ消去（data erasure）](https://en.wikipedia.org/wiki/Data_erasure)と認証された再利用またはリサイクルは、ライフサイクルの終わりであり、後付けではない。[循環型経済（circular economy）](https://en.wikipedia.org/wiki/Circular_economy)のアプローチは、製品と素材をできるだけ長く使い続ける。

ハードウェアのメトリクスは、おなじみの歪みにさらされています。低い平均デバイス年齢で報われるチームは、問題のないデバイスを更新するかもしれません。低い支出で報われるチームは、故障が人々を妨げるまで寿命を引き延ばすかもしれません。[グッドハートの法則（Goodhart's law）](https://en.wikipedia.org/wiki/Goodhart%27s_law)からの防護柵が当てはまるので、各測定値は、数字だけでなく、人々と地球がより良い状態にあることの確認と組になっています（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

## 主要な原則

- **着実な流れを計画する。** 期間ごとに環境の一部を更新し、各バッチから学ぶ。
- **証拠で決める。** 自分たち自身の故障、年齢、利用のデータを使って、いつ交換するかを選ぶ。
- **分布を見る。** 平均は、古く、故障し、遊んでいる裾を隠す。
- **総コストを数える。** 購入価格は、デバイスの寿命にわたるコストの一部である（トピック 7.5「サービスコストとユニットエコノミクス」を参照）。
- **最後までデータを守る。** デバイスは、データが消え、証拠が記録されるまで、廃止されていない。
- **再利用と修理を優先する。** 機器が人々にうまく役立つ限り、使い続ける。
- **機器を働く環境の一部として扱う。** 人々には、動くデバイスが必要である。

## 推奨事項

### 流れを計画する

**1. 各クラスに計画された寿命を設定し、仮説として扱う。** ベンダーの保証と自分たちの経験から始め、データが届くにつれて見直します。ノートパソコンは数年、ネットワーク機器はより長く、酷使されるデバイスはより短いという計画された寿命が典型ですが、自分たちの環境に合う正しい数字は、自分たち自身の故障と利用のデータから来ます。台帳に根拠を書きます。

**2. 小さなバッチで継続的に更新する。** 毎月または四半期ごとに、年齢、故障の履歴、必要に従って並べた、着実な割合のデバイスを交換します。小さなバッチはコストをならし、イメージングと引き渡しの作業を分散し、コミットする前に少数のユーザーで新しいモデルをテストできるようにします。数年ごとの単一の大きな更新は、リスクと労力を集中させます。

**3. 控えめな予備の緩衝を持つ。** 準備のできたデバイスの小さなプールは、故障、紛失、新入社員の交換のリードタイムを短くします。緩衝の大きさを自分たち自身の故障と採用の履歴から決め、四半期ごとにレビューします。利用率を歪めないよう、予備を独自のクラスとして数えます。

**4. 財務に対してではなく、財務とともに計画する。** デバイスがどう資産計上され、減価償却されるか、着実な更新が予算にどう現れるかに合意します。[減価償却（depreciation）](https://en.wikipedia.org/wiki/Depreciation)の規則は、紙の上でいつ交換が最も安いかに影響しますが、人々にまだうまく役立っているデバイスの交換を駆動すべきではありません。計画とその前提の共有の見方を保ちます。

### 自分たち自身のデータから学ぶ

**5. モデル、バッチ、年齢別に故障を研究する。** 修理とインシデントの記録を台帳に結合し、モデルと年齢帯別の100台あたり年間の故障を見ます。早く故障するバッチ、特定の形で故障するモデル、故障が上がり始める年齢を探します。所見を使って、モデルを選び、交換の時期を決めます。小さな標本には注意し、モデルのデバイス数が判断には少なすぎるときは、そう述べます（トピック 1.6「サービスメトリクスのための統計リテラシー」を参照）。

**6. 保証と修理を賢く使う。** [保証（warranty）](https://en.wikipedia.org/wiki/Warranty)が何をどのくらいの期間カバーするかを知り、請求を記録し、修理のコストを交換と比較します。修理は機器を使用中に保ち、廃棄物の流れから外します。部品と情報の修理する権利は、いくつかの場所で活発な政策のテーマです。他の条件が同じなら、修理とアップグレードができるモデルを優先します。

**7. 利用を測って、遊んでいるものと負荷のかかっているものを見つける。** 活動データをクラスごとに集約し、決して使われないデバイスと、一貫して限界まで使われているデバイスを探します。遊んでいるデバイスは再割り当てまたは廃止できます。負荷のかかっているデバイスは摩擦で、ユーザーはそれを感じるでしょう（トピック 6.4「ユーザー体験と従業員体験」を参照）。プライバシーを尊重します。クラスとグループ別に報告し、個人別には決して報告せず、最小限のデータを使います。

**8. 交換のリードタイムをサービスとして追跡する。** 故障や紛失の後、人が動くデバイスを得るまでにどのくらいかかるかを測り、ステップを含めます。報告、承認、在庫、イメージング、配送、引き渡し。85パーセンタイルは、運の悪い事例がどれだけ悪いかを教えます。最も遅いステップを先に直します。

### デバイスをうまく管理する

**9. デバイスを中央で一貫して管理する。** [モバイルデバイス管理（mobile device management）](https://en.wikipedia.org/wiki/Mobile_device_management)や同様のツールは、デバイスの登録、設定、更新、消去を遠隔で行えるようにし、手作業とリスクを減らします。台帳を正確に保ち、人々の集中に配慮して更新を配信し、紛失したデバイスへの対応を支えるために使います。

**10. 安全な廃棄を定義されたプロセスにする。** 米国国立標準技術研究所が公表しているガイダンスや、自分の法域での同等のものなど、媒体の消去について認められた規格に従います。各デバイスについて、方法、日付、証拠を記録し、破壊とリサイクルには認証されたパートナーを使います。証拠のない廃棄のステップは、ギャップです。

**11. 再利用を優先し、次にリサイクルする。** デバイスがまだ動くなら、社内で再配置するか、承認されたパートナーを通じて寄付するか、消去した後に再販します。残りには認証されたリサイクル業者を使います。廃止されたデバイスのうち各経路に行く割合と、直接廃棄物に行くものの理由を測ります。電子廃棄物の規制は法域によって異なり、執行されるので、法務とサステナビリティの同僚を関与させます。

**12. ライフサイクルを、それを使う人々とレビューする。** 四半期に一度、財務、セキュリティ、調達、サービスデスク、数人のユーザーを集めて、年齢、故障、リードタイム、廃棄を見ます。何がうまくいき、何が人々を苛立たせているかを尋ねます。これは働く環境をめぐる継続的な協働で、計画を現実的に保ちます。

## 悪用の手口と防護柵

| メトリクス | 悪用のされ方 | 組になる防護柵のメトリクスまたはプラクティス |
| --- | --- | --- |
| 年齢構成 | 平均を下げるために健全なデバイスを交換する、予備として再分類して古いデバイスを除外する | 年齢帯別の故障率。遊んでいるデバイスの割合。再分類のレビュー |
| 更新の期限内達成率 | 計画した窓を広げる、計画を編集して計画日を延期する | 理由とともに記録される計画の変更。故障とユーザーのフィードバックと比較する |
| モデル別の故障率 | 故障をユーザーの損傷やソフトウェアの故障としてコード化する、修理の記録を遅らせる | 故障のコード化を抽出する。修理の記録をインシデントの記録と比較する |
| 遊んでいるデバイスの割合 | 予定されたバックグラウンドの活動を利用として数える、遊んでいるデバイスを幽霊ユーザーに再割り当てする | 人のサインインを活動のシグナルとして使う。割り当てを抜き取り確認する |
| 交換のリードタイム | 発送で時計を止める、ユーザーが動くデバイスを持つ前に依頼をクローズする | 時計はユーザーの確認で終わる。最近の交換のアンケート |
| 安全な廃棄の完了 | 証拠なしに消去を記録する、証明書がシリアル番号と照合されない | 証明書をシリアル番号と照合する。廃棄のパートナーとともに抽出を監査する |
| 再利用とリサイクルの率 | 下流の取り扱いが不明なブローカーに送られたデバイスをリサイクルとして数える | 認証されたパートナーと下流の報告を求める。抽出の監査 |

健全な読みは、細い古い裾を持つ年齢構成、購入を導く故障率、短い交換時間、完全な廃棄の証拠、そして廃棄物に行く機器の割合の減少です。

## トレードオフ：長所と短所

| 手法 | 強み | 弱み |
| --- | --- | --- |
| 固定周期の更新 | 予測可能な予算と単純な規則 | 問題のないデバイスを交換する。作業の大きなピークを作る |
| バッチでの継続的な更新 | コストと作業負荷が滑らか。バッチの間に学べる | 良いデータと規律が要る |
| 故障するまで使う | 購入コストが最も低い | 人々を妨げる。計画外のコスト。古いシステムのセキュリティリスク |
| 短い計画された寿命 | より新しく、速く、よりよく支援される | コストが高く、無駄が多い |
| 長い計画された寿命 | コストが低く、無駄が少ない | 裾でより多くの故障とセキュリティの露出 |
| 社内での修理と再利用 | デバイスを使用中に保つ。無駄が少ない | 技能と部品が要る |
| 外部委託の廃棄 | 専門的な取り扱い | 下流の連鎖の監督が要る |

散文での答えは、年齢、故障、必要に基づいて小さなバッチで継続的に更新し、人々の役に立つところでは修理と再利用を行い、廃棄の連鎖を証拠で示せる基準で保つことです。

## チームで話し合う問い

**1. 私たちのデバイスの年齢と故障の様子はどうで、最も古いものを持っているのは誰か？**
年齢の分布と、年齢帯別の故障率を示します。最も古いデバイスを持つのが誰か、その人々が信頼できる機器を最も必要とする人々かを見ます。ファシリテーターは、その様子に基づいて、チームが更新の順序について何を変えるかを尋ねてください。

**2. デバイスが壊れてから、動くデバイスを得るまでどのくらいかかるか？**
直近三回の交換を、報告から動くデバイスまでたどります。待ちに注意します。どのステップを取り除く、あるいは自動化できるかを尋ねます。変更を一つと、効果を測る方法に合意します。

**3. 最も問題を起こすモデルはどれで、どうやってそれを知るか？**
故障またはチケットの率が最も高いモデルを列挙します。標本が判断に十分大きいかを確認します。所見が次の購入にどう影響するかを尋ねます。しないなら、調達にどうフィードバックするかを決めます。

**4. 廃止されたデバイスがデータ付きで現れたら、どうするか？**
廃棄の経路と、各ステップで保たれる証拠を通して確認します。最も弱いリンクはどこで、下流のパートナーを誰が検証するかを尋ねます。次の四半期に廃棄の証拠の抜き取り確認を行うことに合意します。

**5. 私たちの機器はどこで遊んでいて、なぜか？**
60日間利用のないデバイスと予備を見ます。再割り当て、廃止、保持のどれにすべきかを尋ねます。対話はまた、人々に発行されたものと、彼らが必要とするものの間のミスマッチを明らかにします。

**6. 廃止したものをもっと再利用または修理するには、何が要るか？**
障壁を列挙します。技能、部品、ポリシー、パートナー。一つのデバイスクラスでのパイロットがどんなもので、どう測られるかを尋ねます。サステナビリティと財務の視点を含めます。

## 四つの視点

### プロダクトとデリバリーのチーム

デリバリーのチームは、信頼できるマシンとテスト用のデバイスに依存し、遅いビルドと故障するノートパソコンを直接感じます。自分たちを遅くする機器にフラグを付け、自分たちの役割のモデルの選択に参加し、素早い交換の経路を期待するべきです。電話のような物理的なデバイスでテストするチームは、それらのデバイスを、オーナーと更新計画を持つ資産として扱うべきです。

### サービスと運用のチーム

運用チームは、購入、受領、イメージング、デプロイ、修理、廃棄というサプライチェーンを運営します。記録を最新に保ち、故障のパターンを見て、妥当な予備のプールを持ち、廃棄の証拠を保つべきです。物理的な作業を担い、そのキャパシティが、更新をどれだけ速く進められるかを制限します。

### リーダーシップとガバナンス

リーダーは、予測可能なコスト、低いリスク、サステナビリティの物語を求めます。着実な更新に資金を付け、単なる平均年齢の代わりに年齢と故障のデータを求め、廃棄の証拠を要求するべきです。ガバナンスは、環境とデータ保護の義務が満たされ、状況の変化に応じて計画が見直されていることを確認するべきです。

### 顧客とユーザー

ユーザーは、動くデバイスと、動かないときの素早い交換を望みます。また、成果の一部も彼らが担います。問題を早く報告する、機器を返却する、異動するときにITに伝える。機器と交換プロセスについての彼らの見方は、利用可能な最も直接的なフィードバックです。自分の仕事のモデルの選択に彼らを関与させます。

## 実践：サービスマネジメントの例

郡政府のIT部門が、40の拠点にわたって3,800人のスタッフを支え、オフィス、現場、共有のデバイスが混在しています。以下の数字は例示です。

4年ごとに、郡はすべてのノートパソコンを一回の調達で交換し、前回の周期は、交換前の年の故障の急増と、交換の年の数か月にわたるイメージングの作業で終わりました。資産マネージャーは着実な更新を提案し、台帳と修理の記録から様子を構築します。ノートパソコンの年齢の中央値は3.2年、85パーセンタイルは5.1年です。100台あたり年間の故障は、3年未満のデバイスの約6から、5年超のデバイスの約19に上がります。一つのバッチで購入された一つのモデルは、2年経過時点で100台あたり年間24件の故障を示し、原因はバッテリーの欠陥です。交換のリードタイムの中央値は5日で、85パーセンタイルは12日、主にイメージングの待ちです。遊んでいるデバイスの割合は7パーセントで、ほとんどは予備と長期休暇中のスタッフのデバイスです。昨年廃止された410台のノートパソコンのうち、366台に消去の証明書の記録があり、完了率は89パーセントで、12パーセントは下流の報告なしにリサイクル業者に行きました。

チームは四つの変更を行います。年齢と故障の履歴に従って並べた、ノートパソコンの約6パーセントの四半期ごとの更新に移行し、現場のスタッフと最も古いデバイスを先にします。欠陥のあるバッチについて、保証のもとで供給者と交渉します。標準のイメージをあらかじめ搭載した、環境の2パーセントの予備のプールを持ち、イメージングの待ちを減らします。廃棄されるすべてのデバイスに、シリアル番号と照合した証明書を求め、下流の取り扱いを報告するリサイクル業者に移行します。また、4年未満のデバイスを再生して再配置する小さなパイロットを始めます。

二四半期後、交換のリードタイムの85パーセンタイルは4日で、5年超のデバイスの割合は22パーセントから13パーセントに下がり、廃棄の証拠の完了は99パーセントで、承認された経路による再利用とリサイクルの率は94パーセントです。財務部門は、平均デバイス年齢の単一の目標を求め、資産マネージャーは、低い平均年齢は健全なデバイスを交換することで買えると説明して、年齢構成と故障率を一緒に追跡することを提案します。判断は判断ログに記録され、6か月後にレビューされます。

## アジャイル、AI、自動化、アナリティクス

### アジャイル

更新を着実な流れとして計画し、年齢と故障のデータをユーザーと定期的にレビューします。注意点は、硬直した交換年齢は、動くデバイスを無駄にし、予算に負担をかけることです。

### AI

AI機能は、たとえばローカルモデルのために、ハードウェアの要件を引き上げることがあり、更新の時期を変えます。故障と年齢を自分たち自身のデータから追跡し、人々が必要とするツールを動かせないデバイスの測定値を加えます。注意点は、AI対応ハードウェアについてのベンダーの主張は、自分たちのワークロードに対してテストすることです。

### 自動化

保証の日付や廃棄のステップなどのライフサイクルのイベントを自動化し、自動化を見逃したイベントで測ります。注意点は、自動の消去と廃棄のワークフローには完了の証明が要るため、抽出を監査することです。

### アナリティクス

年齢構成とモデル別の故障率を、件数とともに示します。これが情報を与える判断は、期間ごとにどれだけ更新するかです。注意点は、小さな台数の故障率はノイズが多いため、少数のデバイスから結論を出すのは避けることです。

## 業種別の視点

**スタートアップ。** デバイスは必要に応じて、しばしば使う人自身によって購入されます。購入日を持つ単純な一覧を保ち、退職時にデバイスを消去し、買いすぎを避けます。後から改修するより安いので、早期にマネージドな登録ツールを使います。

**中小企業。** 故障したデバイスのコストは少数の人にかかります。予備を一、二台持ち、保証の日付を記録し、消去と廃棄の手順を持ちます。地元のリサイクル業者や再生業者は良いパートナーになりえます。三行の廃棄チェックリストは、ないよりはるかに良い。

**大企業。** 規模は、バッチの振る舞いと供給者管理を重要にします。故障データを使って供給者と交渉し、クラスごとに少数のモデルを標準化し、物流の支援を伴う継続的な更新を運営します。ハードウェアがITのフットプリントを支配することが多いので、サステナビリティの報告と整合させます。

**政府・公共部門。** 調達規則、記録の保持、厳格なデータ保護がライフサイクルを形作ります。認められた規格に沿った消去を文書化し、廃棄の証拠を必要な期間保持し、サステナビリティと修理についての公的なコミットメントを検討します。公的機関は、電子廃棄物の報告を求められるかもしれません（トピック 8.3「コンプライアンスと監査のメトリクス」を参照）。

## ビジネスケース：動機、ROI、TCO

コストは、台帳、修理、エンドポイントのデータを結合する労力、まだなければデバイス管理のツール、予備のプール、証拠を伴う廃棄のプロセスの仕事です。節約と便益は、妨げとなる故障の減少、より滑らかな予算、機器の無駄の減少、データインシデントのリスクの低下として現れます。

自分たちのデータからケースを築きます。サポートの労力と故障あたりの失われた作業時間を含め、計画された寿命を超えてデバイスを運用するコストを、早く交換するコストと比較します。予備のプールのコストを、故障あたりに節約される失われた作業の日数と比較します。消去の証拠のない廃止されたデバイスの数と、それに続く単一のデータインシデントのコストを数えます。方法と日付を確認せずに、公表された情報源からの平均的なデバイスの寿命や電子廃棄物の数字を引用するのは避けます。総所有コストが、これらの部分をまとめ（トピック 7.5「サービスコストとユニットエコノミクス」を参照）、デバイスの完全な[総所有コスト（total cost of ownership）](https://en.wikipedia.org/wiki/Total_cost_of_ownership)には、購入、サポート、エネルギー、中断、廃棄が含まれます。

## アンチパターンと落とし穴

- **カレンダーですべてを交換する。** 動くデバイスを無駄にし、作業の急増を生む。年齢、故障、必要を使う。
- **故障するまで使う。** 計画外のコストと中断が節約を上回る。年齢の裾を見る。
- **平均年齢を目標として使う。** 健全なデバイスを交換することで満たせる。構成と故障率を示す。
- **メーカーの信頼性の数字を信頼する。** 使い方が異なる。自分たちの故障データを使う。
- **証拠なしに廃棄する。** 記録されない消去は、管理したことを示せないリスクである。
- **最安のリサイクル業者にデバイスを送る。** 下流の取り扱いが重要である。認証されたパートナーを使う。
- **デバイスを通じて人を追跡する。** クラスとグループ別に報告し、個人別には決して報告しない。
- **修理と再利用を無視する。** 機器を使い続けるほうが、安く、環境に優しい。

## 成熟度モデル

| 観点 | 1 開始 | 2 発展 | 3 標準化 | 4 管理 | 5 協調 |
| --- | --- | --- | --- | --- | --- |
| 計画 | 壊れたら買う | カレンダーによる定期的な更新 | クラスごとの計画された寿命。バッチでの着実な更新 | 年齢、故障、必要で時期を決める更新。データから大きさを決める予備 | 供給者、財務、拠点にまたがるサステナビリティの目標と調整された更新 |
| データからの学び | 故障の記録なし | 修理の記録が保たれる | モデルと年齢別の故障率が追跡される | 所見が購入と時期を変える。リードタイムが管理される | 設計と条件を改善するため、故障と利用のデータが供給者と共有される |
| 退出 | デバイスが消える | 非公式の消去 | すべてのデバイスに証拠を伴う廃棄のプロセス | 証拠が監査される。再利用とリサイクルが追跡される | 認証されたパートナーと公的な報告を伴う循環型の実践 |

## チェックリスト

- [ ] デバイスのクラスと計画された寿命が定義され、根拠が記録されている。
- [ ] 着実な更新計画があり、財務とレビューされている。
- [ ] 年齢構成、モデル別の故障率、交換のリードタイムが報告されている。
- [ ] 予備のプールが、故障と採用のデータから大きさを決められている。
- [ ] 遊んでいるデバイスが、プライバシーの規則のもとでクラス別に特定されている。
- [ ] 保証の請求と修理が記録され、購入の判断で使われている。
- [ ] 廃止されたすべてのデバイスに、記録された消去の方法と証拠がある。
- [ ] 廃棄のパートナーが認証されており、下流の取り扱いを報告している。
- [ ] 再利用とリサイクルの率が追跡されている。
- [ ] 四半期ごとのレビューに、財務、セキュリティ、調達、サービスデスク、ユーザーが含まれる。

## AIプロンプト

**モデルと年齢別の故障データを分析する。**

```text
以下は [期間] の [デバイスのクラス] のハードウェアの故障の要約で、モデル、稼働台数、年齢帯、故障数です：[表を貼り付け]。モデルと年齢によるパターンを述べ、異常に見えるバッチやモデルにフラグを付け、標本が判断には小さすぎる箇所を述べ、次に何を確認すべきかを提案してください。メーカーの数字を適用したり、ベンチマークの値を捏造したりしないでください。前提を列挙してください。
```

**継続的な更新計画を設計する。**

```text
次のクラスに [数] 台のデバイスがあります：[年齢構成付きの一覧]。故障と修理のデータ：[要約]。予算の制約：[要約]。着実な割合を交換し、年齢、故障の履歴、ユーザーの必要で交換を並べ、予備のプールを保つ、四半期ごとの更新計画を提案してください。固定周期の更新に対するトレードオフと、何を測るかを説明してください。価格を捏造しないでください。前提を列挙してください。
```

**廃棄のプロセスをレビューする。**

```text
廃止された [デバイスの種類] の廃棄のプロセスは次のとおりです：[ステップ、パートナー、記録を説明]。データの消去、証拠、証拠保全の連鎖、環境上の取り扱いのギャップについてレビューし、改善と抜き取り確認を提案してください。要件は法域によって異なり、法務とセキュリティの専門家と確認すべきことに言及してください。法的な結論を出さないでください。前提を列挙してください。
```

**交換のリードタイムを短縮する。**

```text
故障したデバイスの交換は、現在、次のステップと典型的な待ちを要します：[一覧]。最も遅いステップを特定し、変更（たとえばあらかじめ準備した予備、遠隔の登録、簡略化された承認）を提案し、中央値と85パーセンタイルへの効果をどう測るかを述べてください。私たちが述べていないツールを仮定しないでください。前提とリスクを列挙してください。
```

## AIスキル

- [サービスマネジメントメトリクスのスキル](../../../../skills/service-management-metrics-skill/SKILL.md)：ハードウェアのライフサイクルのメトリクスの、組になる防護柵を探すときに使います。
- [サービスマネジメントメトリクスのメンテナースキル](../../../../skills/service-management-metrics-maintainer-skill/SKILL.md)：ハードウェアのメトリクスの項目が、悪用の手口、防護柵、証拠の規則を備えているかを確認するときに使います。

## 要点

- 自分たち自身の年齢、故障、利用のデータを使って、デバイスの着実な割合を継続的に更新する。
- 平均ではなく、年齢の分布とモデル別の故障を見る。
- 予備のプールと、短く測定された経路で、交換を素早く保つ。
- 証拠を伴う安全な廃棄をライフサイクルの終わりとして扱い、修理、再利用、認証されたリサイクルを優先する。
- デバイスのクラスとグループ別に報告し、機器を通じて個人を追跡しない。
- 財務、セキュリティ、調達、ユーザーとともに、ライフサイクルをレビューする。
