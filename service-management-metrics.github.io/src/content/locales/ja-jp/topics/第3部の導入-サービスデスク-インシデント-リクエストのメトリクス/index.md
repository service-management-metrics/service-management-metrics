# 第3部の導入：サービスデスク、インシデント、リクエストのメトリクス

**サービスデスク、インシデント、リクエストのメトリクスは、サービスを使う人々にとって、サポートと復旧の仕事がどれだけうまく機能しているかを示す。そのため、レポートの見栄えではなく、助けを得る体験を改善できる。**

この部は、ユーザーがサービスに出会う、本書の部分です。サインインできない人、注文が失敗する顧客、新しいノートパソコンが必要な従業員は、みなサービスデスク、監視のアラート、セルフサービスのポータル、チャットのメッセージを通じて組織に到達します。その後に何が起きるかが、サービス全体をどう判断するかを決めます。この領域のメトリクスは、その体験を二つの側から記述します。何かが壊れたときに組織がどれだけ速く、どれだけうまくサービスを復旧するか、そして人々が出す日常的なリクエストをどれだけ確実に履行するか。

ITIL 4では、インシデント管理とサービスリクエスト管理は別個のプラクティスで、サービスデスクは両方の窓口です。自分たちが作ったものを運用するアジャイルのチームは、同じ仕事を、オンコールの輪番と共有のキューで扱うことがよくあります。どちらの場合も、測定の問題は似ています。件数は仕事の分類の仕方に依存し、時間は時計がどこで始まりどこで止まるかに依存し、平均はユーザーが覚えている長い遅れを隠します。第1部で述べた統計の習慣は、全体を通じて当てはまります（トピック 1.6「サービスメトリクスのための統計リテラシー」を参照）。

サポートのメトリクスは、特に悪用されやすいものです。デスクは、早めにクローズすることでチケットをより速くクローズでき、電話の相手を急がせることで処理時間を短縮できます。チームは、インシデントをリクエストに再分類することで、インシデントの件数を減らせます。そのため、この部の各トピックは、メトリクスが報いる振る舞い、隠す振る舞い、その違いを捉える防護柵に名前を付けています（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。ここのすべての測定値は、チーム、サービス、システムを記述します。個々のエージェントや対応者に順位を付けるものはありません。

四つの視点は、この部で最も重要です。AIによるトリアージ、仮想エージェント、自動化された履行が、これらの測定値が数える仕事の一部を扱うようになっているからです。人に届かなかった問い合わせは、問題が解決されたときにのみ成功なので、ここの各速さまたは量の測定値は、再問い合わせ、再オープン、または品質の測定値と組にします。自動収集が時計を供給し、アナリティクスは、その背後にある事例の数とともに分布を示します。

## この部のトピック

- **3.1 サービスデスクのメトリクス**：問い合わせの量、初回問い合わせでの解決、放棄、処理時間。それぞれが何を報い、何を隠すか。
- **3.2 インシデントの件数と優先度**：インシデントの件数、区分、影響と緊急度、優先度の構成、繰り返されるインシデント、利用状況に対する量の正規化。
- **3.3 インシデントの対応時間と解決時間**：検出、確認応答、対応、解決までの時間。平均時間の測定値とその統計上の問題。代わりにパーセンタイルを使う。
- **3.4 重大インシデントのメトリクス**：頻度、継続時間、顧客への影響、連絡のタイムリーさ、アクションのやり切り。
- **3.5 サービスリクエスト履行のメトリクス**：履行時間、バックログ、カタログ項目別のリクエスト量、自動化の割合。
- **3.6 ナレッジマネジメントのメトリクス**：記事の利用、解決での再利用、リンク率、鮮度、ナレッジ中心のサービス（KCS）の指標。
- **3.7 セルフサービスと自動化のメトリクス**：デフレクション、セルフサービスの成功、自動化の網羅率、量と複雑さに対するシフトレフトの効果。

## これらのトピックの相互関係

最初の四つのトピックは、障害の一生をたどります。問い合わせがデスクに届き、これがトピック3.1の関心事です（トピック 3.1「サービスデスクのメトリクス」を参照）。故障を報告するものがインシデントになり、トピック3.2（トピック 3.2「インシデントの件数と優先度」を参照）が件数を数え、影響と緊急度で分類します。トピック3.3（トピック 3.3「インシデントの対応時間と解決時間」を参照）は、各段階にかかる時間を測ります。深刻な被害を引き起こす少数のインシデントは、トピック3.4（トピック 3.4「重大インシデントのメトリクス」を参照）で独自に扱われます。その希少さと大きさのために、通常の平均が誤解を招くからです。

これらの測定値の多くは、誠実さを保つために相棒を必要とします。トピック3.1の処理時間のようなデスクでの速さは、初回問い合わせでの解決と、それが生む再問い合わせと並べて読むべきで、速い電話が解決された問題と取り違えられないようにします。トピック3.3の解決時間は、トピック3.2の繰り返されるインシデントと並べるべきです。一週間後に再び失敗する素早い復旧は、ユーザーの役に立っていないからです。トピック3.2の優先度の構成は、すべての時間の測定値に文脈を与えます。解決時間の中央値の上昇は、チームの対応の良し悪しの変化ではなく、到着するインシデントの種類の変化を反映しているかもしれません。

リクエストとインシデントは並べて測るべきですが、決して統合してはいけません。トピック3.5（トピック 3.5「サービスリクエスト履行のメトリクス」を参照）は、リクエストあたりの労力が安定して縮小することが狙いである、予測可能で繰り返し可能な履行の仕事を扱います。インシデントの仕事は予測できず、その狙いは、速く耐久性のある復旧です。両者を一つのキューの平均にまとめると、両方の問題が隠れます。第2部のフロー指標は、共有の時計と、二つの流れが互いに飢えさせないための仕掛かり作業の制限を供給します（トピック 2.9「運用作業と計画外作業」を参照）。

最後の二つのトピックは、他のトピックが測る量に作用します。トピック3.6（トピック 3.6「ナレッジマネジメントのメトリクス」を参照）のナレッジは、前の人が学んだことを次の人が再利用できるようにして解決を短縮し、トピック3.7（トピック 3.7「セルフサービスと自動化のメトリクス」を参照）で測るセルフサービスのコンテンツに供給します。デフレクションと自動化は、デスクに届く単純な問い合わせを減らし、残った人々にはより難しい仕事の構成を残します。その変化は予期されるべきで、結果として処理時間が上がることもあるため、パフォーマンスの低下ではなく、構成の変化として読むべきです。

繰り返されるインシデントは、第4部の問題管理への入力になります。
