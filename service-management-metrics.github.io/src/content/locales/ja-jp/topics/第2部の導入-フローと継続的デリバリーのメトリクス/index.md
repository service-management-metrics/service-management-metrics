# 第2部の導入：フローと継続的デリバリーのメトリクス

**フローのメトリクスは、サービスを構築し運用するチームを仕事が実際にどう流れるかを示す。それにより、仕事がどこで待つかを見つけ、何を変えるかを決め、その変更が役立ったかを確かめられる。**

サービスも運用するアジャイルのチームは、計画された機能、欠陥の修正、サービスリクエスト、実際のインシデントによる割り込みという、混在した仕事の流れを扱います。そのすべてが、同じ人と同じ注意を奪い合います。フローのメトリクスは、その流れを、作業アイテムの視点から記述します。いくつのアイテムが進行中か、どのくらいかかるか、どのくらい古いか、期間内にいくつが終わるかを問います。

この見方が有用なのは、遅れの大半が、働いている時間ではなく待っている時間だからです。リクエストは、キュー、レビュー、承認の中で、誰かがそれに費やす時間よりもはるかに長く座っていることがあります。人の労力ではなく、アイテムの時計を測ることで、そうした隙間が露わになり、チームに改善のための共有された事実に基づく出発点が与えられます。それはまた、両方の世界に合います。アジャイルの実践はサイクルタイムとスループットを語り、ITILの実践はバリューストリームとサービスパフォーマンスを語ります。どちらも同じ仕事の動きを記述しているのです。

フローのデータは偏っており、誤用しやすいものです。時間の測定値は、第1部で述べたように、パーセンタイルを伴う分布として読むべきです（トピック 1.6「サービスメトリクスのための統計リテラシー」を参照）。この部のすべてのメトリクスは、チーム、サービス、システムを記述します。個人に順位を付けるものはなく、単独で押し上げたり押し下げたりする目標にするものもありません（トピック 1.2「グッドハートの法則とメトリクスの心理学」を参照）。

本書の四つの視点は、ここで独特の形で現れます。継続的デリバリーとステークホルダーの関与が、測定される仕事のリズムを決めます。AIの支援は、アイテムが待つ時間を短縮せずに、完成して見えるアイテムの数を増やすことがあるため、フローの測定値は手戻りと品質のシグナルと組にされます。自動化はイベントのタイムスタンプを供給し、自らも失敗について測定されるべきです。アナリティクスは時計を範囲と傾向に変え、それぞれの背後にあるアイテムの数を示します。

## この部のトピック

- **2.1 フロー指標**：仕掛かり作業、スループット、作業アイテムの年齢、サイクルタイムを、プロジェクトとサービスの仕事に適用する。
- **2.2 リードタイム、サイクルタイム、フロー効率**：チームをまたいで通用する定義、時計がどこで始まりどこで止まるか、待ち時間を露わにする方法。
- **2.3 仕掛かり作業と待ち行列**：リトルの法則、稼働率とキューの成長、仕掛かり作業（WIP）の制限、そして完全に忙しいサービスチームが遅いチームである理由。
- **2.4 バリューストリームのメトリクス**：バリューストリームマッピングの測定値、処理時間、待ち時間、完全かつ正確な割合、ITILのバリューストリーム。
- **2.5 デリバリー予測と計画のメトリクス**：ストーリーポイントとベロシティ、デリバリーゴールの成功、予測の精度、そしてベロシティをチーム間で比較してはならない理由。
- **2.6 バックログとリファインメントのメトリクス**：バックログの大きさと年齢、準備ができた仕事、リファインメントの網羅率、プロダクトとサービスのバックログの違い。
- **2.7 プルリクエストとコードレビューのメトリクス**：フローのシグナルとしてのレビュー時間、プルリクエストの大きさ、手戻りと、それに伴う悪用の手口。
- **2.8 DORAメトリクス**：変更のリードタイム、デプロイ頻度、失敗したデプロイからの復旧時間、変更失敗率、デプロイの手戻り率。研究自身の注意点を含む。
- **2.9 運用作業と計画外作業**：計画された仕事と計画外の仕事、割り込みの負荷、緊急レーン、変更の仕事と運用の仕事の間でのキャパシティ配分。

## これらのトピックの相互関係

最初の四つのトピックが、この部の中核を成します。トピック2.1（トピック 2.1「フロー指標」を参照）は、仕掛かり作業、スループット、作業アイテムの年齢、サイクルタイムという基本的な量を定義します。トピック2.2（トピック 2.2「リードタイム、サイクルタイム、フロー効率」を参照）は、あらゆる比較が依存する、時計の開始と停止の位置を固定します。トピック2.3（トピック 2.3「仕掛かり作業と待ち行列」を参照）は、なぜそれらの量が一緒に動くのかを説明し、トピック2.4（トピック 2.4「バリューストリームのメトリクス」を参照）は、一つのチームのボードから、リクエストから価値までの経路全体へと視野を広げます。

いくつかのトピックは、他のトピックの防護柵として働きます。スループットと速さの測定値は、仕事をより小さな断片に分割したり、急がせたりすることで水増しされうるため、手戻りと品質のシグナルと併せて読むべきです。トピック2.7（トピック 2.7「プルリクエストとコードレビューのメトリクス」を参照）のプルリクエストの大きさとレビュー時間は、遅れと手戻りの早期の指標です。トピック2.8（トピック 2.8「DORAメトリクス」を参照）のデリバリーのアウトカムは、速さの測定値を安定性の測定値と組にし、速いデリバリーがより多くの失敗で買われないようにします。トピック2.5（トピック 2.5「デリバリー予測と計画のメトリクス」を参照）のベロシティは、一つのチームのための計画の補助であり、アウトプットとして読むのではなく、予測の精度とフローの測定値に照らして確認すべきです。

残りのトピックは、仕事が流れる条件を記述します。長い、古い、またはリファインメントが不十分なバックログは、フローを悪くします。これがトピック2.6（トピック 2.6「バックログとリファインメントのメトリクス」を参照）の関心事です。トピック2.9（トピック 2.9「運用作業と計画外作業」を参照）で扱う計画外の仕事と割り込みは、サイクルタイムが伸び、予測が外れる隠れた理由であることがよくあります。それらをトピック2.3の仕掛かり作業と待ち行列と並べて読むと、余裕のないチームがなぜ他のすべてを遅らせずにインシデントを吸収できないのかが分かります。

以降の部は、これらの測定値の上に築かれます。第3部と第4部のインシデント、変更、リリースのメトリクスは、サポートと変更の仕事に適用した、同じ時計と同じ分布の考え方を使います。まとめれば、フローの見方は、アジャイルとITILのチームが、一つの共有された仕事のシステムについて語ることを可能にします。
