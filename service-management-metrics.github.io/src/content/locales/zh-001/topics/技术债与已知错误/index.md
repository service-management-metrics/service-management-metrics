# 技术债与已知错误

**把已知错误和技术债视为一本可见的、关于被推迟的修复的账簿，度量每一项保持未关闭的每个月让你付出什么代价，并把受保护的一份容量花在利息最高的项上。**

## 概述与动因

每个团队都会推迟一些修复。一个缺陷被理解了却没有修复，为赶日期走了捷径，一个组件被放任老化，一个变通办法被写进运行手册。每一次推迟在作出时都是明智的决定。麻烦始于推迟在看不见之处累积，因为承担它们的代价日后表现为事件、缓慢的交付和疲惫的人，而任何报告上都没有一行把代价与原因联系起来。

两套词汇描述同一种模式。在 [ITIL](https://en.wikipedia.org/wiki/ITIL) 中，**已知错误（known error）**是其根因已被理解、并存在变通办法或尚未应用的永久修复的问题。已知错误被记录下来，使服务台和运维人员能够迅速解决重复的事件，该记录保持开启，直到修复被发布。在敏捷的软件工作中，**[技术债（technical debt）](https://en.wikipedia.org/wiki/Technical_debt)**是这样一种隐喻，由[沃德·坎宁安（Ward Cunningham）](https://en.wikipedia.org/wiki/Ward_Cunningham)于 1992 年提出，指使未来变更更困难的设计和实现选择。这一隐喻携带两个对度量重要的理念：**本金（principal）**，即消除债务所需的工作量，以及**利息（interest）**，即债务存在期间你每个周期所付出的额外工作量或风险。

两种视角在看哪里上不同。已知错误通过运维被发现：一起事件或一次问题调查找到了原因。技术债通常通过交付被发现：开发人员注意到一项变更比它应有的更难。已知错误往往是已开始伤害客户的技术债。技术债往往是即将发生的已知错误。把清单分开保存，一份在 ITSM 工具中，一份在待办事项列表或维基中，会隐藏二者的联系，并为同一份稀缺的容量产生两个相互竞争的论点。

本主题为合并的账簿提供一小组测量值。它避免对整个组织的债务给出单一的美元数字，因为没有任何方法能可靠地产生它，转而度量你能观察到的：未关闭的项、等待的时间、造成的事件、增加的工作，以及花在修复上的容量。这本账簿随后为产品与运维之间的优先级排序交流提供输入（问题记录和永久修复见主题 4.1，问题管理度量，债务所造成的打断负荷见主题 2.9，运维工作与计划外工作）。

本主题中使用的术语：

- **变通办法（workaround）**是在不消除原因的情况下恢复服务或避免失败的办法。
- **永久修复（permanent fix）**消除原因。[根因分析（Root cause analysis）](https://en.wikipedia.org/wiki/Root_cause_analysis)是找到它的工作。
- **[代码重构（code refactoring）](https://en.wikipedia.org/wiki/Code_refactoring)**在不改变外部行为的情况下重构代码。它是偿还设计债的通常方式。
- **[代码异味（code smell）](https://en.wikipedia.org/wiki/Code_smell)**是代码中常常表明更深层问题的表面迹象。它是去查看一下的提示，不是裁决。
- **[机会成本（opportunity cost）](https://en.wikipedia.org/wiki/Opportunity_cost)**是你因选择把时间用于某一种用途而放弃的最佳替代方案的价值。每一项修复都与某个功能竞争，而这一比较才是真正的决定。
- **[延迟成本（cost of delay）](https://en.wikipedia.org/wiki/Cost_of_delay)**是推迟一项工作所造成的经济损失。它是为一项债务项的利息定价背后的理念。
- **[软件缺陷（software bug）](https://en.wikipedia.org/wiki/Software_bug)**是软件中的缺陷。已知错误可能是缺陷、配置弱点、设计限制或供应商缺陷。
- **[静态程序分析（static program analysis）](https://en.wikipedia.org/wiki/Static_program_analysis)**在不运行代码的情况下检查它。它的警告和复杂度得分是可能存在债务的指标，是比事件历史更弱的证据。

并非所有债务都是错误。马丁·福勒（Martin Fowler）的象限把有意的与无意的、鲁莽的与审慎的债务区分开（见参考文献清单）。附有偿还计划的审慎捷径是一笔稳妥的贷款，而鲁莽的债务则是应当预防的那一类。这里的度量不评判起源。它们显示余额。

## 关键原则

- **一本账簿，两扇门。** 来自运维的已知错误和来自交付的债务项进入同一份可见的清单，并在描述同一原因的记录之间有一个链接。
- **既度量利息，也度量本金。** 修复的规模不如未关闭项每月让你付出的代价重要，即在事件、变通办法和被拖慢的变更方面。按每单位修复工作量的利息排序。
- **让推迟成为带负责人的决定。** 每一项都有负责人、陈述的等待理由和评审日期。没有人选择推迟的项是被忽视，并被如此计数。
- **在需要之前就保护容量。** 提前商定的、为修复工作所设的每个团队容量的明确占比，胜过糟糕的季度之后英雄式的清理。
- **让变通办法保持诚实。** 变通办法是一项服务，有它自己的成本、负责人和失效模式。度量它被使用的频率和失败的频率。
- **描述系统，绝不描述人。** 债务属于一项服务或一个组件。绝不把它归于某位作者，也绝不按工程师触碰的债务给他们排名。
- **粗略地估算。** “小时”“天”和“周”的规模就够了。超出这一点的精确是虚构的。

接受风险是关闭已知错误的一种正当方式，因为有些问题不值得修复。它被单独列出，使关闭各项不会悄悄地改善年龄数字。变通办法覆盖率中 6 个月的评审窗口是一个示例。团队设定窗口以匹配其系统变化的速度，并写入度量登记册。

## 建议

### 建立账簿

**1. 把已知错误清单和债务清单合并成一本账簿。** 保持一份登记册，带有来源（运维或交付）、服务、负责人、规模区间以及与相关记录的链接等字段。ITSM 工具可以容纳它，跟踪器也可以，只要每个系统都链接到另一个。没有单一的视图，运维中的已知错误，就会与交付中未被看见的债务项争夺同样的工程师。

**2. 在债务被创建或发现的那一刻就登记它。** 有意走的捷径，在同一个拉取请求或变更记录中进入登记册，附陈述的理由和评审日期。后来发现的债务由发现者登记。一条廉价的一行字的捕获规则，比定期审计效果更好，因为人们会忘记上个季度所知道的。

### 度量利息

**3. 每次都把事件与已知错误相联。** 事件与其已知错误之间的链接，是你拥有的关于利息的最强数据，它在解决时只需几秒钟。当原因已知时，让链接成为必填字段，并报告未链接的占比，使缺口不会看起来像好消息（见主题 3.3，事件响应与解决时间）。当同一原因出现在几起事件中时，问题记录承载修复的证据。

**4. 给债务所造成的工作打标签。** 让工程师在由于已知弱点而需要变通办法、手工步骤或额外返工时标记一个工作项，并把它链接到账簿中的项。标签成本很低，却在团队层面给你债务利息的数字。把结果视为带有很大误差的估计，对给项排序和观察趋势有用，而不用于会计核算。

**5. 用两个数字给每一项定价：修复工作量和月度利息。** 对工作量使用粗略的区间，比如小时、天、周，对月度成本则依据关联的事件、被标记的工作，以及你的组织已经估算的任何停机成本，给出一个粗略的数字。用利息除以工作量，得到一个简单的回收期。不要虚构精确：一个区间和一条陈述的假设就足以把明显的速赢与可以等待的项区分开。

### 保护容量并作出决定

**6. 预留一份常设的容量占比，并报告它。** 与产品负责人商定每个周期用于修复工作的占比，依据账簿的趋势设定，并每个季度重新审视。把债务容量占比与计划工作的数字并排报告，使领导者把修复工作视为一项有意的投资。预留的占比还使团队免于在每次规划交流中争论权衡，而功能待办事项列表通常会赢得这种争论。

**7. 用同一种通货对修复与功能排序。** 把已知错误和债务项与功能放入同一场优先级排序交流，以延迟成本和回收期来表达。消除一次每周的事件、并在一个季度内收回其工作量的修复，凭自身的优点竞争。按嗓门大小、资历或登记日期排序，结果很差（见主题 4.4，变更失败与返工）。

**8. 为推迟的决定闭环。** 对每个被有意让其保持未关闭的项，记录谁接受了风险、评审日期，以及会把它往上提的触发因素，比如第二起事件或该区域的一项计划变更。按它自己的节奏评审接受清单。被推迟三次却没有触发因素的项，就是一项忽略它的决定，账簿应当如此说明。

### 保持数字诚实

**9. 先发布修复，再关闭记录。** 已知错误保持未关闭，直到永久修复进入生产环境，并在规定的窗口内检查了再发。在“已合并”或“工单完成”时关闭，会美化年龄和净变化的数字，并在之后重新打开事件（见主题 4.5，发布与部署度量）。把已知错误的重开率作为对关闭规则的质量检查来跟踪。

**10. 查看账簿的形态，而不只是总数。** 持平的计数可能隐藏一条由很老的项构成的长尾、某一项服务所占比例的增长，或一本因把一切都以“不修复”关闭而保持很小的账簿。在一页上展示年龄分布、按服务的划分和接受风险的清单。与拥有这些服务的人一起，在规划下个季度工作的同一次会议上评审它。

## 钻空子途径与护栏

| 度量 | 如何被钻空子 | 配对的护栏度量或实践 |
| --- | --- | --- |
| 已知错误待办事项列表年龄 | 以“接受风险”或“不修复”关闭旧记录；把一条旧记录拆成新的年轻记录；通过重新登记来重设时钟 | 在同一页上报告接受风险的计数和年龄；由所属团队之外的人评审关闭；保留记录谱系 |
| 变通办法覆盖率 | 为满足该字段而撰写含糊的变通办法；统计没有任何坐席试过的变通办法 | 关联事件中变通办法的使用和失败率；定期测试一批变通办法样本 |
| 与未关闭已知错误相联的事件 | 让事件保持未链接，或把它们链接到另一个原因，使占比下降 | 在其旁边报告未链接事件占比；对已关闭事件抽样评审是否漏了链接 |
| 债务存量 | 不登记债务，使存量看起来很小；把许多项合并成一个大项；登记琐事以显得勤勉 | 对照代码评审和事件事后复盘的样本评审登记册；项的规模和具体性检查 |
| 债务利息 | 为避免被审视而少打标签，或为赢得修复预算而多打标签；把该数字读作对团队的评级 | 对已标记和未标记项的抽样审计；只在团队层面查看，不在团队之间比较；利息与事件链接一起阅读 |
| 债务容量占比 | 把普通的功能工作标记为修复；选择容易的表面项来填满占比 | 成果检查：最老的高利息项的年龄和事件链接在下降；对照排序评审修复了什么 |
| 债务净变化 | 解决许多微小的项以抵消少数大的；以“不修复”关闭项使计数下降 | 按规模区间和利息展示净变化；报告“不修复”这一行；对已解决项的再发检查 |

健康的读数显示一本可见、具体、并朝着团队所选方向移动的账簿。最老的高利息项在数量上下降。与未关闭已知错误相联的事件呈下降趋势，未链接的占比很小。债务容量占比稳定在商定的水平，而不是在危机之后飙升、之后又消失。接受风险的清单很短并经评审。当任何单个数字看起来极好而其他的毫无变动时，在庆祝之前先怀疑定义。

## 权衡：利与弊

| 方法 | 优势 | 劣势 |
| --- | --- | --- |
| 一本合并的已知错误与债务账簿 | 单一的优先级排序；运维和交付看到同样的成本 | 需要共享工具或链接；必须解决跨两个职能的归属问题 |
| 为修复工作设定常设的容量占比 | 可预测；保护修复工作不受功能压力的影响 | 如果排序薄弱，可能被花在低价值的项上 |
| 仅当修复赢得优先级争论时才安排修复工作 | 灵活；响应当前的优先事项 | 功能几乎总是获胜；账簿一直增长到发生危机 |
| 根据事件和被标记的工作估算利息 | 把债务与可观察的成本相联；支持排序 | 数字粗略；依赖诚实的标记和事件链接 |
| 专门的修复突击或“债务周” | 聚焦且进展可见 | 偶发性的；账簿在两次突击之间重新填满；打断计划中的承诺 |

选择能使最老的高利息项保持移动的最轻量的安排。小团队可以在一块看板上用一个标签和每月的评审来运行账簿。较大的组织需要工具之间的链接和商定的排序方法。目的是对每一项作出有意的决定，而不是一份空清单。

## 与团队讨论的问题

**1. 哪三个未关闭的项每个月让我们付出的代价最大？我们怎么知道？**
请人们凭记忆说出候选，然后对照事件链接和被标记的工作检查它们。比较记忆中的清单与度量出来的清单，并记下差距。商定从现在起如何收集排序的证据。

**2. 当我们推迟一项修复时，谁来决定？我们何时再看？**
走一遍最近的五次推迟，问谁接受了风险、设定了什么评审日期。凡没有人决定之处，该项是被忽视，而不是被推迟。商定一条规则：每次推迟都带有负责人、理由和触发因素。讨论接受风险的清单将如何评审，由谁来评审。

**3. 我们应当为修复预留多少容量？什么会改变这个占比？**
展示账簿的趋势和当前的债务容量占比。问团队愿意放弃什么来提高它，以及什么证据能让它下降。记录数字、理由和重新审视的日期。

**4. 我们的变通办法是真实的吗？一位新坐席能照着做吗？**
随机挑选一个变通办法，请一位没有写它的人照着做。商定对涵盖影响最大的错误的变通办法的测试例程。

**5. 什么算已修复？在关闭记录之前，我们观察多久？**
比较运维、交付和产品负责人所用的关闭规则。讨论适合该服务的再发窗口，以及当一个已关闭的项重新打开时团队会怎么做。商定一个定义并写入度量登记册。

**6. 我们的债务数字可能在哪些地方给我们讲了一个舒适的故事？**
问每个数字可能被美化的方式：未登记的债务、先修复容易的项、以“不修复”关闭的项。查看未链接的事件占比和接受风险的清单。选一道本季度要添加的护栏，并说出由谁检查。

## 四种视角

### 产品与交付团队

交付团队最先看到债务，通常是在更改代码时。他们受益于易于添加的登记册，以及受保护的容量占比，使修复工作不依赖于在每次规划交流中赢得争论。他们应当在走捷径时就登记它们，给由弱点造成的工作打标签，并避免把债务用作任何他们不想做的工作的标签（债务对前置时间的影响见主题 2.2，前置时间、周期时间与流动效率）。

### 服务与运维团队

运维团队看到的是利息：重复的事件、手工步骤、脆弱的变通办法，以及随之而来的值班负荷。他们拥有已知错误记录和变通办法文档，并拥有为利息定价的事件数据。他们应当把每起事件与其已知错误相联，测试变通办法，并把排好序的证据而不是一份抱怨清单带到规划交流中（见主题 5.7，繁琐工作与值班度量）。

### 领导层与治理

领导者决定修复工作获得多少容量，而他们设定的激励决定账簿是否保持诚实。他们应当索要年龄分布、利息数字和接受风险的清单，而不是单一的债务得分。把账簿读作对团队的评级，会惩罚登记，并把债务逼入地下。治理论坛应当把风险接受视为带负责人和评审日期的决定。

### 客户与用户

客户把债务感受为重复的失败和他们必须遵循的变通办法。凡变通办法影响用户之处，就连同预期何时修复的朴素说明一起公布，并守住日期或解释变更。更少的重复事件和对已知问题的诚实状态，比承诺没有缺陷建立更多信任（见主题 6.1，客户满意度度量）。

## 实践：一个服务管理示例

一家区域医院的 IT 部门运营着一项患者排程服务，由一个产品团队和一个运维小组支持。本示例中的所有数字均为示意。

运维小组在 ITSM 工具中保存了 23 个已知错误。产品团队在其看板上另行保存了 41 个债务项的清单。一次季度评审发现，其中 9 个已知错误和 7 个债务项描述的是同样的五个原因。最老的已知错误已有 14 个月，已知错误年龄的中位数为 5 个月，第 85 百分位数为 11 个月。变通办法覆盖率为 61%。与未关闭已知错误相联的事件占该季度事件的 18%，另有 22% 的事件未链接，所以真实的占比可能更高。

团队把两份清单合并成一本包含 55 个不同项的账簿。对关联事件最多的十个项，它以区间估算修复工作量，并以小时估算月度利息。有一项十分突出：一个夜间预约同步作业，大约每两周悄悄失败一次，需要值班人员手工重启。它的修复估计需要两周。它的利息，来自关联的事件和被标记的工作，约为每月 10 小时，而且每次失败都会延迟早晨的门诊清单。回收期约为四个月，比当时计划中的任何功能都更快。

记录在决定日志中的决定，是为产品团队的容量预留 15% 用于修复工作，按每单位工作量的利息排序，并先修复同步作业。运维主管还同意，凡存在已知错误之处，就把每起事件与之相联，并测试五个最常用的变通办法。

两个季度后，已知错误年龄的中位数为 4 个月，第 85 百分位数为 9 个月。与未关闭已知错误相联的事件降至 11%。未链接的占比降至 8%，这使团队对该数字更有信心。随后团队发现了一个钻空子的风险。债务净变化这一行显示，一个季度解决了 12 项，但其中 6 项是以不修复关闭的，而其中两项是最老的高利息项。一位团队之外的评审者阅读记录，发现这些关闭是为改善年龄数字而作出的。这些项被重新打开，关闭理由成为带指名批准人的必填字段，接受风险的项现在与年龄分布出现在同一页上。

## 敏捷、AI、自动化与分析

### 敏捷

把受保护的一份容量花在利息最高的债务上，并定期与干系人一起评审。需要注意的是，针对债务计数的目标会导致拆分和重新标注项。

### AI

AI 生成的代码可以迅速增加债务，AI 也可以帮助发现并偿还它。把 AI 辅助区域的债务净变化和与未关闭已知错误相联的事件单独跟踪，并加以标注。需要注意的是，建议修复的模型可能让根因原封不动。

### 自动化

把对陈旧已知错误以及依赖和开关腐化的检测自动化，并就误报来度量自动化。需要注意的是，自动化扫描器产生的噪声会掩埋重要的项。

### 分析

用每个项造成的事件和工作量估算利息，并给出范围。这为之提供依据的决定是接下来修复什么。需要注意的是，债务成本的估算是粗略的，所以避免虚假的精确。

## 行业视角

**初创公司。** 债务通常是有意的，往往也是对的，因为拿到第一位客户的速度最重要。在看板上保持一份带标签的清单，在走捷径时就登记，并设定评审日期，使“以后”有意义。当利息开始在事件中显现时，提高修复的占比。

**小型企业。** 单个管理员或小团队往往同时承担运维和交付，所以两份清单自然就是一份。把已知错误及其变通办法记录在一份共享文档中，并注明每一项依赖哪个供应商或合同。由供应商拥有的缺陷是你自己无法修复的已知错误，所以要跟踪供应商承诺的日期和你的变通办法。

**大型企业。** 众多团队、众多服务和众多供应商造成几份相互竞争的清单，以及几种“完成”的定义。确定一种账簿结构、一条关闭规则和一种排序方法，并让团队添加带有明确映射的本地字段。

**政府与公共部门。** 遗留系统、漫长的采购周期和固定的预算，使有些债务偿还起来代价高昂，有些替换决定迟缓。记录阻碍修复的法律、保留和审计方面的约束，因为它们解释了推迟。把账簿作为风险报告的一部分展示，并在预算周期中规划修复，而不是把它视为计划外的成本（见主题 8.5，受监管与政府报告）。

## 业务论证：动因、投资回报与总拥有成本

动因是停止支付你看不见的利息。重复的事件、手工的变通办法，以及缓慢而有风险的变更，是可见的成本，它们通常在不同的预算中被记录为独立的问题。合并的账簿把它们变成修复的成本与承担债务的成本之间的一次比较。

这项实践的成本有三个部分。第一是设置：一份登记册、ITSM 工具与跟踪器之间的链接，以及标记的约定。第二是运行工作量：每起事件几秒钟用于链接，每个工作项几秒钟用于标记，以及每项服务每月一两个小时的评审。第三是修复容量本身，它是最大的一项，并且是一项有意的投资，而不是开销。

回报来自你可以自己度量的模式。比较一个已知错误修复前后与之相联的事件、受影响变更上被标记的工作的小时数前后对比，以及避免的值班打断。如果你的组织已经估算了停机成本，就加上它。不要借用行业关于债务成本的数字：关于这个主题的研究文献是真实的，但数字取决于背景，你自己的事件和时间数据是更好的证据。《Accelerate》的研究把交付绩效与组织绩效联系起来（见主题 2.8，DORA 度量），尽管它没有给你的账簿定价。关于成本和回报更广泛的论述，见主题 7.7（投资回报与业务论证）。

## 反模式与陷阱

- **两份从不相遇的清单。** 运维和交付用不同的证据争夺同样的容量。合并清单，或把每个共同的原因链接起来。
- **整个组织一个单一的债务得分。** 它隐藏成本在哪里，并招致给团队排名。按服务报告账簿，附年龄、利息和归属。
- **把大重写作为唯一的修复。** 大型清理会停滞，而账簿在它们进行时重新填满。以小步淘汰各项，按回收期排序。
- **以零债务为目标。** 追求它奖励琐碎的关闭，并阻碍诚实的登记。以一本最老的高利息项在移动的账簿为目标。
- **在“已合并”时关闭已知错误。** 修复尚未到达用户，事件会回来。在发布时关闭，然后在规定的窗口内观察再发。
- **把推迟藏在“不修复”里。** 年龄数字改善而风险依旧。把接受风险单独统计，附负责人和评审日期。
- **把静态分析视为真理。** 得分反映的是代码的形态，而不是成本。用它来寻找候选，然后用事件链接和变更历史加以确认。
- **把债务归于作者。** 它教人们隐藏捷径、避开困难的组件。让每项测量值保持在服务和团队层面（见主题 1.2，古德哈特定律与度量的心理学）。

## 成熟度模型

| 维度 | 1 起步 | 2 发展 | 3 标准化 | 4 管理 | 5 协同 |
| --- | --- | --- | --- | --- | --- |
| 账簿与定义 | 已知错误和债务存在于人们的脑中或零散的笔记里 | 运维和交付各自保存一份清单，规则不同 | 一本账簿，附书面定义、负责人，以及每项的关闭规则 | 对照书面定义评审年龄、接受风险和净变化 | 当定义不再为决定提供依据时，与供应商和客户一起修订 |
| 度量利息 | 事件与原因之间没有链接 | 一些事件被手工链接到已知错误 | 凡原因已知，就要求事件链接；工作在团队层面被标记 | 为主要的项估算利息和回收期并做趋势分析 | 利息与服务成果相联，并在团队和供应商之间共享 |
| 容量与优先级排序 | 修复只在危机中发生 | 一些团队非正式地留出时间 | 商定的容量占比和通用的排序方法 | 依据账簿趋势调整占比，并作为计划工作获得资助 | 在共享平台和供应商之间协调修复容量 |
| 变通办法与关闭 | 变通办法没有文档，或掌握在一个人手中 | 为一些错误做了文档，未经测试 | 变通办法位于知识库中，附发布时关闭的规则 | 度量变通办法的使用、失败和关闭之后的再发 | 随着修复发布，变通办法被自动淘汰，并得到用户的反馈 |

## 检查清单

- [ ] 已知错误和债务项位于一本账簿中，或逐项相联。
- [ ] 每一项都有负责人、规模区间、服务和评审日期。
- [ ] 有意的捷径在走的时候就被登记，并附理由。
- [ ] 凡原因已知，事件都与已知错误相联，并报告未链接的占比。
- [ ] 由弱点造成的工作在团队层面被标记，且通过抽样审计标记情况。
- [ ] 每个主要的项都有修复工作量区间和月度利息估算。
- [ ] 为修复工作商定一份容量占比，加以报告，并每季度评审。
- [ ] 已知错误在修复发布时关闭，并附规定的再发窗口。
- [ ] 接受风险的关闭被单独列出，附批准人和评审日期。
- [ ] 对影响最大的错误的变通办法按计划测试。
- [ ] 连同总数一起展示年龄分布和按服务的划分。
- [ ] 没有债务度量被用来比较或给个人排名。

## AI 提示词

**把两份清单合并成一本账簿。**

```text
我有两份被推迟的修复的清单。清单 A 来自 [运维工具或来源]，有 [数量] 个已知错误。清单 B 来自 [交付跟踪器或来源]，有 [数量] 个技术债项。这是各条目：[粘贴条目，含标题、服务、登记日期和一行描述]。请把似乎描述同一原因的条目分组，为每组提出一个单一的账簿条目，并标出需要人来确认匹配的条目。不要虚构原因、服务或日期。请列出你的假设，以及在合并之前我应当回答的问题。
```

**为主要的项估算工作量区间和月度利息。**

```text
对于 [服务] 上的账簿项 [项标题]，我有这些证据：关联的事件 [附日期和持续时间的清单]、被标记的工作 [小时数或项数]，以及团队的修复估算 [估算]。请帮我写出粗略的工作量区间和月度利息区间、一个简单的回收期，以及每个数字的置信水平。展示你的算术。不要虚构成本、基准值或行业数字。如果缺少某个数字，请向我索取。请列出你的假设。
```

**评审关闭和钻空子风险。**

```text
这是我们已知错误与债务账簿的定义以及上个季度的数据：[年龄、变通办法覆盖率、债务净变化和关闭规则的定义] 以及 [已关闭项的摘要，附关闭理由]。请找出这些度量可能被美化的方式、数据中表明它已经发生的证据，以及各自的护栏。把这当作对仪器的评审，而不是对人的评审。不要指控任何人，也不要虚构数据。请列出你的假设。
```

**为与产品负责人的优先级排序交流做准备。**

```text
我需要就 [团队] 下个季度如何在功能与修复工作之间划分容量提出建议。账簿显示 [账簿摘要：计数、年龄分布、带工作量和利息区间的主要项]。功能计划包含 [由产品负责人提供的计划功能及其预期价值的摘要]。请起草一份一页纸的提案，比较修复占比的各种选项，说明主要修复项的延迟成本，并指明各种取舍。不要虚构价值估算或基准占比。请列出你的假设，以及产品负责人必须作出的决定。
```

## 要点

- 已知错误和技术债是同一本被推迟的修复的账簿的两种视角，所以把它们放在一起或相联。
- 度量每一项每个月让你付出的利息，即在事件、变通办法和被拖慢的变更方面，并按回收期给修复排序。
- 让每次推迟都成为带负责人、理由和评审日期的决定，并单独报告接受风险。
- 为修复工作预留商定的容量占比，并把它与计划工作并排报告。
- 在修复发布时关闭已知错误，然后在信任结果之前先观察再发。
- 让每项测量值保持在服务和团队层面，并使用护栏，使更好的数字意味着更好的系统。
