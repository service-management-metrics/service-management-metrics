# 第 9 部分导读：人员、团队与改进度量

**每项服务都依赖受到激励、得到支持、并能自由改进自己工作的人，所以本部分中的测量值描述条件和习惯，没有一项是给任何人排名或监视任何人的办法。**

本书的前八个部分描述服务、流动和记录。本部分转向构建和运行它们的人。每项度量背后都站着一个必须与之共处的团队，而工作的质量不可能高于团队工作所处的条件。《敏捷宣言》的原则说得很直白：围绕有积极性的个人来构建项目，给予他们所需要的环境和支持，信任他们能把工作做好，并让他们能够无限期地保持恒定的节奏。它们还说，团队应当定期反思如何变得更有成效。本部分中的测量值，就是使这些话变得可检查的办法。

由 ITIL 所规范的 IT 服务管理（ITSM），通过其劳动力与人才管理、知识管理、组织变革和持续改进实践，触及同一片领域。两种传统在本质上是一致的：人们需要清晰的目标、发声的安全、学习的时间，以及对工作如何被组织的发言权。它们不同之处，大多只是词汇。

本部分承载了本书中最重的伦理负荷。涉及人的测量值可能滑向监视、制造恐惧，并产生虚假的答案。单单一次错误的使用，比如依据投入度得分给个人排名，或跟踪在线时间，就可能毁掉多年的信任，并使之后的每项度量都变得无用。因此，这里的每个主题都说明其隐私规则，在团队层面汇总，设定最小群体规模，并禁止在个人评价中使用这些数据。每项度量仍然附带它被钻空子的方式和一道护栏，因为即使是出于善意的关于人的测量值，在变成目标时也会被扭曲（见主题 1.2，古德哈特定律与度量的心理学）。

四个视角塑造了本部分。可持续的节奏和有积极性的个人，是这些测量值的目的。AI 助手改变工作负荷和技能，所以要直接询问收益和负担。自动化应当用于收集和提醒，而不是监控人。分析应当在团队层面报告，附回复数和最小群体规模。

## 本部分的主题

- **9.1 团队健康与开发者体验**：反馈闭环、认知负荷、心流、由团队拥有的健康检查，以及消除障碍。
- **9.2 满意度与福祉度量**：可持续的节奏、心理安全、工作负荷压力，以及如何在不窥探、不诊断的情况下询问。
- **9.3 协作与交接度量**：交接、等待、依赖、实时协作、共享的知识，以及干系人响应时间。
- **9.4 技能与学习度量**：受保护的学习时间、交叉培训、入职、实践社区，以及跨团队分享的经验教训。
- **9.5 持续改进度量**：对行动的落实、效果检查、重复出现的问题，以及用于改进的容量。
- **9.6 组织变革与采纳度量**：目标的清晰度、对照比较的成果、变革负荷、自愿的采纳，以及实践与仪式之间的区别。

## 这些主题如何相互关联

主题 9.1（见主题 9.1，团队健康与开发者体验）描述日常的条件：反馈到达有多快、心智上的负荷有多重，以及人们是否能够集中注意力。它引入了贯穿整个部分的规则，即团队拥有自己的健康检查，并首先阅读结果。主题 9.2（见主题 9.2，满意度与福祉度量）走向更深的问题：节奏是否可持续，以及人们是否觉得安全地说出来，并给出本书中最严格的隐私规则。

主题 9.3 和 9.4 查看工作和知识如何在人们之间流动。交接和依赖（见主题 9.3，协作与交接度量）显示工作在哪里等待。技能与学习（见主题 9.4，技能与学习度量）显示知识是否传播得足够广，使等待和风险下降。两者都依赖前两个主题中的条件：没有专注时间、或没有安全地求助的团队，不会分享其所知道的。

主题 9.5 和 9.6 以改进和变革为本部分收尾。持续改进（见主题 9.5，持续改进度量）问想法是否变成了变更，以及变更是否被检查。组织变革（见主题 9.6，组织变革与采纳度量）问一种新的工作方式是因其预期的理由而扎根，还是仅仅作为仪式而传播。两者都是对前面所述条件的检验：改进需要受保护的时间和安全，而无视节奏和人的变革会失败。

由此得出几组护栏配对。团队健康得分应当与障碍清单以及针对它所做的事一起阅读。福祉脉冲应当与团队层面的工作负荷事实一起阅读，绝不与个人的工时一起。学习测量值应当与使用中的能力证据一起阅读，使出席不代替技能。采纳数字应当与对照比较组的成果一起阅读，使形式不被误认为实质。

本部分借鉴前面各部分的测量值：流动和规划（见主题 2.5，交付预测与规划度量）、运营负荷（见主题 2.9，运维工作与计划外工作）、繁琐工作和值班（见主题 5.7，繁琐工作与值班度量），以及内部用户的体验（见主题 6.4，用户与员工体验）。它通向最后两个部分：AI 改变这些测量值中许多的含义，而度量计划本身就是一项变革，需要以本部分所描述的细心来引入。
